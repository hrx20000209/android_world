# MobileExplorer 当前设计（2026-09-08，v42）

本文对照论文的三个模块，说明**代码里实际实现的是什么**，以及每处设计选择背后的实测依据。所有数字来自 `results/` 下的真实跑测。

实现分两套 runner，共享同一批组件：

- `scripts/run_one_parallel_exploration_task.py` — 并行版，探索藏在推理窗口内（论文主张的形态）
- `scripts/run_serial_exploration_task.py` — 串行版，探索串在推理之间。**只用于快速验证机制，延迟数字不可用**：串行探索在关键路径上，而 LabServer 上一次推理仅 1-3 秒，省不回探索的开销。延迟收益必须回并行版、在慢后端上测。

## 三问速览：图存了什么 / 怎么增强探索 / 怎么增强推理

这一节是全文的索引，每条都给出代码位置。下面各模块是同一件事的展开。

### 一、图保存了什么？怎么更新？怎么选元素？

**节点存什么**（`belief_graph.py:71` `GraphNode`）

| 字段 | 含义 | 谁在读 |
|---|---|---|
| `node_id` | `sha256(activity, layout_signature)[:20]` | 一切 |
| `layout_signature` | 只含可交互控件骨架（class + resource_id + 粗位置），**不含文字、不含像素哈希** | 节点身份 |
| `visual_signature` / `structural_signature` | 严格签名（含文字、pHash） | **只用于回滚验证** |
| `visit_count` | 真实站上这块屏幕的次数（探测落点不算） | 跳过门、探索门 |
| `decision_entropy` | `H = -Σ p_j log p_j`，对本节点所有可行出边 | 跳过门 |
| `salient_ui_labels` / `freshness` / `status` | 显著标签、时效、`COMMITTED/SPECULATIVE/STALE/INVALID` | 蒸馏器、过期 |

节点身份用**宽松**签名、状态验证用**严格**签名，是两个不同问题——用一个签名回答会顾此失彼。宽松是必需的：含文字的签名会把 `ExpenseAddMultiple` 的一个列表 Activity 裂成 5 个从不重访的节点，渐进式记忆无从积累。

**边存什么**（`belief_graph.py:97` `GraphEdge`）

`edge_id = sha256(源节点, canonical_action)[:24]`，**目的地不参与身份**（`belief_graph.py:218`）。`canonical_action`（`belief_graph.py:34`）优先用 `control_key = resource_id|text|content_desc|class`，**不含 bounds、不含坐标**——模型预测的坐标会抖动，同一个按钮点 11 次曾被记成 (540,1063)×6 和 (540,1068)×5 两条边。

边上分三类信息：

- **动力学**：`observed_destinations`（这条转移去过的所有落点）、`discovered_labels`（落点上**新增**的标签，≤8 个）、`inverse_level`（哪一级恢复动作真正撤销了它）
- **意图**：`inference_alignment_count`、`execution_hit_count/miss_count`、`nodes_at_last_execution`
- **代价与安全**：`probe_count`、`rollback_success_count/failure_count`、`cumulative_realized_ig`、`cumulative_exploration_cost`、`skip_attempt_count/success_count`、`risk_level`

状态机 `UNEXPLORED → SPECULATIVE → INFERENCE_ALIGNED → VERIFIED → REUSABLE`（+`STALE`/`INVALID`）。

**每步怎么更新**（`run_serial_exploration_task.py:1491` `serial_step`，顺序即代码顺序）

1. **开窗**：`capture.capture()` → `src_id` → `upsert(visited=True)`（`visit_count += 1`）
2. **前缀对齐**：上一步探测过的深度 1 边，若其 `dst_node` 等于模型这一步真实落点 → `record_inference_alignment` + `promote_children_of_aligned_prefix`（深度 2 子边升 `REUSABLE`）
3. **bootstrap 折叠**（step 0、在桌面、任务点名了应用）：直接 `open_app`，**不占一个计数步**，落地后重新 capture、重新 upsert
4. **跳过判定**（读 step *i−1* 快照）→ 命中则执行并 `record_execution_verification` + `record_skip_result`，整条路径记 **1 步**
5. **起探索进程**（在推理之前，与推理并行的位置）
6. **蒸馏 + 注入**（读同一份 step *i−1* 快照）
7. **推理** `original_step`
8. **记权威边**：`add_speculative_transition(..., path_probability=1.0, risk_level="SAFE")` + `record_execution_verification(True)`，写 `nodes_at_last_execution = len(graph.nodes)`，同时喂跨任务记忆 `observe_execution`
9. `commit_step()` — 这一步的写入到此才对下一步可见

**时序不变量**（`run_serial_exploration_task.py:294` `GenerationGuardedGraph`）：step *i* 只能读 step *i−1* 的**拷贝**快照，读当前世代直接抛 `GenerationError`。这不是防御性编程，是复刻并行版语义——串行执行时唯一阻止泄漏的本来只有自觉。

**探测怎么选元素**（`live_probe.py:1204` `select_candidate`）

```
候选池 → StateGraphInformationMatrix.build（8 组特征）
       → SafetyGate.evaluate（硬过滤，在打分之前）
       → PredictiveElementScorer.rank
       → 全部候选带名次落盘 scored_candidates.jsonl
```

安全是**门**不是**分**（`state_graph_information.py:347`）：排序是相对的，全部候选都很差时最不差的仍会被探测——这对"有用性"对，对安全错。一次不可撤销的探测代价不是选了个次优，是整个 episode 走不下去。

### 二、图的信息怎么增强 exploration？

**（a）选元素：矩阵 → 安全门 → 打分器**

`CandidateInformationRow`（`state_graph_information.py:151`）八组特征，其中**四组来自图**：

| 组 | 来源 | 例子 |
|---|---|---|
| A1.1 当前 UI | 截图/a11y | `role` `norm_x` `clickable` `nearby_text` |
| **A1.2 节点成熟度** | **图** | `node_visit_count` `node_decision_entropy` `exploration_coverage` |
| **A1.3 精确边历史** | **图** | `alignment_rate` `execution_hit_rate` `rollback_success_rate` `mean_realized_ig` |
| **A1.4 目的地** | **图** | `destination_visit_count` `destination_entropy` `destination_in_recent_path` |
| **A1.5 上下文历史** | **图（聚合）** | 按 `(probe_type, role, need_type)` 聚合的成功率 |
| A1.6 信息需求 | 上一步模型输出 | `target_match` `risk_conflict` |
| A1.7 安全 | 图 + 黑名单 | `estimated_recoverability` `blocked_element` |
| A1.8 代价 | 图 + 先验 | `expected_total_exploration_cost` |

**未观测的统计一律 `None` 而非 `0.0`**——把"对齐率 0%"存给从没试过的候选，会让它排在已被证明无用的候选之后，正好反了。

A1.5 按**交互种类**聚合而不是按控件文字：「列表屏上的菜单探测有 84% 能回滚」可以跨应用迁移，按文字聚合就变成了应用专属规则。

打分公式（`state_graph_information.py:808`）：

```
utility(e) = path_probability(e) × expected_IG(e) / max(0.5, expected_cost(e))
硬约束（打分前执行）: estimated_recoverability ≥ 0.55，未拉黑，未跨包，risk ∉ {HIGH, IRREVERSIBLE}
```

图历史如何改变排序：

| 图里的情形 | 效果 |
|---|---|
| 反复与模型真实动作对齐 | `path_probability` ↑（Beta-Binomial 收缩，`prior_strength=3`） |
| 反复产出有用目的地 | `expected_IG` ↑（`mean_realized_ig`） |
| **反复回滚失败** | **判为不可行，打分前剔除** |
| 目的地已知 | `expected_IG × 0.25`——推动成熟节点转向未探候选 |
| 目的地在最近路径 | `× 0.5` |
| 反复通向无关分支 | `× 0.5`（降权，不封禁） |

全部由图统计涌现，没有任何按应用/按任务的规则。所有权重集中在 `ScoringConfig`（`state_graph_information.py:61`）一个 dataclass。

**（b）图怎么"总结"给探索**：不总结成文字。探索进程拿到的是 `dataclasses.asdict(snapshot)` —— step *i−1* 的**结构化拷贝**，加上三份从图里抽出的表：

- `blocked_recovery_contexts`：`(activity, probe_type)` 已在本局吃过一次不可恢复
- `blocked_element_identities`：曾把设备带出应用包的元素
- `known_inverse_levels`：`(activity, probe_type) → 真正管用的那一级恢复动作`——探索**从这一级起步**，而不是每次从阶梯顶端重走

**（c）图怎么决定"该不该探"**（`run_serial_exploration_task.py` `may_probe`）：`step ≥ 2`、`node_visits ≥ 2`（或跨任务记忆里见过这块屏幕）、非系统设置包、屏幕上无未保存输入、本局尚未出现过未复原的探测、本局探测总量 < 12、距上次探索 ≥ `explore_interval`。

### 三、图的信息怎么增强 reasoning？

一个门（`graph_distiller.py:384` `ReasoningGate`）从**同一份**信念状态里决定三选一，不是三套独立逻辑：

```
                  step i−1 快照
                        │
              ┌─────────┴─────────┐
        有可复用边?              没有
              │                   │
        _skip_blocked()           │
         ├─ 通过 → SKIP_INFERENCE │
         └─ 被挡 ─────────┬───────┘
                          │
                    蒸馏出正面事实?
                    ├─ 有 → GRAPH_ENHANCED_INFERENCE
                    └─ 无 → NORMAL_INFERENCE
```

**（a）怎么跳过**（`run_serial_exploration_task.py:146` `reusable_edge`）

两个来源，证据性质不同：

1. **确定屏幕上的权威边**：`entropy ≤ 1e-9` 且 `node_visits ≥ 2` 且该节点**只有一个**模型选过的可行出边（`execution_hit_count ≥ 1`）且那条边 `execution_hit_count ≥ 2` 且 `skip_replays < 2` 且**图在两次执行之间长出过新节点**（`len(node_visits) > nodes_at_last_execution`）。最后一条是区分"任务在迭代"和"agent 在打转"的唯一办法：迭代会发现新屏幕，打转不会。
2. **前缀对齐的前瞻边**（`REUSABLE`）：探索在深度 2 探到、其父边被模型真实动作确认过。这是唯一能**领先**权威路径的来源，但实测几乎不产生（四次跑测共 2 次晋升，见「前瞻通道的实测现状」）。

**曾经的第三个来源已删除**：只要屏幕重访就重放模型上次的选择。按来源拆开统计（2026-08-31）：bootstrap 80/80，这一类 3/17，且每个步数变差的离群任务都是它造成的。屏幕看起来一样 ≠ 处境一样。

多跳（`reusable_path`，≤3 跳）在**同一个计数步内**连续执行——这是唯一真正缩短轨迹的机制，此前的跳过只省推理不省步数。每跳按 `observed_destinations` **集合**校验（模型重复的动作本来就会落到不同屏幕），一旦不符立即中断交还模型。

安全阀：每局 ≤2 次、一错即停、连续 ≤3 次、本局命中率过半才允许多跳、不跳回最近节点（对模型自己重复 ≥2 次的转移豁免）。

**（b）怎么把图总结成信息**（`graph_distiller.py:174` `GraphDistiller`）

`retrieve → filter → score → compress → template`，**全程确定性，零模型调用**——一次总结调用的成本约等于它要省下的那次推理。

- `_retrieve`（`:181`）：**只取当前节点的出边**，一跳。屏幕之外的东西模型这一步用不上，占的是截图的位置。
- `_to_fact`（`:191`）：每条边 → `GraphFact`，四型 `VERIFIED / OBSERVED / DONE / NO_RELEVANT_EVIDENCE`。
  - **只能用坐标命名的控件直接丢弃**——模型在截图里找不到它。`_action_label`（`:151`）同时读 `control_key` 和 `element_identity`：此前只读后者，而只有探测边带 `element_identity`，于是**模型自己走过的边只能用坐标命名，全部被这条规则滤掉**——这就是 116 个任务里从未注入过任何图上下文的原因。
  - `utility = (0.25 + need_match) × certainty_weight × (0.5 + 0.5 × historical) × freshness`，`freshness = exp(-代龄/6)`
- `compress`：≤3 条事实、≤64 token、**负面事实至多 1 条**、`utility ≥ 0.15`
- **没有任何正面事实就整段不注入**（`distill` 末尾）：只剩一条 Need 行和一个死胡同时，注入的是模型自己的话加一条它用不上的信息。

三条硬规则，都由实测反例逼出来：

| 规则 | 反例 |
|---|---|
| **陈述，不是建议** | 早期写「Tapping X opens Y」，模型照做，`MarkorCreateFolder` 在 "+" 和文件名框之间循环 10 步 |
| **没有覆盖率不谈"没有"** | 「Reviews 没有电话号码」是对整棵子树的断言，探索只看过一个探测；改为「未观察到相关证据」，且 `probe_count ≥ 1` 才允许说 |
| **坐标不能当控件名** | 「the control at (540,605) already used」曾是一整次注入的全部内容 |
| **只记落点上新增的标签** | 取全部标签会把应用自己的工具栏当成事实：「FOLDER -> {Markor, Go to, Sort by, Search}」注入 3 次，任务从 5 步变 15 步 |

**（c）怎么注入 prompt**（`run_serial_exploration_task.py:1461` `build_with_briefing`）

包装 `gelab_agent.build_gelab_messages`，把蒸馏结果追加到第一个 text content 之后：

```
[Memory]
Need: Zucchini Noodles with Pesto.
Verified: Details -> {Phone, Address}.
Done: FOLDER already used.
```

`briefing_now["text"]` 在**推理之前**由 step *i−1* 快照填好，所以这一步自己的探索结构上不可能混进来。

**这条通路曾经从未接通**：安装条件原本只有 `--inject_briefing`，而没有任何批次传过这个 flag——蒸馏器每步算完就丢，模块三在任何一次全量跑测里都没有端到端跑过，"注入是中性的"那个测量测的是空气（2026-09-02 定位）。现在改为 `args.inject_briefing or args.graph_context != "off" or args.decision_constraints` 时安装。

## 模块一：探索与逆动作回滚

### 探索什么

动作空间限定 **click 与 scroll** 两类，且**只在深度 1**。这不是为了省事，而是可恢复性决定的：这两类的逆动作明确（滚动反向滚回、点击导航用 Back），其余的不是。2026-08-31 曾加入 `TYPE_TEXT` 与 `LONG_PRESS`，长按会弹出上下文菜单、消除后留残留，五个任务全部比 baseline 多跑 3-4 步（`MarkorDeleteNote` 5→9、`MarkorCreateFolder` 5→8），随即移除。它们只占模型动作的 11%，换不来一条不可信的恢复路径。

**TAP_NAV 深度 1 需要屏幕先"挣到"资格**：该屏幕必须已有一次**精确恢复**（`NOOP` 或 `INVERSE`，不算 `BACK_N`/`DEEPLINK` 这些近似档）才允许点击式探测。依据是 264 次探测的分类型统计（2026-08-31）：SCROLL 深度 1 回滚成功 **91%**（52/57），其中 48 次是精确恢复；TAP_NAV 深度 1 只有 **72%**（102/141），并且贡献了全部 55 次失败中的 39 次。差别是结构性的——滚动的逆动作是同一手势反向，点击的逆动作是 Back，Back 能还原导航，还原不了屏幕当时显示的内容。SCROLL 在哪都能用，所以探索仍然每步在跑，只是先在没测过的屏幕上做那件便宜且可精确撤销的事。

进一步按**实测回滚可靠性**筛选探测类型，只保留 `TAP_NAV`（失败率 7%）与 `SCROLL`（10%），去掉 `TAP_MENU`（16%）与 `EXPAND`（23%）。v4 整体 21% 的回滚失败率主要由后两类贡献，去掉后降到 7%。

**深度 2 已恢复，改为按证据放行**（`live_probe.py:1173` `inverse_is_known`，开关 `--depth2_needs_known_inverse`）。深度 2 是前瞻跳步（`REUSABLE` 边）的唯一来源，直接砍掉等于放弃整条能领先权威路径的通道；而它 20% 的回滚失败率是可以定向消除的。现在的规则是：**只有当到达那里的那次深度 1 探测，在这块屏幕上已经演示过一次干净的逆动作（`NOOP` / `INVERSE` / `INVERSE_ANCHOR`）时，才允许下降到深度 2**。

这个条件只加在深度 2，**绝不加在深度 1**——加在深度 1 是循环论证：一块屏幕正是靠被探测才学到自己的逆动作。这个错误实测过（2026-09-04）：三个任务跑出 12 轮探索、0 次探测，104 个候选全部因为「缺少一个还没有人可能记录过的逆动作」被拒。深度 2 没有这个循环，因为把探索带到那里的深度 1 探测已经演示过一次了。

候选由 `InformationNeedRanker` 排序（见模块三的 reasoning prior）。

### 什么时候探索

按屏幕**在线学习可恢复性**，而不是按"节点是否见过"：

- 任一 `(activity, probe_type)` 组合，第一次允许试探
- 该组合在此屏幕上回滚失败过 → 此后不再尝试
- 深度 2 只从「已知逆动作」的根节点下降（见上），失败则该屏幕整个关闭深度 2
- 上一步回滚失败 → 本步不探索，不在未验证的状态上叠加扰动

早先用的是「只探索图里没有出边的新节点」，理由是已有出边的节点熵低。那个判断关于信息是对的，关于风险却是无关的，代价是**探索从 82% 的步骤中消失**（145 次真实点击里 119 次发生在完全没有探测的步骤上）。前缀对齐需要先有猜测才谈得上准不准，当时的 1.7% 是因为根本没猜。

### 探索之后的主动修复

阶梯走到底时只是报告失败然后停手，而下一步推理会直接读到探测搁浅的那块屏幕。现在探索轮结束后检查前台包名：**只要跑出了应用**，就先按 Back（最多 3 次，能保住应用内进度）、不行再 HOME + 重新打开。全量跑测里这条路径 14/14 全部成功把应用带了回来。

重新拉起后若落在**系统对话框包**（`permissioncontroller` / `packageinstaller` / ResolverActivity），按 Back 消掉再验一次，而不是把系统弹窗丢给模型——拉起短信类应用时 Android 会要求授予默认短信应用角色，模型撞上去就会反复点同一个按钮直到耗尽步数。这是关于系统对话框的框架级事实，不是应用专属规则。

只在**真的跑出应用**时才修复：留在应用内但状态没完全还原时重开，会把应用内进度一起丢掉——实测把成功任务的平均步数从 7.2 推到 10.4。留在应用内的情形交给"本 episode 停止探测"的规则处理，不动设备。

修复是在 agent 的动作历史之外执行的（和 bootstrap 一样），不占用 episode 的步数预算。

### 回滚阶梯

`NOOP → INVERSE → BACK_N → BACK_OVERLAY → DEEPLINK → TRAJECTORY_REPLAY → FAILED`，每级执行后重新捕获状态并与基线严格比对（activity + 结构签名 + pHash）。

`NOOP`（判定探测没造成影响、无需回滚）额外要求**元素几何位置逐一相同**。结构签名对滚动位置是盲的——它只记录哪些控件存在及其粗粒度位置，列表滚过之后哈希不变。此前 178 次成功回滚里有 55 次判为 `NOOP`（16 次 `SCROLL`、39 次 `TAP_NAV`），其中相当一部分屏幕实际已被改动却直接放行，导致该臂的失败中 53% 是"模型提前宣布完成"，而 baseline 只有 25%。加入几何比对后这一比例回落。

**Back 不能从应用根部按下去。** `BACK_N` 的按数原先是 `max(1, post_depth - baseline_depth)`——探测没往栈上压东西时，那个 `max(1,...)` 会强行按一次 Back，而从应用自己的根 activity 按下去就是桌面。探测轨迹显示，几乎所有"失败"的探测其实都**停在应用自己的界面里**，是恢复过程把设备走出去的：22 个 episode 里有 8 个是从桌面或另一个应用被捞回来的（2026-08-31）。现在按数就是栈深差，只有栈比根更深时才允许那一次额外的 Back（用于关掉同 activity 上的浮层）；任何一级把包名走离应用，立刻用 `am start` 重新进来再继续往下走。

**`TRAJECTORY_REPLAY` 不能对着桌面重放坐标。** 它先按 HOME 再重放已提交的动作；若某个 `open_app` 解析不到包名就被跳过，后续的盲点坐标全部落在 launcher 的图标上——这就是"给记账应用做回滚，结果落到 YouTube"的来源，实测出现过两次。现在解析不到就立即中止，并且**轨迹里根本没有可解析的启动动作时不按 HOME**，就地重放。

`TRAJECTORY_REPLAY` 需要主 agent 已提交的动作序列才能从 HOME 重建状态。串行 runner 最初漏传这个列表，导致阶梯直接见底：107 次失败全部停在 `FAILED`，失败率 49%（并行版同期 13%）。补上后降到 34%。

**逆动作记忆**：成功撤销某转移的那一级记在 `GraphEdge.inverse_level` 上，按 `(activity, probe_type)` 查表，下次从该级直接开始。阶梯是按代价从低到高排的，从头走一遍在第一次是对的、之后每次都是浪费——需要 `BACK_N` 的屏幕，每次探测都要先白试一次 `INVERSE`，而那本身就是一次真实的设备交互。实测回滚占单次探测耗时的 613/1584 ms。

## 模块二：渐进式记忆（信念图）

### 节点身份

`node_id = hash(activity, layout_signature)`。`layout_signature` 只保留**可交互控件的骨架**：class + resource_id + 粗粒度位置，不含文字、不含像素哈希。

关键一条：**重复出现的控件只记种类不记位置**。列表有 3 行还是 4 行是数据，不是身份。没有这一条时，重复性任务每迭代一次就产生一个全新节点——`ExpenseAddMultiple` 的单个列表 Activity 裂成 5 个节点，永远不会被"重访"，渐进式记忆无从积累。

严格的 `struct_sig` 与 `phash` 保留在节点上，专用于回滚验证——那里要回答的是"是不是我离开时的那个状态"，严格正是所需。**节点身份（宽松）与状态验证（严格）是两个不同的问题**，用同一个签名回答会顾此失彼。

### 边身份

`edge_id = hash(源节点, 规范化动作)`。**目的地不参与身份**，它是这条转移被观察到会去往的地方，不是这条转移本身。

这一条是整个跳过机制能否成立的关键，而它曾经是错的。原先的 `hash(源, 动作, 目的地)` 把一次重复的决策拆成了多条边：`RecipeDeleteMultipleRecipes`（2026-08-31）里，模型在菜谱详情页三次都点了同一个控件，但每次删完剩下的列表都少一个菜谱，三次落点哈希成三个不同节点，于是图记下的是**三条各自只有一次执行的边**，而不是一条执行了三次的边。任何"模型在这里做过这件事吗"的判断读出来都是 1，渐进式记忆最该服务的重复型任务，恰恰是它永远无法触发的那一类。

合并之后，同一个节点立刻呈现 `execution_hit_count=3、出度 1、决策熵 0` 的确定情形。目的地全部保留在 `observed_destinations` 里：只有一个说明这条转移是确定性的、重放可以按它校验；有多个说明动作仍然是对的，但落到哪里取决于图没有建模的状态，校验必须相应放宽。

### 边与状态

`UNEXPLORED → SPECULATIVE → INFERENCE_ALIGNED → VERIFIED → REUSABLE`（另有 `STALE`/`INVALID`）。

两种来源，证据强度完全不同：

- **权威边**：agent 真实执行过的转移。这个动作本来就要发生，记录它零成本、零风险。它携带**意图**——"模型在这个处境下选了它"。
- **投机边**：探测试出来的。只携带**动力学**——"这个动作能到那儿"，不含意图。

实测差异极大：用权威边跳过的命中率 75%，用未对齐的投机边只有 37-48%。跳步需要的恰恰是意图，所以两者走不同通道（见模块三）。

### 每步更新

- 真实执行的转移记为 `VERIFIED` 边，并附目标页面的显著标签
- 探测结果经 `ingest_probe_trace` 入图为 `SPECULATIVE`；回滚未验证的行直接丢弃（落点不可信）
- 每步重算所有节点的决策熵 `H = -Σ p_j log p_j`
- `visit_count` 只在真实落地时累加

### 时序边界

图带**世代号**：step *i* 只能读到 step *i-1* 结束时的快照，越界抛 `GenerationError`；快照是拷贝，不会事后长出新边。

这不是防御性编程，是复刻并行版的语义。并行版里 step *i* 的探索与 step *i* 的推理**同时**发生，模型从构造上看不到它；串行执行会把探索结果放进内存、就在推理调用之前，此时唯一阻止泄漏的只有自觉——而自觉正是后续改动最容易弄丢的东西。

## 模块二补充：跨任务的应用结构记忆

信念图每局从零重建，这会丢掉两类性质完全不同的知识：

- **这个应用是什么**——哪个控件通往哪块屏幕、那里有什么、恢复阶梯的哪一级能撤销这里的点击、哪些探测被证明不可恢复。这些与任务无关。实测（2026-09-01，三次全量跑测）：**33% 的屏幕跨任务复现，平均每个被 4.0 个任务访问**；9 个 `(activity, probe_type)` 组合在多个任务里重复回滚失败，共 14 次探测事故——而"有一轮未复原"的 episode 成功率是 67%，"每轮都复原"是 89%，这 14 次不是免费的。
- **模型决定了什么**——它在这块屏幕上选了这个控件、选了几次。这完全是任务专属的：上个任务在菜谱列表点了删除，不代表这个任务也该点。跨任务复用意图会去喂已被测量证明有害的跳过（有跳过的任务 1/17，对照 6/17）。

所以只有第一类持久化。`android_world/parallel_exploration/app_memory.py`，按 package 一个 JSON 文件。

### 切分线

| 跨任务持久化 | 每局重建 |
|---|---|
| 屏幕节点、投机边、`discovered_labels` | `execution_hit_count` |
| `(activity, probe_type) → 逆动作级别` | `visit_count` |
| 回滚失败黑名单、跨包逃逸元素 | `skip_replays`、`nodes_at_last_execution` |

`seed_graph` 播种时把执行计数强制写零，节点的 `visit_count` 不动——**一块上个任务见过的屏幕，仍然必须在本局被重访过，才可能触发任何重放**。这条由单测锁定，不靠自觉。

### 动力学来自每一步，不只是探测

最初只有探测产生的转移进入记忆，结果 **19 个任务只攒出 7 条转移**，对着 70 多块屏幕，播种几乎无料可用。探测太稀少了。

而 agent 真实执行的转移**同样描述这个应用**：「点 Details 会到详情页」是动力学，「模型选了 Details」才是意图。我最初把整条权威边都排除了，应该只排除意图那一半。修正后（`observe_execution`）转移数随任务线性增长，全量跑测累积到 **300+ 屏幕、500+ 条播种边**。

`observe_execution` 与 `observe_probe` 分开：真实执行从不回滚，把它算进回滚统计会虚高 `seed_graph` 读到的可恢复性。

### 离开应用不是关于应用的知识

跨任务记忆会把**失败轨迹里的动作**当作应用动力学固化下来。实测（2026-09-02）：每个短信任务的 prompt 里都被注入了

```
[Memory]
Verified: Cancel -> {Sun, Oct 15, 0, Gmail, Photos}.
```

`Gmail`、`Photos` 是**桌面**的内容。这条事实来自更早某个 episode——它卡在"设为默认短信应用"的系统弹窗里，点 Cancel 逃到了桌面，这个动作被记成权威边，跨任务记忆把它固化，然后复述给之后每一个短信任务。技术上没错，完全无用。

所以**目的地是桌面或系统弹窗的转移不构成关于应用的知识**。文件选择器是应用真的会送你去的地方，值得记住；桌面不是。

这条要在**两处**同时生效，缺一不可：

1. **记忆层**（`app_memory.py` 的 `_is_app_destination`）——这类转移不写入持久化记忆；探测若逃逸，**回滚记录仍然保留**（探测花了什么代价值得记），但目的地和标签不保留。
2. **本局图**（runner 记录权威边处）——只修记忆层不够：这条边在每个 episode 里都会被重新造出来，而蒸馏器读的是本局图。现在这类转移仍然记录（图需要知道 agent 去过那里），但**不携带目的地标签**。

修复代价为零：全量跑测在同一批 113 个任务上成功数与修复前完全相同（45 vs 45），而配对步数从 −0.97 改善到 **−1.08**，图跳过从 16/17 做到 **15/15（100%）**。

## 模块三：跳过推理 / 增强推理

### reasoning → exploration（论文 Eq. 4）

`parse_reasoning_prior` 从模型自己的 `<THINK>` / `explain` / `summary` 中提取

```
P_{i-1} = { K_target, A_expect, K_risk, U_miss }
```

即目标关键词（引号内容、专有名词、文件名）、期望控件类型、风险词、未解决的信息缺口，作为探索候选排序的一路信号。**零额外模型调用**——这是能塞进推理窗口的前提。

此前这条边根本没接：`parse_information_need(None, task_text)` 的第一个参数恒为 `None`，排序器只能拿**整个 episode 恒定不变的任务目标**做匹配，在第一屏和最后一屏给出的排序几乎一样。

### exploration → reasoning：跳过推理

三个来源，按实测证据强度排列（全量 116 任务，2026-09-01）：

1. **app bootstrap（四次跑测 368/368，零失误）**：任务描述里点名的应用，第一步必然是打开它。这个决策由任务文本固定，花一次推理没有意义。应用名从**设备实际安装列表**匹配（含单复数归一、最长优先），不用硬编码别名表。且**不单独计一步**——开完 app 后在同一个 `agent.step()` 里继续对新界面推理，两者折叠成一个计数步，轨迹真实缩短一步。开完 app 后**等界面稳定再截屏**（轮询 layout signature，上限 2 秒）：固定 0.4 秒等待够列表出现、不够日历画完月视图，而这一步恰恰又是模型要做决策的那一步。
2. **确定屏幕上的权威边重放（v23 全量 16/17，94%）**：一个屏幕被访问过至少两次，模型在它上面**只选过一个动作**，且那个动作被执行过 **≥2 次**。这三条合起来就是重复型任务的循环后缀从图里看到的样子——`RecipeDeleteMultipleRecipes` 把 `(1025,197) → (652,602) → (860,1295)` 走了三遍，只有每轮起点的菜谱不同；`ExpenseDeleteMultiple2` 同样重复 `(967,1658) → (540,2221)`。一次执行只说明"这里这么做行得通"，两次才说明"这里的答案一直是它"。
3. **前瞻边**：探测在深度 2 探到的边，其父边经过**前缀对齐**（探索的猜测与模型真实落点一致）后晋升为 `REUSABLE`。这是唯一能**领先权威边**的来源，也是至今仍未跑通的一环——详见下面的实测。

**曾经的第 2 条来源已被删除**：早先只要屏幕重访过就允许重放模型上次的选择。按来源拆开统计（2026-08-31，28 次图跳过）后被否决——bootstrap 是 80/80，这一类是 3/17（18%），且每一个步数变差的离群任务都是它造成的（`MarkorCreateFolder` 5→19 步、`SaveCopyOfReceipt` 8→16、`ExpenseDeleteDuplicates2` 11→18）。屏幕看起来一样，不等于处境一样。

### 多步路径执行

跳过此前一次只走一步，省下的是推理调用而**不是步数**——AndroidWorld 按 `agent.step()` 计数，一步内做多少事都算一步。`reusable_path()` 从当前节点沿图取一串可复用边（最长 3 跳），**在同一个计数步内连续执行**，这是唯一真正缩短轨迹的机制。

每一跳执行后仍逐个验证落点，但校验的是 **`observed_destinations` 这个集合**，不是单一目的地：模型重复的动作本来就会落到不同屏幕（删掉第二个菜谱之后的列表 ≠ 删掉第一个之后的），按最近一次的目的地校验，会把这个机制最好的情形判成失配。若该转移只观察到过一个目的地，就按它严格校验；若观察到多个，则要求落到集合内、或至少离开了原节点。一旦不符，说明后续预测都基于一个已经不成立的状态，立即中断并交还模型。

### 安全阀

- **本 episode 的跳过命中率低于一半就停止跳过**，且在多跳路径内部逐跳检查。只在进入路径前查一次时，一条三跳路径可以在一个已经大面积出错的 episode 上跑完；而路径形式让每步的跳过数翻三倍，错跳累积也快三倍——`ExpenseAddSingle` 因此跳了 10 次错 4 次，`MarkorCreateFolder` 6 次错 4 次，都低于本应生效的 50% 门槛。
- **路径长度由命中率决定**：本 episode 的跳过必须已经全部命中（≥2 次）才允许多跳，否则一次只走一跳、逐跳验证。多跳是拿一次预测赌好几步，只有在这个 episode 已经证明跳过可靠时才值得。
- **前两步不探测**：开局图为空，探测连不上任何已知信息，而扰动恰好落在模型即将读取的界面上。`NotesIsTodo`（baseline 4 步）这类看一眼就能答的短任务都是被开局探测搞掉的。
- **只在重访过的界面上探测**（`node_visits ≥ 2`）。探索学到的东西，恰好在那个屏幕再次出现时才值钱；而实测显示**任何一次跳过所复用的边，`probe_count` 都是 0**——探索从未为跳过提供过任何一条边。在只经过一次的屏幕上探测是纯付出。
- **本 episode 一旦有一轮未能复原就停止探测**。按探索行为分桶（35 任务，2026-08-31）：完全不探测 89% 成功，探测且每轮都复原 89%，探测且有一轮未复原 **67%**。能复原的探索是免费的，不能复原的吃掉五分之一成功率。
- **屏幕上有已输入文本时不探测**。整个机制的前提是探测可逆，而回滚阶梯逆的是导航——Back 关掉一个页面，用户在上面输入的文字也跟着没了，阶梯里没有任何一级能把它打回来。
- **单 episode 探测总量上限 12**：`ExpenseAddSingle` 曾探测 30 次，其余丢分任务都在 1-7 次。
- **不跳回最近走过的节点**——但**对模型自己执行过 ≥2 次的转移豁免**。环里每一跳单独看都验证正确，所以下游无从察觉在绕圈：`CameraTakeVideo` 13 次跳过全部命中预测落点，仍然耗尽步数而毫无进展。那是投机边造成的。而"删掉一个菜谱、回到列表、再删下一个"本身就是任务在重复，不是我们在打转；这条守卫（在 `reusable_edge` 和 `ReasoningGate` 里各有一份）曾经恰好在机制终于积累够证据的那一刻把它拦下。豁免只给模型亲自重复过的转移。
- **每局最多跳过 2 次，且一错即停。** 合并五次全量跑测（2026-09-01）：图跳过触发过的 109 个 (版本, 任务) 组合里只有 6 个成功。其中很大一部分是任务本身难——跳过需要节点重访，重访多的是跑到步数上限的长任务，对照臂在这批任务上只有 28% 成功率（其余任务 59%），平均 16.1 步（其余 9.7 步）——但在同一批 40 个任务上对照仍拿到 11 个，而我们最好的一版是 10、最差 3。唯一还站得住的信号是**次数**：1–2 次跳过时 5/68，3–4 次时 1/32，5 次以上 0/9。而置信度方向是反的：**重放的边有 ≥3 次执行历史的 episode 全部失败（0/65）**，所以提高置信门只会更糟。剩下能做的就是限量加立即刹车。
- **两次执行之间图必须长出过新节点。** 重复一个动作，可能是任务在迭代（删掉一个菜谱、回到少一项的列表、再删下一个），也可能是 agent 卡住了在原地打转，从边上看完全一样。图能区分：迭代会发现新屏幕（少一项的列表就是另一块屏幕），打转不会。
- **不在系统设置类界面探测**（`com.android.settings` / `com.google.android.settings` / `com.android.systemui`）。拨动的开关不是导航，恢复阶梯的任何一级都还不回来；而读取这些开关状态的任务恰恰住在设置里，探测不只是有风险，是会破坏被检查的对象本身。
- **连续跳过不超过 3 次**，之后必须交还给模型。一串跳过意味着连续多个动作没有任何模型看过；单跳有落地验证，整个序列却没有，早期一次错误转向可以被沿用整局。
- 跳过执行后立即比对落地状态，不符则作废该边及其子树。

### 已测量并否决的方案

| 方案 | 结果 |
|---|---|
| 锚点校验（要求控件仍在原位） | 6/12，5 次跳过 0 命中 |
| 仅重放 chrome（排除列表行） | 5/12，2 次跳过 0 命中 |
| 证据注入（把探索发现写进 prompt） | 0/12（措辞像建议，诱导模型反复点同一控件） |
| 每步固定探测，不设门控 | 0/12，回滚失败 74 次 |

前两项都**削减了跳过次数却没提高准确率**，说明失配不是"控件移位"或"点到列表行"造成的。函数保留在代码中并标注为已停用，附测量结果，以免后来者重跑一遍。

## 模块一补充：图引导的探索（状态图信息矩阵）

此前候选排序只有 `InformationNeedRanker` 一路信号——它只回答"这个控件的文字像不像任务要找的东西"，那是**当前屏幕唯一能回答的问题**。图知道另外三件事，而且是花了真实步数学来的：探这个控件的历史猜测有没有对过、它回不回得来、它要花多久。

`android_world/parallel_exploration/state_graph_information.py`：

```
当前 UI → 候选抽取 → 安全/可恢复性硬过滤 → 构建信息矩阵 → 预测式打分 → 选择探测目标
```

**`CandidateInformationRow`**（每个候选一行，八组特征）：

| 组 | 内容 |
|---|---|
| A1.1 当前 UI | identity、text、content_desc、role、probe_type、归一化位置、可点/可滚/选中态 |
| A1.2 节点成熟度 | visit_count、decision_entropy、出边数、有效出边数、已探元素数、**探索覆盖率**、图世代 |
| A1.3 精确边历史 | probe_count、status、对齐次数/命中次数/失效次数、跳过成功率、平均实现 IG、回滚成功率、已知逆动作级别、目的地 |
| A1.4 目的地结构 | 访问次数、熵、出度、子树规模、已知标签数、是否在最近路径上 |
| A1.5 上下文历史 | 按 `(probe_type, role, need_type)` 聚合的统计，**不按控件文字聚合** |
| A1.6 信息需求 | target/affordance/slot 各自独立保留，不提前塌缩成单一相似度 |
| A1.7 安全 | 拉黑元素、拉黑恢复上下文、跨包历史、风险级别、**估计可恢复性** |
| A1.8 代价 | 期望探测延迟、期望回滚延迟、期望总代价 |

两条不可让步的性质：

1. **未知不是零。** 没探过的候选，历史统计一律为 `None` 而不是 `0.0`。把"对齐率 0%"存给一个从没试过的候选，会让它排在一个已被实测证明无用的候选之后——正好反了：没试过的才是唯一还能学到东西的。
2. **安全是硬门不是罚分。** `SafetyGate` 在打分**之前**剔除候选。分数是相对的——当所有候选都很差时，最不差的那个仍会被探测，这对"有用性"是对的，对安全是错的：一次无法撤销的探测代价不是选了个次优，而是整个 episode 走不下去了。

**`PredictiveElementScorer`**：

```
predictive_value(e) = path_probability(e) × expected_IG(e)
utility(e)          = predictive_value(e) / expected_cost(e)
        s.t. recoverability(e) ≥ 阈值，且动作安全
```

- `path_probability` 优先取**对齐历史**（探测的猜测后来与模型真实选择一致的次数），因为那是唯一直接测量"被预测的那件事"的信号；无历史时退回 need 匹配先验，并按 Beta-Binomial 向先验收缩（两次两中不等于确定）。
- `expected_IG` **不再等于 `new_element_count/10`**。那个量只保留为 `ui_novelty_score`：满屏陌生标签不等于回答了模型卡住的问题。主项是任务相关性；**目的地已知的转移被重罚**（0.25×），这正是"节点覆盖率高时把探索推向未试候选"的来源。
- `expected_cost` 按探测类型分别估计，回滚失败按 12 秒定价——让代价项本身（而不只是硬门）偏好可靠可逆的候选。

先验数字全部来自实测（2026-08-31，452 次探测：TAP_NAV 回滚成功 93%、SCROLL 90%、TAP_MENU 84%、EXPAND 77%）。打分器不训练、可解释、每一项分量单独落盘，接口保留给以后的 `SmallModelPredictiveEstimator` 替换。

深度 2 仍走原排序器：子界面是刚刚第一次到达的，图里没有节点、没有任何矩阵要读的历史，走打分器只会用同一个先验跑一条更贵的代码路径。

## 模块三补充：图蒸馏与三路推理门

跳过推理要求接近确定，因此很少触发；在此之前，其余每一步里探索学到的东西**被整个丢掉**。三路门是补上这条路径。

### 三路门（`ReasoningGate`）

```
NORMAL_INFERENCE          图里没有可用事实 → 不污染 prompt
GRAPH_ENHANCED_INFERENCE  有用但不足以确定 → 注入紧凑事实 + 正常推理
SKIP_INFERENCE            高度确定 → 直接重放，立即验证落点
```

三者读同一套信念统计，**同一个 step *i-1* 快照**，世代守卫不变。跳过被否决时给出理由（最近成环 / 节点熵过高 / 连续跳过到顶 / 边有风险），此时仍走增强推理，而不是退回一次普通推理——这正是"不确定"也能拿到探索收益的地方。

### 图蒸馏器（`graph_distiller.py`）

确定性流水线 `retrieve → filter → score → compress → template`，**不调用任何额外 LLM/VLM**（一次总结调用的代价约等于它想省下的那次推理）。只看当前节点的出边（1 跳），因为再远的东西模型这一步也用不上。

先把图结构转成 `GraphFact`（`VERIFIED` / `OBSERVED` / `DONE` / `NO_RELEVANT_EVIDENCE`），再按

```
U(fact) = NeedMatch × Certainty × HistoricalUtility × Freshness
```

贪心选前 K 条，`max_graph_facts=3`、`max_graph_context_tokens=64`。确定性内部值转成语言（Verified / Observed / Tentative），**不向模型暴露 `confidence=0.63` 这类原始数字**。

输出格式固定：

```
[Memory]
Need: ...
Verified: ...
Observed: ...
Done: ...
```

四条实测约束：

1. **陈述而非建议。** 早先版本写 "Tapping X opens Y"，读起来是推荐，模型照做、反复点已经用过的控件（`MarkorCreateFolder` 在 "+" 和文件名框之间循环十步）。全部改成观察句，并把"已经做过什么"明说出来。
2. **没有正面事实就完全不注入。** 2026-08-31 的 12 任务实测：20 次注入**没有一条**带正面事实，全部是 `Need:` 复述模型自己的话加一句"没观察到证据"，该臂丢了 4 个任务。否定事实和 `DONE` 事实是正面发现的配角，永远不构成开口的理由。
3. **坐标不能当名字。** "the control at (540,605) already used" 模型无法在截图里按坐标找到那个控件，这句话不可执行却照样占预算。任何只能用坐标称呼的控件一律不进 prompt。
4. **不做覆盖度不支持的否定断言。** 说的是"在 Reviews 下未观察到相关证据"，不是"Reviews 里没有电话号码"；并且只有真正探测过（`probe_count ≥ 1`）的边才有资格说这句，每次最多一条。

`Need:` 行去重并按名词短语形状过滤：`parse_reasoning_prior` 故意过量产出（目标实体、同一实体再作为槽位、以及它的每个单词），照抄会得到 `Need: Zucchini Noodles with Pesto, Zucchini Noodles with Pesto, Zucchini, Noodles, Pesto.`——20 个 token 用来复述模型看得见的目标。同时滤掉从 `<THINK>` 里挖出来的半句话（"s detail page. I will click on the"、"Therefore"）。

### 统一的图统计（PART C）

`GraphEdge` 上新增累计量：`probe_count`、`skip_attempt_count/skip_success_count`、`rollback_success_count/rollback_failure_count`、`cumulative_realized_ig`、`cumulative_exploration_cost`、`last_updated_generation`，并通过 `record_probe / record_inference_alignment / record_execution_verification / record_skip_result / record_rollback_result` 统一写入，不再散落在 runner 各处。

单值字段记录最近一次观察，累计量记录历史——"回滚成功过一次、失败过两次"和"回滚成功过一次"是完全不同的处境，而两者的 `rollback_success` 都是 `True`。

`record_skip_result` 与 `record_execution_verification` 刻意分开：前者问"信图而不信模型这次划算吗"，后者问"这条转移的动力学还成立吗"。一条边可以如实描述 UI，同时在任务的这个位置是错误的选择。

## 当前基准与进展（全量 AndroidWorld 116，v23，2026-09-02）

### 基准的选择与步数上限

**不能用 `results/4B_2.txt` 单独做成功率基准。** 它跑在另一个环境上，而这套 agent 的单次跑测方差本身就很大：`4B_2`（54/116）与同期另一个纯 baseline `base116_cap15`（57/116）**交集只有 45**，各自独有 12 和 9——两个都不含本设计机制的跑测彼此翻转了 21 个任务。所以每次对比都带一条**同 session、同 runner、机制全关**的对照臂。

**步数上限统一为 15 步。** 依据：289 次成功里 98.3% 发生在 15 步以内，只有 5 次是第 16 步之后才成功的。对照臂与 4B_2 的历史记录按 15 步**事后截断**——上限只决定何时停止、不改变前 15 步的轨迹，所以截断等价于用 15 步上限重跑，两边公平。

### 结果

| 对比 | 共同任务 | 本设计 | 对方 | 差 | 配对步数 | 逐任务 |
|---|---|---|---|---|---|---|
| vs 同环境对照 | 114 | 45 | 53 | **−8** | **6.00 vs 7.08（−1.08）** | **29 快 / 3 慢 / 6 平** |
| vs `4B_2` | 114 | 45 | 46 | **−1** | 5.74 vs 6.29（−0.56） | 22 快 / 7 慢 / 5 平 |

成功任务平均步数 **6.00** vs 对照 7.08；全体平均步数 9.75 vs 10.09。

### 机制表现

| 机制 | v24 全量 |
|---|---|
| bootstrap 折叠 | **96 / 96（100%）** |
| **图跳过** | **15 / 15（100%）** |
| 图注入 | 13 次 |
| 探测 | 65 次，6 轮未复原（9.2%） |
| 跨任务播种 | 356 条边 |

三个模块同时工作且零系统性失误。

### 结论的边界

- **步数：成立。** 配对比较对三个基准全部占优，对老 baseline 是 −1.32 步、33 快对 3 慢。
- **机制本身：成立。** 图跳过从 v12 的 3/17（18%）做到 16/17（94%），注入从全量 0 次做到 17 次。
- **成功率：未达标，且不能用"归属干净"开脱。** 掉分归属是机制触发无失误 7 个、无机制活动 6 个、探测未复原 1 个——只有 1 个可归咎于机制过错。但 −8 与之前几轮方向一致，不能仅凭归属就判定为无害。

**跑测过程中的变化值得记录**：这一轮在 37 个任务时是 +2、65 个任务时持平（28 vs 28），差距出现在后半段（SMS 与 System 两批）。其中 SMS 系列已确认是设备侧问题——`adb` 直接拉起短信应用就会跳 `RequestRoleActivity`，**对照配置（机制全关）同样跑不通**。

### 噪声地板（对论文重要）

**同一份代码跑两次：42 成 vs 49 成，9 个任务翻转。** 单次跑测分辨不出 ±7 以内的效应，而这里要测的效应就是这个量级。任何单次 AndroidWorld 结果都不足以支撑成功率结论；要下结论必须两臂各重复多次取平均。

探索轮确实开启了，但 `probes_completed` 全为 0——`_unprobeable()` 正确拦住了设置界面，每轮只花约 120 ms 且**没有触碰设备**。跳过与注入在这 7 个任务里也是零。也就是说 v24 与 `boot_only` 在这些任务上的唯一差异是 `_decision_constraints` 这段 prompt。

其第一条约束是"除非当前屏幕**可见地证明**了最终状态，否则不要选 COMPLETE"。Wi-Fi 开关、蓝牙开关、亮度滑块恰恰是最终状态在截图里读不出来的界面：模型不敢收尾，把 15 步全部耗尽。同一签名此前已在拍照/录像任务上测到（`CameraTakePhoto` 4 步 → 13 步）。

这段 prompt 是从 `explorer_agent_gelab_light` 移植的，移植理由是"Light_design 的领先来自 prompt 而非探索"。移植本身没错，错在**它和三个机制被绑在同一个配置里测**，于是机制背了 prompt 的锅。

### v29 暴露的两个真缺陷（已定位，待验证修复）

1. **目的地事实被固定 chrome 占满。** 真实执行路径把 `after.elements` 的全部文本写进 `discovered_labels`，没有减去源屏幕已有的元素。`MarkorCreateFolder` 因此被注入三次 `Verified: FOLDER -> {Markor, Go to, Sort by, Search}`——Markor 自己的工具栏，点击前后都在——任务从 5 步变 15 步。探测路径一直用的是 `new_texts`（已做差集），执行路径漏了。修法：目的地只保留相对源**新增**的标签，无新增则不产生事实（信息增益为 0）。
2. **探测弄脏同 app 内的屏幕后无人收拾。** `repair_after_exploration` 在包名未变时直接返回，因为"任何未复原就重启"曾把步数从 7.2 推到 10.4。但探测打开菜单/弹窗又关不掉时，下一步推理读的就是那个浮层（`RetroPlayingQueue` step 7 `RESTORE_FAILED` 后再没恢复）。修法：仅当 `RESTORE_FAILED` **且**当前节点确实不同于探测前时，按一次返回；单次有界，不做阶梯。

全局频率：脏探索 4/65 轮（6%），重复跳过同一动作 1 个任务。两者都在噪声地板以内，需重复跑测才能确认收益。

## v33（2026-09-02 晚）：候选集覆盖率假设被证伪

### 出发点

v32 的 1842 次候选过滤中，**48.1% 是"这个界面上这类探测已不可恢复"**，远超图标无标签的 20.4%：

| 占比 | 过滤原因 | 主要控件类型 |
|---|---|---|
| 36.8% | TAP_NAV already unrecoverable here | — |
| 20.4% | icon_only_no_accessible_label | ImageView×126, LinearLayout×94 |
| 16.3% | no_semantic_identifier | LinearLayout×122, CardView×105 |
| 11.8% | action_button_requires_semantic_inverse | Button×217 |
| 11.3% | SCROLL already unrecoverable here | — |

黑名单键是 `(activity, probe_type)`，且经应用记忆**跨任务传播**。在 103 条探测记录里只有 24 次封禁事件，却造成约 886 次候选拒绝。

其中 6 次（25%）来自**回滚其实成功、只是走了深层梯级**的探测。这条分支自相矛盾：同一条探测在几行之前刚被记为 `observe_rollback(ok=True, level=...)`，这里又被记为 `ok=False`——而 `known_inverse_levels` 本就会让下次探测直接从管用的那一级起步。深层回滚是**更贵**，不是**不可能**。

v33 = v32 + `--no_deep_rollback_blocks`（新增消融开关，默认保持原行为）。

### 结果：探测量翻倍，命中率纹丝不动

| | 实际探测 | 真实动作在候选集中 | 命中率 | 前缀对齐 | 成功 | 成功任务均步 |
|---|---|---|---|---|---|---|
| v29 | 38 | 7/56 | 10.9% | **0** | 58 | 6.36 |
| v32 | 65 | 3/52 | 6.8% | **0** | 57 | 6.26 |
| **v33** | **80** | 5/64 | **11.5%** | **0** | 55 | **6.13** |

探测量 38 → 80（+110%），命中率始终在 11% 上下。**被安全过滤挡掉的候选不是模型会点的那些**，所以放宽过滤增加的是成本，不是信息。

副作用如预期：探测更多 → 回滚失败更多 → 新封禁更多，`不可恢复类` 占比只从 48.1% 降到 47.7%（深层但成功只占封禁事件的 25%，其余 75% 照旧）。

逐任务归因：5 个掉的任务里只有 `RetroCreatePlaylist` 可归因于放开的探测（探测 3 次、脏 1 次），其余 4 个与 3 个新赢的任务**探测数全为 0**，是噪声。

### 更根本的一层

`steps_with_candidates: 80 / inference_calls: 1034` —— 探索总共只在 **7.7% 的步骤**上产生过候选。即使命中率提到 100%，可影响的步骤上限也只有 7.7%。

### 与前两轮合并的结论

推测式前瞻这条线现在已被**三种独立方式证伪**：
1. 前瞻深度与预算（此前三轮）——探索花掉的成功率大于它省下的 <2% 推理；
2. prompt 侧（v31）——验证类约束在 15 步上限下净亏；
3. 候选集覆盖率（v33）——放宽安全过滤不提高命中率。

系统的价值集中在 **bootstrap 折叠**：97/97 任务零失误，配对比较对 Light_design 是 32 快 5 慢（−0.77 步）、对同环境对照 33 快 7 慢（−1.09 步）。这是可复现、可解释、可迁移到真机的部分。

**发布配置仍为 v29/v32**（源码默认值即是；两个新开关均为 `store_false`，不改变默认行为）。

## v34（2026-09-02 深夜）：把"重访"改成跨任务，机制被激活但成功率净亏

### 出发点：7.7% 的步骤覆盖率是怎么来的

对 v33/v32 的全部 1041 步做门控归因：

| 占比 | 被哪条门控挡住 |
|---|---|
| **62.9%** | **`node_visits >= 2`——屏幕在本集内首次到访** |
| 21.7% | `step >= 2`——开局前两步 |
| 2.8% | `unrecovered_once`——一次回滚失败关停整集（涉及 5/116 任务） |

主因是"只探重访屏幕"。这条当初有强证据（"每一条被跳过重放的边 probe_count 都是 0，探测单次经过的屏幕不付钱却承担全部回滚风险"），但那是**记忆还是单集局部**时测的。

跨任务记忆已经存在，于是重新量了屏幕复用度：**478 个屏幕节点中 40.6% 出现在不止一个任务里**，应用复用更强（日历 17 个任务、Markor 15、设置 12、Broccoli 11）。一个屏幕在本集是首次到访，但有四成概率在别的任务里再遇到——这个价值单集视角看不见。

v34 = v32 + `--cross_task_revisit`：把"重访"判定改为查开局快照的跨任务屏幕签名集合。**只用于探索门控**；跳过门控继续读单集访问计数与执行计数，跨任务知识依然不能授权无模型重放。

### 结果：机制激活了，成功率没有

93 个共同任务上：

| | 探索轮 | 步骤覆盖率 | 实际探测 | 未复原 | 真实跳过 |
|---|---|---|---|---|---|
| v29 | 70 | 7.8% | 34 | 5 | 5 |
| v32 | 75 | 8.6% | 59 | 4 | 4 |
| **v34** | **142** | **16.2%** | **111** | 7 | **21** |

覆盖率翻倍、探测近两倍、**真实跳过 5 倍**——这是所有版本里机制最活跃的一次。跳过动作匹配 18/21（86%）。

但成功率：90 个任务时 v34 38，v29/v32 各 43（**−5**）。逐任务归因：**6 个掉的任务可归因于新开的探测**（`MarkorCreateFolder` 8 步成功 → 14 步失败、`MarkorCreateNote`、`RetroCreatePlaylist`、`FilesMoveFile`、`ExpenseDeleteMultiple2`、`SimpleSmsReply`），2 个是零探测噪声；赢的 6 个里只有 3 个有探测。

### 四次独立证伪，同一个结论

| 轮次 | 假设 | 结果 |
|---|---|---|
| 此前三轮 | 加大前瞻深度/预算 | 探索花掉的成功率 > 省下的 <2% 推理 |

## v35–v39（2026-09-02/03）：探索为什么朴素，以及一次环境事故

### 诊断：模型真正点的元素去了哪里

把模型第 i+1 步实际点击的坐标，比对第 i 步探索时的候选池（76 例配对）：

| 占比 | 归属 |
|---|---|
| 27.6% | 真候选（小控件 <5% 屏） |
| 7.9% | 真候选（中等 5–20%） |
| 23.7% | 仅大容器命中（容器包住子元素，算不得命中） |
| 27.6% | 被安全过滤掉 |
| 13.2% | 从未进入候选池 |

命中元素**恰好被选去探测的只占 37.8%**——目标常在池子里却没被选中。于是查打分，2712 条候选中：

| 特征 | 非零占比 |
|---|---|
| `target_match` | 0.5% |
| `expected_affordance_match` | 2.1% |
| `unresolved_information_match` | 5.3% |
| `ui_novelty_score` | 0.0%（完全失效） |
| `candidate_action_type_match` | 100%（恒为 1，零区分度） |

**所有语义信号都是死的**，排序完全由通用结构先验驱动。这就是"朴素"的准确含义。

### 三个根因，逐个修复

**① 匹配公式把信号稀释掉。** `_overlap = |a∩b|/|a|`，`a` 是所有 slot 合并的词袋，模型说得越多分越低。Markor 案例里模型 `<THINK>` 点名的 "Plain Text" 只得 0.15。改为**逐项匹配 + 按较短一侧归一**（`_best_item_overlap`），该控件得 1.00，无关控件保持 0；加 `_GENERIC_MATCH_WORDS` 护栏，避免仅靠 "by"/"new" 这类虚词命中。开关 `use_per_item_need_match`。

**② 推理先验滞后两步。** `current_need` 来自第 i-1 步输出，而探索预测第 i+1 步。探索在推理之后运行，第 i 步输出那时已可用——通过 `INFERENCE_START` 事件把新鲜需求送进探索进程。开关 `--no_fresh_reasoning_prior`。

**③ 语义匹配把探测拉向"刚点过的控件"。** 最隐蔽的一个：模型的推理描述的是它**当下正在点**的控件，所以加强语义匹配反而把已点控件推到前面。v35、v36 两轮独立验证：平均排名从 3.2 恶化到 12.5。修法是排除刚按下的控件（其目的地已被权威执行记录，探它零信息增益）。开关 `--no_skip_just_taken_control`。

### 一次环境事故，以及它污染了什么

v37/v38 的六个 `SimpleSms*` 任务全部失败，模式一致（13 步、2 次跳过、动作匹配 100%）。我一度归因于"跳过破坏了历史语义"，并据此把跳过写入历史的 summary 从 `str(action_dict)` 改成自然语言——**改完行为一字未变，假设被证伪**。

真因在轨迹里：

| | SimpleSmsSend 访问过的界面 |
|---|---|
| v32 | ThreadActivity / NewConversationActivity / MainActivity（正常） |
| v37/v38 | 只有 Launcher 与 `RequestRoleActivity`（**从未进入应用**） |

Android 的 `android.app.role.SMS` 持有者漂移到了 `com.google.android.apps.messaging`，而 legacy 的 `sms_default_application` 仍写着 smsmessenger，两者不一致就会在每次启动时弹角色请求。模型从 step 0 起就陷在 `点击 → 被踢出 → 重开应用` 的循环里，**循环形成于第一次跳过之前**。

## 前瞻通道的实测现状（v43/v45/v47/v48，日志在 `~/mobileexplorer_runs_backup`）

深度 2 恢复之后，前瞻通道的每一环都能测。四次跑测合计：

| 环节 | v43 | v45 | v47 | v48 | 合计 |
|---|---:|---:|---:|---:|---:|
| 探索轮 | 186 | 194 | 178 | 152 | 710 |
| 完成的探测 | 132 | 100 | 115 | 96 | 443 |
| **触达深度 2 的轮次** | 51 | 36 | 42 | 23 | **152** |
| 待检验的前缀候选 | 117 | 115 | 144 | 147 | 523 |
| 前缀**对齐**成功 | 2 | 1 | 7 | 13 | **23（4.4%）** |
| 排序器**猜中模型动作** | 2 | 0 | 0 | 1 | **3（0.6%）** |
| **晋升为 `REUSABLE`** | 1 | 0 | 0 | 1 | **2** |

三条结论，都是这张表直接读出来的：

**1. 深度 2 通了，前瞻没通。** 152 轮探索真的到了深度 2，但整条链路只产出 **2 条 `REUSABLE` 边**。也就是说「领先权威路径」这条设计上唯一能省下模型没答过的那一步的通道，实际贡献接近零；目前所有的步数收益都来自 bootstrap 折叠和确定屏幕上的权威边重放。

**2. 对齐（23）远多于猜中（3）——而这不是好消息。** `prefix_check` 把两件事分开记，正是为了区分这个：`action_was_guessed` 问「排序器有没有提出模型后来真正采取的那个动作」，`aligned` 问「探测的落点是否等于模型这一步的落点」。23 次对齐里只有 3 次是真的猜中了动作，其余 20 次是**不同的动作恰好落到同一个节点**。节点身份是宽松的（只看可交互骨架），所以「点了别的东西也回到这块屏幕」会被记成对齐。这是一种比设计意图弱得多的证据，而 `promote_children_of_aligned_prefix` 会照单全收。

**3. 瓶颈是排序器，不是探测预算。** 0.6% 的动作猜中率意味着加大 `--probes_per_step` 或 `--probe_budget` 改善不了这条链路——之前已经用「探测量翻倍、命中率纹丝不动」独立证伪过一次。要动的是 `path_probability` 那一项，或者干脆承认前瞻通道不成立、把设计叙事收敛到已经跑通的两条来源上。

**这也解释了为什么把深度 2 砍掉时成功率没有变差**：它本来就没在产出。恢复它的理由是通道完整性和可测量性，不是当前收益。

### 附带修掉的一个比较器缺陷（2026-09-09）

原 `action_was_guessed` 用 120px 几何邻域判"是否同一控件"，对 `input_text`/`swipe` 这类无坐标动作**结构性失明**——它们占候选的 22.1%，也就是上面 44% 的对齐它一次都验证不了。新的 `aligned_by_action` 走 `_canonical_control`，对 swipe 回退到 `direction`、对输入回退到 `text`，覆盖面严格更大。

同一天还修了它的对称缺陷：模型动作只有坐标、没有 `control_key`，而 `_canonical_control` 优先读 `control_key`，于是**每个 click 都在拿真实键和 `""` 比较，`aligned_by_action` 恒为 false**。修法是把权威边早就在用的 `_control_key_at(before, action)` 补到模型这一侧（`run_serial_exploration_task.py:2135`），两侧用同一函数、同一块 pre-action 屏幕解析，键直接可比。`serial_generation_test.py` 加了四个回归测试锁住这个失效模式，并把"解析不出控件"与"控件不匹配"分开记录（`model_key_resolved`、`aligned_action_unresolved`）——把测量缺口报成发现，这次已经踩过一回。

## Stage 1b：前瞻通道的判定实验（2026-09-09，两臂各 116 任务）

假设：`prefix_check` 记录的"节点对齐"大多不是排序器猜中了模型的动作，只是**另一个动作恰好落到同一块屏幕**；如果是这样，`promote_children_of_aligned_prefix` 一直在用一种远弱于设计意图的证据晋升边。

两臂同一台模拟器、同一次开机、背靠背，唯一差异是 `--align_requires_action_match`（只放行控件键也相同的对齐；解析不出控件键的一并拒绝）。参数记在各臂的 `ARGS.txt` 里——此前 11 次全量跑测**没有一次记录过自己的运行参数**，"哪一次是零探测"这类问题事后无法回答，这个缺口在这里补上。

|---|---:|---:|---:|---:|---:|
| **s1a（宽松）** | 115 | 49 | 42.6% | 8.90 | **5.61** |
| **s1b（严格）** | 113 | 53 | 46.9% | 8.79 | 5.75 |

| v43 | 113 | 54 | 47.8% | 8.40 | 5.54 |

### 门的三个答案

**1. 假设成立。** s1a 的 172 个候选里只有 1 次节点对齐，规范化之后确认是**相反手势**造成的假对齐（探测 `scroll forward`，模型 `swipe down` = `scroll back`）。真动作匹配 **0/1**。

按模型真实动作类型拆开，s1a：

| 动作 | 候选 | 对齐 |
|---|---:|---:|
| `click` | **132** | **0** |
| `input_text` | 22 | 0 |
| `long_press` | 8 | 0 |
| `swipe` | 5 | 1（假） |
| `open_app` / `wait` | 5 | 0 |

**132 条 click 候选一次都没对上**，而本轮探测量（125 次）高于全部六个历史参照（47–75）。给足探测机会，主路依然是零。s1b 的 140 个候选里节点对齐 **0**。

**2. 晋升 0 条，两臂都是。** 加上历史：十一次全量跑测总共产生过 **2 条** `REUSABLE` 边（v43 与 v48 的 `SimpleCalendarAddOneEventInTwoWeeks`），追查两个 episode 的后续跳过，**两条都从未被执行**。

> 前瞻通道在十一次全量跑测里兑现的收益是 **0 步**，不是"接近零"。不是效果小，是通道末端没有出口。

**3. 门没有通过，落在第二行（前瞻通道不成立）。** 门的第一行「promotions 上升」按构造无法达成：s1b 是 s1a 的严格子集，严格臂的晋升不可能高于宽松臂，而宽松臂是 0。

### 副产品：同配置重复跑测的噪声基线

两臂的 flag **一次都没有生效过**——s1b 的节点对齐是 0，没有任何对齐可供它拦截；两臂晋升都是 0。所以 s1a 与 s1b 在机制上是**同一个配置**，它们的差异就是纯复现噪声：

```
同任务 n=113    s1a 48    s1b 53    净差 +5
翻转 11 个（s1a 胜 3 / s1b 胜 8），翻转率 9.7%
```

这是本项目第一次拿到**同构建、同环境、背靠背**的复现噪声，此前的"±7、9 个任务翻转"是跨版本估的。翻转集中在少数边界任务上，不是弥散的。

### 据此撤回一个怀疑

跑测过程中观察到 s1a 对六个历史参照**全负**（−2 到 −9，均值 −6.7），一度怀疑当前工作树相对 v45/v48 有真实回归。**这个怀疑不成立**：

- 同配置两臂本身就相差 5（48 vs 53），参照两两之间最大相差 8
- s1b 对同样六个参照是 −5 到 +3，均值 **−2.0**，落在区间内

s1a 只是落在自己复现分布的低端。**用单臂对历史跑测做减法，在这个噪声水平上得不出结论**——这也是"每个结论都要同臂对照"的直接理由。

（`ContactsNewContactDraft` 两臂都因 AndroidWorld 自身 `contacts.py:211` 的 `is_successful` 崩溃而无结果；s1b 另有 `RetroSavePlaylist`（adb 超时）与 `SaveCopyOfReceiptTaskEval`（fast a11y socket 读取失败）两次环境异常，故 N=113。）

### 同期修掉的三个比较器缺陷

三个都是同一类错误——**两侧用不同方案记录同一件事**，而每一个都让某个统计量恒为零，读起来像发现：

1. **模型动作没有 `control_key`**，而 `_canonical_control` 优先读它，于是每个 click 都在拿真实键和 `""` 比较，`aligned_by_action` 恒为 false。修法：把权威边早就在用的 `_control_key_at(before, action)` 补到模型侧（`run_serial_exploration_task.py:2135`），两侧同函数、同一块 pre-action 屏幕。
2. **`action_was_guessed` 用 120px 几何邻域判同控件**，对 `input_text`/`swipe` 这类无坐标动作结构性失明——它们占候选 22.1%，而历史上 44% 的对齐正是 swipe。
3. **`scroll` 与 `swipe` 在 AndroidWorld 里互为逆动作**（`actuation.py:172` 注释自陈）：`scroll down` 手指向上露出下方内容，`swipe down` 手指向下露出上方内容；探测的 SCROLL 拖 75%→25%，是 `scroll down`。按原始 `direction` 字符串比较会把**一对相反手势判成匹配**。修法是按内容方向归一（`_canonical_scroll`）。

`serial_generation_test.py` 为这三类各加了回归测试（共 9 个），并把"解析不出控件"与"控件不匹配"分开记录（`model_key_resolved`、`aligned_action_unresolved`）——把测量缺口报成发现，本轮已经踩过一次。

## 设计修订（2026-09-09，基于 Stage 1b 与 8 次跑测的归因）

这一节取代此前"三条来源共同贡献步数收益"的叙事。改动的依据全部是可复核的磁盘数据，逐条给出。

### 一、省下的推理来自哪里：94–97% 是 bootstrap 折叠

按事件逐次统计（`skip` 事件区分 `kind_detail=app_bootstrap`）：

| 跑测 | 推理步 | bootstrap 折叠 | 图跳过 | 蒸馏注入 | 省下的推理 | 占比 |
|---|---:|---:|---:|---:|---:|---:|
| s1a | 1034 | **97**（命中 97） | 5（命中 4） | 9 | 102 | 9.0% |
| s1b | 1004 | **95**（命中 95） | 4（命中 2） | 12 | 99 | 9.0% |
| v48 | 988 | **96**（命中 96） | 3（命中 3） | 13 | 99 | 9.1% |
| v45 | 1017 | **96**（命中 96） | 7（命中 5） | 5 | 103 | 9.2% |

**bootstrap 折叠占省下推理的 94–97%，命中率 384/384 = 100%。** 它是"任务目标点名了哪个 app 就直接 `open_app`"的表查找，不经过信念图。信念图的跳过贡献 3–7 次，即总步数的 **0.3–0.7%**。

### 二、探测对两个省步机制都没有贡献

追查 8 次跑测（v43/v45/v47/v48/v49/vrand/s1a/s1b）**每一次**图跳过所用的边，按 `probe_count` 与 `action.probe_type` 判来源：

```
模型自己走出来的边   48
探测发现的边          0
```

（注意 `probe_type: "EXECUTED"` 是"模型执行过"的标记，不是探测类型；真正的探测边是 `SCROLL` / `TAP_NAV`。全部 48 条被跳过的边 `probe_count` 均为 0。）

加上 Stage 1b 的结论——前瞻通道 11 次跑测兑现 **0 步**（2 条 `REUSABLE` 边，两条都从未被执行）——可以合并成一句：

> **探测（exploration probing）对目前唯一两个能省步的机制都没有贡献。** bootstrap 折叠是表查找；权威边重放 48/48 来自模型自己重复走过的转移。探测唯一的下游消费者是前瞻通道，而它产出为零。

### 三、步数收益的配对重算：从 −1.7 收缩到 −0.1 ~ −1.1

此前"成功任务均步全面低于 baseline"是在**各自的成功集**上算的。两个配置成功的任务不是同一批，简单相减把"我们只在更容易的任务上成功"也算成了步数优势。只在**双方都成功**的任务上重算：

| 对比 | 朴素（各自成功集） | 配对（双方都成功） |
|---|---:|---:|
| s1a vs Light_design | −1.68 | **−1.07**（n=44） |
| s1a vs 4B_2 | −0.79 | −0.92（n=37） |
| s1b vs Light_design | −1.54 | **−0.32**（n=44） |
| s1b vs 4B_2 | −0.65 | **−0.10**（n=40） |

s1a 与 s1b 是**同一个配置**（`--align_requires_action_match` 在两臂都一次没生效过），所以 −1.07 与 −0.32 之间的差距是复现噪声。**对 Light_design 的最佳估计约 −0.7 ± 0.4 步，对 4B_2 约 −0.5 ± 0.4 步。**

### 四、baseline 表的截断口径必须统一

`4B_2` 此前记的 54/116 @ 7.85 是**未截断**数字；同一份 `results/4B_2.txt` 按 15 步截断后是 **47/116 @ 6.40**。用我们的截断数字去比它的未截断数字，同时虚增步数优势、虚减成功率优势。`Light_design` 不受影响（没有成功任务超过 15 步）。

统一按 cap=15：

| 配置 | N | 成功 | 成功均步 | 全体均步 |
|---|---:|---:|---:|---:|
| Light_design | 116 | **58** | 7.29 | 9.47 |
| s1b | 113 | 53 | 5.75 | 8.79 |
| s1a | 115 | 49 | 5.61 | 8.90 |
| 4B_2 | 116 | 47 | 6.40 | 10.67 |

**成功率上我们落在两个 baseline 之间，不高于 Light_design。**

### 五、据此的设计修订

**退役前瞻通道。** `promote_children_of_aligned_prefix`、`prefix_check` 的晋升分支、以及为它服务的深度 2 下降，是探测的唯一下游消费者，11 次跑测兑现 0 步，同时引入了一条"用弱证据（节点身份宽松匹配）晋升边"的假证据路径——Stage 1b 实测 1/1 的节点对齐是假的。保留它的唯一理由曾是"通道完整性与可测量性"，现在测完了。

**改为按证据保留的部分：**

| 组件 | 处置 | 依据 |
|---|---|---|
| bootstrap 折叠 | **保留，且是主力** | 384/384 命中，占省下推理 94–97% |
| 确定屏幕上的权威边重放 | 保留 | 48/48 图跳过来自它；但只占总步数 0.3–0.7% |
| app memory（跨任务屏幕知识） | 保留 | 33% 屏幕跨任务复现，平均 4.0 个任务访问 |
| 蒸馏上下文注入 | **保留但未验证** | 5–13 次/跑测，省 0 步；对决策质量的影响从未单独测过 |
| 前缀对齐 → 晋升 → `REUSABLE` | **退役** | 0 步收益，且是唯一的假证据来源 |
| 深度 2 下降 | **退役** | 唯一用途是给前瞻通道供料 |
| 安全门（`SafetyGate`） | 保留原样 | 放宽已被 v33 证伪；空轮只花 128 ms 且不碰设备 |

**探测本身的处置留待验证再定。** 它不给两个省步机制供料，但仍在给 app memory 和图结构供料，而后两者的价值尚未单独测量。直接删掉会同时删掉一个未测量的东西——这正是本轮反复踩到的错误模式。正确顺序是先测再删。

### 六、修订后仍未回答的两个问题

**1. 蒸馏注入有没有用？** 这是现在唯一还可能解释"成功任务步数低于 baseline"的机制（bootstrap 折叠只省 1 步/任务，图跳过 0.05 步/任务，加起来解释不了配对后的 −0.7）。需要 `--graph_context distill` vs `off` 的同臂对照，其余完全一致。这是**下一个该做的实验**，不需要新代码。

**2. 96% 空闲的并行窗口该用来做什么？** 实测每步有约 3.3 秒免费并行预算，探测中位只用 0.14 秒（利用率 4%），而加大探测预算填不满它（v33：探测量 +110%，命中率不动）。目前没有证据支持任何具体用法——**不要在没有假设的情况下往这个窗口里塞东西**，本轮已经证明"更多探索"不是答案。

### 七、方法论：本轮确立的两条规矩

**每个结论都要同臂对照。** s1a 对六个历史参照全负（−2 到 −9，均值 −6.7），一度读作"当前构建有回归"；而同配置的 s1b 对同样六个参照是 −5 到 +3（均值 −2.0）。**同配置两臂自己就差 5 个成功、11 个任务翻转（9.7%）。** 用单臂对历史跑测做减法，在这个噪声水平上得不出结论。

**每次跑测必须记录自己的运行参数。** 此前 11 次全量跑测没有一次记录，导致"armA 和 v48 配置是否一致"这个问题事后无法回答，一次成功率差异的归因就此永久无解。两臂已各写 `ARGS.txt`；让 runner 自己把 argv 落盘是更彻底的修法。

## 图的真正瓶颈：55.7% 的边叫不出名字（2026-09-09 实测）

〈设计修订〉一节确定了图目前贡献极小（跳过占总步数 0.3–0.7%，注入 8 次/跑测）。这一节回答**为什么**，因为所有"更好地利用图"的方案都取决于这个答案。

### 因果链

```
64.9% 的步骤发生在重访屏幕上（node_visits >= 2，实测 3055 个 gate 事件）
      ↓  22 倍落差
 2.9% 的步骤图真的说了话（58 次 GRAPH_ENHANCED + 31 次 SKIP = 89/3055）
```

**不是没数据。** 三分之二的步骤所在的屏幕，图里都有出边可讲。落差全部发生在把边转成一条可说的事实这一环。

### 损失在"给控件起名字"

`_action_label`（`graph_distiller.py`）从 `control_key` / `element_identity` 取 **第 1–2 段（text、content_desc）** 作为控件名；两段都空就退化成坐标，而坐标被判为不可用——模型无法在截图里按坐标找控件。实测一次全量跑测的 991 条边：

| 边 | 数量 | 占比 |
|---|---:|---:|
| **标签不可用 → 无法产生任何事实** | **552** | **55.7%** |
| 可用标签 + 有 `discovered_labels` → 能产生正面事实 | 249 | 25.1% |
| 可用标签 但无 `discovered_labels` → 只能是负面事实 | 190 | 19.2% |

这一环是**卡死的**，因为注入有一条硬门：

```python
if not any(f.fact_type in ("VERIFIED", "OBSERVED") for f in chosen):
    return ""     # 没有正面事实就不说话
```

这条门有实测依据（2026-08-31：12 个任务的 20 次注入全是"Need 行 + 死胡同"，那一臂丢了 4 个任务），**不放宽**。

其余环节都不是瓶颈，逐个排除过：
- **落点标签充足**：991 条边里 563 条（57%）带 `discovered_labels`，其中 513 条来自模型自己走的边
- **`min_fact_utility=0.15`、`max_graph_facts=3`、64 token 预算**：这些只在已有正面事实之后才起作用
- **探测预算**：v33 已证伪（探测量 +110%，命中率不动）

`_action_label` 的 docstring 自己记着这句话，只是此前没有量化：*"That is the whole reason no graph context was ever injected across 116 tasks."*

### 一个零成本的部分修法，以及它的真实规模

`_action_label` 跳过了 `control_key` 的**第 0 段 `resource_id`**，而 `resource_id` 常常本身就是好名字（`conversations_fab`、`btn_record_stop`）。

**但不能直接回退。** 552 条里的第 0 段大半是噪声，直接用会把废话注进 prompt——正是本项目被烧过的那类错误（"the control at (540,605) already used" 曾是一整条注入的全部内容）：

- `android.widget.FrameLayout@5,12` —— `_control_key_at` 在控件无名时合成的「类名@网格」键，不是 resource_id
- `0_resource_name_obfuscated` —— 构建时混淆掉了
- `month_view_background`、`*_scrolling_parent`、`*_container` —— 容器，不是用户会按的控件

按保守过滤（剔除合成键、混淆名、容器名、超长名）实测：

```
552 条不可用  →  可救回 78 条（14%）
                 其中带落点标签、能变成正面事实的 51 条
```

救回的名字质量确认对路：`conversations_fab`、`btn_record_stop`、`imv_delete_icon`、`aggregated_stats_button`、`track_list_search`、`top_right_arrow`、`medium_thumbnail`——正是模型最常点、而 a11y 树里没有 text/content_desc 的图标类控件。

**规模要说实话：正面事实源 249 → 300（+20%），注入频率约 8 → 10 次/跑测。在 ±5 个成功的复现噪声下，这不会产生可测量的成功率变化。** 它的价值是解除源头的结构性限制，让后续任何图侧改动有出口，而不是它自己能涨点。

剩下 474 条在 a11y 树里**确实没有任何名字**——要么需要 OCR / 图标分类（离线、CPU、<150 ms 的那条路），要么本来就是不该被命名的容器。这是"55.7% 叫不出名字"里真正硬的部分，也是唯一还没被证伪过的方向。

## 可复现性的边界：temperature=0 也不是逐步可复现（2026-09-09）

这条决定了**哪些实验设计是可行的**，比它所属的那次消融本身更重要。

### 测量

注入消融（`--graph_context distill` vs `off`，其余参数经 `run_args.json` 逐项核对完全一致）本来打算用步级配对来判：在 g_on 发生注入的那一步，两臂此前决策相同时，模型选得是否不同？任务级不可能判——注入 10 次/跑测，而复现噪声是 5 个成功。

结果全部不可比：

| 任务 | 注入步 | 决策首次分叉步 |
|---|---:|---:|
| `ExpenseAddMultipleFromMarkor` | 10 | 1 |
| `FilesDeleteFile` | 7 | 5 |
| `FilesDeleteFile` | 9 | 5 |
| `FilesMoveFile` | 8 | 3 |
| `MarkorCreateFolder` | 7 | 2 |

**注入晚（step 7–10），分叉早（step 1–5），5/5 无有效配对。**

而 `run.py:237` 给 `gelab_agent` 传的是 **`temperature=0.0`**——解码本来就是贪心的。所以分叉源不是采样，只剩环境非确定性：截图的渲染与动画时序、a11y dump 时序，让同一个 prompt 模板下模型看到的图像不完全一样。

### 两条推论

**1. 任何"要跑若干步之后才有资格触发"的机制，都无法用配对步级比较来评估。** 等它有资格发火时，两臂已经走散。这排除了图侧几乎所有机制的步级 A/B——跳过、注入、前缀对齐都要求屏幕被重访过。

**2. ±5 成功 / 9–14 翻转的噪声底是环境噪声，不是采样噪声。** 因此"多跑几次取平均"能压它，"固定随机种子"不能。

### 这解释了此前所有图侧实验为什么"看起来没效果"

事件量一直在测量底噪之下：

| 机制 | 触发量/跑测 | 噪声底 |
|---|---:|---|
| bootstrap 折叠 | 96 | 远高于底噪，因此是唯一能被清楚测到的 |
| 图跳过 | 3–7 | 低于底噪 |
| 蒸馏注入 | 5–13 | 低于底噪 |
| 前缀对齐晋升 | 0–1 | 低于底噪 |

**注入的效果不是"测出来没用"，是"测不了"。** 区别很重要：前者是结论，后者是测量能力不足。

### 因此设计的下一步是被这个约束唯一决定的

要让图侧机制进入可测量区间，必须先抬触发量。而抬触发量唯一未被证伪的杠杆就是〈图的真正瓶颈〉一节测到的根因——**55.7% 的图边叫不出名字**。保守的 `resource_id` 回退能救回 78 条边（其中 51 条能产生正面事实），正面事实源 +20%。

这个改动**不是为了涨成功率**（+20% 在 ±5 噪声下仍不可测），是为了让后续任何图侧改动有可测量的出口。这也是本轮唯一站得住的优化方向：其余路径（探测预算、放宽安全过滤、跨任务重访、深度 2、前瞻晋升）都已各自被证伪。

### 记入方法论

- 每个结论都要**同臂对照**，且差异小于 5 个成功不可判读（三次同配置复现实测：48 / 53 / 52）
- 每次跑测必须落盘 `run_args.json`（已实现）
- **评估一个机制之前，先算它的触发量是否高于噪声底**；低于就先想办法抬触发量，而不是去测它有没有用

## 蒸馏注入消融：设计里最后一个未验证的部分（2026-09-09，两臂各 116 任务）

`--graph_context distill` vs `off`，跳过在两臂都开着，其余参数经 `run_args.json` 逐项核对完全一致（差异只有 `graph_context`、各自的 `app_memory` store 与输出目录，`git_head` 相同）。同一台模拟器、同一次开机、背靠背。

| 臂 | N | 成功 | 成功率 | 全体均步 | 成功均步 | 注入 | bootstrap | 图跳过 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **g_on**（distill） | 115 | 53 | 46.1% | 8.69 | 5.92 | **10** | 96/96 | 5 |
| **g_off**（off） | 115 | **54** | 47.0% | 8.70 | **5.74** | **0** | 96/96 | 10 |

同任务 n=115：净差 **−1**，翻转 11。**关掉注入的那一臂成功多 1 个、成功均步低 0.18。**

### 与同配置复现噪声并排看

`s1a`、`s1b`、`g_on` 三臂参数完全相同（`s1b` 的 `--align_requires_action_match` 全程未生效过），是同一配置的三次独立复现：

| 对比 | 净差 | 翻转 |
|---|---:|---:|
| s1a vs s1b | −5 | 11 |
| s1a vs g_on | −4 | 14 |
| s1b vs g_on | +1 | 9 |
| **g_on vs g_off（注入消融）** | **−1** | **11** |

**消融的差异（−1，翻转 11）比同配置跑两次的差异（最大 −5，翻转 9–14）还小。** 换句话说：把这个机制整个关掉，和把同一份配置再跑一遍，在结果上分不出来。

### 步级：4 个可比事件，1 个改变了决策

任务级不可能判（10 个事件对抗 5 个成功的噪声底），步级也几乎无法配对——注入发生在 step 7–10，两臂决策在 step 1–5 就分叉（见〈可复现性的边界〉）。10 次注入里只有 4 次落在分叉之前：

```
MarkorDeleteNewestNote  step3  决策相同
MarkorDeleteNote        step3  决策相同
MarkorTranscribeVideo   step1  决策相同
MarkorTranscribeVideo   step2  决策不同
    注入: [Memory] Need: VLC, Markor. Observed: FOLDER -> {Markor, Go to, Sort by, Search}.
    g_on  input_text "ZwUN_moment_70__transcription"
    g_off click(934,641)
```

**注入确实能改变决策（1/4），但没有证据说明改得更好**——那唯一改变了决策的任务两臂都失败了。n=4 的区间宽到没有推断价值。

### 结论

**蒸馏注入没有可测量的效果，点估计还略偏负面。** 这不足以证明它有害（−1 在噪声内），但足以说明它**不是步数收益的来源**——〈设计修订〉一节里配对重算后剩下的那 −0.7 步，现在也不能归给它了。

配合此前的归因，图的两条输出路径都测完了：

| 路径 | 触发量/跑测 | 实测收益 |
|---|---:|---|
| 权威边重放（跳过） | 3–10 | 总步数的 0.3–0.7%，48/48 来自模型自走的边 |
| 蒸馏注入 | 0–13 | 无可测量效果 |
| 前缀对齐 → 晋升 | 0–1 | 0 步（11 次跑测 2 条边，均未执行） |
| **bootstrap 折叠**（不经过图） | **96** | **省下推理的 94–97%** |

**信念图目前的净贡献落在噪声内；测得到的省步全部来自 bootstrap 折叠这张表查找。** 这是当前设计必须承认的地基，也是〈图的真正瓶颈〉一节要解决的问题——在 55.7% 的边叫不出名字被修掉之前，图侧机制的触发量都在测量底噪之下，做什么都测不出来。

## 设计修订 II：图的构建、探索与推理增强（2026-09-09，参考文献 + 本项目实测）

前几节测完了现有设计的每一条路径，结论是**信念图的净贡献落在噪声内**。这一节回答三个问题——图怎么建、怎么用来探索、怎么用来增强推理——每条主张都标明是文献做法还是本项目实测。

### 参考的四篇

| 论文 | 与本设计相关的做法 |
|---|---|
| [UI-KOBE](https://arxiv.org/abs/2605.29534) | 每 app **离线**探索 300 步建图（54 节点 / 226 边 / 3.2 小时 / $6.2），节点=语义页面状态，边=动作+自然语言指令+落点观察；运行时两阶段检索（视觉召回→模型确认或全拒），把「自环动作 / 邻接转移 / 自由动作 / 任务完成」四类选项交给模型 |
| [Executable Agentic Memory](https://arxiv.org/html/2605.12294) | 状态节点与**动作节点交替**的 DAG；离线 DFS 探索；双层去重（embedding 粗筛 + VLM 细验，元素级用 bbox IoU）；**BPE 式动作组挖掘**把高频动作序列压成可复用的多步动作；在线用 Q 引导的 MCTS 在图上搜路径 |
| [GraphPilot](https://arxiv.org/abs/2601.17418) | 离线阶段把交互历史分析成「页面功能 / 元素功能 / 元素→页面转移规则」；在线用图引导 LLM **近乎一次查询**产出整条动作序列，再用图中的转移规则**校验并迭代修正** |
| [KG-RAG](https://aclanthology.org/2025.emnlp-main.274/) | 按任务目标从图中检索相关元素，结构化描述 + 关系图注入 prompt |

**四篇的共同点：图在任务开始前离线建好。** 这是与本设计最根本的差异，也是下面每个答案的出发点。

### 先摆一个必须承认的实测

| | 本设计 | UI-KOBE |
|---|---|---|
| 每任务结束时的图 | 中位 **9 节点 / 7 边** | — |
| 每 app 的图 | Markor 最好 60 屏 / **69 转移**（116 任务累积） | **54 节点 / 226 边**（任务前就有） |
| **平均出度** | **0.77**（Markor 1.15） | **4.2** |

**出度 0.77 意味着大多数节点没有任何出边。** 从这样的图里回答不了"我在这块屏幕上能做什么"——注入找不到正面事实、跳过没有可重放边、前瞻无法对齐，是同一个原因的三种表现。

原因是结构性的：**我们只记录智能体真的走过的转移**，一次访问产出一条出边，图因此是「走过的路径树」而不是「app 的图」。命名问题（55.7% 的边叫不出名字）是真的，但**次要**——出度 0.77 的图就算每条边都有名字也没什么可说。

## 问题一：如何高效地建图

### 预算其实是够的，而且是免费的

```
一次 116 任务跑测：推理步 1010
  并行窗口总预算   61.5 分钟
  探索实际用掉      2.5 分钟（4.0%）
  闲置             59.1 分钟
```

UI-KOBE 每 app 花 3.2 小时离线建图，是**付费、串行、任务前**的成本。我们每次跑测有 **59 分钟闲置的并行预算**，藏在推理背后、不增加任何墙钟时间。**这就是本设计相对文献真正的位置：同样的图，用免费的时间建。**

现在只用了 4%，原因是三重限流：`node_visits >= 2` 的门、`probes_per_step 3` 的预算、安全门（67% 的探索轮零探测）。**这三条都不是为「建图密度」设计的，是为「当步前瞻命中」设计的**——而前瞻已经证伪。目标换了，限流条件就该跟着换。

### 存什么

保留现有的节点/边 schema（`(activity, layout_signature)` 的节点身份、`control_key` 的边身份、`discovered_labels`、执行/跳过计数、`rollback_success`），并按文献补三项：

1. **落点观察要存得比 `discovered_labels` 更结构化**（UI-KOBE 的「target observation」）。现在只存"落点上新出现的标签"，8 个封顶。正面事实的质量直接由它决定。
2. **边上存自然语言指令**（UI-KOBE），而不只是 `control_key`。这正是〈图的真正瓶颈〉那一节的问题：55.7% 的边叫不出名字。文献用一次 VLM 调用给边生成描述——我们有闲置的并行窗口，可以在探测之后顺带做，**但这引入模型调用，必须先测值不值**。
3. **节点身份加语义确认**（UI-KOBE 的两阶段、Executable Agentic Memory 的双层去重）。我们现在纯结构（activity + 可交互骨架），已经踩过一次坑：键盘/状态栏浮层把一块屏幕拆成三个节点（已用 `OVERLAY_PACKAGES` 修）。语义确认能防的是反向错误——结构相同但语义不同的两块屏幕被合并。**这个错误目前没有证据发生过，先不做。**

### 怎么更新：exploration 与 inference 各写什么

这一点本设计已经比文献更清楚，实测支持：

- **inference 写权威边**：模型每一步真实执行的转移。**48/48 次图跳过用的都是这类边**，探测发现的边被跳过 0 次。这是图中最有价值的部分。
- **exploration 写投机边**：探测发现的转移，`rollback_success` 决定可信度。它目前不给任何省步机制供料，但它是**唯一能提高出度的手段**——权威边一次访问只给一条出边。

**改动**：把探索的目标从"猜中当步动作"改成"提高当前节点的出度"。具体是把 `min_node_visits` 从 2 降到 1（首访屏幕也探，此前禁止它的理由是"探测从未为跳过供料"，那是在 node_id 对不上的系统上测的），并把 `probes_per_step` 按**剩余并行窗口**动态给（当步推理还剩多少时间就探多少），而不是固定 3。

### 怎么插节点

保持现在的做法：只在**真实转移落地时**插入节点，不预测性插入。文献里 UI-KOBE 的 auditing 与 Executable Agentic Memory 的双层去重都是为了修离线批量探索引入的重复节点——我们逐步在线插入，重复节点的来源只有身份键不稳，那一类已经修过（overlay、node_id 不匹配）。**不引入 auditing。**

## 问题二：如何利用图进行更好的探索

### 选什么元素

现状是 `information_need` / `graph_matrix` 打分器按「与任务需求的语义重合 + 位置先验 + 落点已知」排序。**这套是为"猜中模型下一步"设计的，而那个目标已被证伪三次**（探测量翻倍、放宽安全过滤、随机排序都不改变结果——`vrand` 用均匀随机排序拿到 57/115，是所有臂里最高之一）。

**随机排序不比精心排序差，这本身就是结论**：在"猜中当步动作"这个目标上，排序器没有信息可用。

换成 UI-KOBE 的目标就有信息可用了：**优先探测当前节点上「尚未有出边的可交互元素」**（UI-KOBE：retrieve "outgoing edges that have already been explored and the visible elements that remain unexplored"）。这是覆盖率目标，不是预测目标——它不需要预测模型会点什么，只需要知道图里缺什么，而这是图本身能可靠回答的。

### 搜索策略

- Executable Agentic Memory 用 **DFS**，UI-KOBE 用**「覆盖导向的再探索」**（周期性挑选探索不足的节点继续探）。
- 我们受一条硬约束：**探测必须可回滚**（`INVERSE`/`BACK_N` 阶梯），所以只能做**深度 1 的星形展开 + 有限深度 2**，做不了自由 DFS。这不是缺陷，是在线并行架构的必然代价——离线建图可以随便走丢，在线不行。
- 因此可行的策略是 UI-KOBE 那一类：**在当前节点做覆盖优先的星形展开**，跨步之间靠「出度最低的已知节点」来决定下次访问该屏幕时探什么。**这需要在 app memory 里记「这块屏幕还有哪些元素没探过」**——现在只记探过的。

### 怎么总结图的历史信息（用于探索）

这是 meeting note 里"aggregate information"的落点，具体三条聚合量，都能从现有数据算：

1. **节点的探索完成度** = 已有出边的可交互元素数 / 可交互元素总数。决定这块屏幕还值不值得探。
2. **`(activity, probe_type)` 的可回滚性**（已有 `known_inverse_levels`）。跨任务复用：一个组合在别处回滚失败过，这里就别探。实测支持：9 个组合在多个任务里重复回滚失败，共 14 次事故，而"有一轮未复原"的 episode 成功率 67% vs 全复原 89%。
3. **跨任务的屏幕复现率**（实测 33%，平均每屏被 4.0 个任务访问）。复现率高的屏幕，探索的摊销收益高，值得优先探。

## 问题三：如何利用图的信息增强推理

### 现状：两条路都测完了，都在噪声内

| 路径 | 触发量/跑测 | 实测收益 |
|---|---:|---|
| 权威边重放（跳过） | 3–10 | 总步数 0.3–0.7% |
| 蒸馏注入 | 0–13 | **无可测量效果**（消融净差 −1，同配置复现噪声 ±5） |
| 前缀对齐 → 晋升 | 0–1 | **0 步** |
| bootstrap 折叠（不经过图） | 96 | 省下推理的 94–97% |

**触发量全部低于噪声底，所以不是"测出来没用"，是"测不了"。** 见〈可复现性的边界〉。

### 文献的做法差在哪

GraphPilot 用图**一次性产出整条动作序列**再用转移规则校验修正；UI-KOBE 把邻接转移作为**结构化选项**交给模型选。两者都不是"注入几条事实让模型参考"——它们让图**直接约束动作空间**。

我们的注入是前者的弱化版：`[Memory] Need: ... Observed: X -> {A, B, C}` 三行文本，10 次/跑测。**这个形态既没有 GraphPilot 的约束力，触发量又低到测不出来。**

### 因此推理侧的改动顺序是被约束唯一决定的

1. **先抬触发量，再谈形态。** 在出度 0.77 提到 2 以上之前，任何注入形态的改进都测不出来。这意味着**问题一的改动必须先做**。
2. **触发量上来之后，把注入从"参考事实"改成"候选约束"**（UI-KOBE 形态）：把当前节点的已知出边作为显式选项列给模型，而不是作为一段描述。这可测——选项被采纳的比例是直接可观测的。
3. **跳过机制保持不变。** 它 48/48 全部来自模型自走的边，命中率 74%，是图上唯一被验证过的省步路径；它的问题是触发量（3–10 次）而不是正确率，同样要等出度上来。

### 明确不做的

- **不做 MCTS / Q 模型**（Executable Agentic Memory）：它依赖离线训练的 Q 模型和图上多步 rollout，我们的图出度 0.77，rollout 无路可走。
- **不做离线预建图**：那是文献已有的做法，且放弃了本设计唯一的差异化位置（免费的并行窗口）。
- **不放宽注入的正面事实硬门**：2026-08-31 实测放宽会丢 4 个任务。
- **不再调探测排序器以求猜中当步动作**：已被三种方式独立证伪，且随机排序不更差。

---

### 实现（2026-09-09）

三处改动，都是新增开关、默认行为不变：

**1. `CoverageRanker`（`rankers.py`）** — 排序目标从「猜中模型下一步」换成「图还不知道什么」：

```
+10  该控件在本节点还没有出边
 +3  该控件能被命名（无 text/content_desc 的边永远变不成事实）
 +role bonus
 −8  本轮已探过
```

`control_key()` 去掉 bounds，与图的边键一致——控件因滚动位移后仍是同一个控件，否则每次滚动都会被当成全新元素。

**2. `_known_control_keys(snapshot, node_id)`（`live_probe.py`）** — 从上一代图快照取本节点全部出边的 `control_key`。**不区分来源**：模型自己走出来的边和探测发现的边，对"这里还需不需要探"的回答是等价的，而再探一次要付真实的回滚风险。

**3. `--exploration_budget_s`（默认 `120.0`，即历史行为；`auto` = 本 episode 已观测推理延迟的中位数）** — 此前 `max_exploration_time_s` 默认 120 秒，等于**没有预算**，循环只受 `max_probes` 限制。这意味着「探索藏在推理背后所以免费」这个不变量从未被强制执行过：实测一个 8 探测的覆盖轮跑了 5.45 秒，而推理窗口中位是 3.42 秒。`auto` 让预算自适应每个 app 与模型，不写死常数；已开始的探测会跑完，所以单轮最多超出一个探测的时长（中位约 0.6 秒）。

冒烟（`MarkorDeleteAllNotes`，8 步）：

| | 基线 | 覆盖策略 |
|---|---:|---:|
| 图出度 | 0.77 | **1.75** |
| 边/探测 | 0.58 | 0.82 |
| 单轮耗时 | — | 5.45s → 3.5–4.3s（加预算后） |

新增 8 个测试（覆盖排序 5、快照键提取 3），全量 180 通过。

**验证方式**：只跑覆盖臂一个 116 任务，基线用同配置的三次复现（s1a 49 / s1b 53 / g_on 53）。**主指标是出度，不是成功率**——成功率按设计就落在 ±5 噪声带内，这个实验测的是「机制能否进入可测量区间」。最大的风险是覆盖排序故意探没人探过的控件，**未复原率可能上升**，那是实测代价最明确的一类轮次。

### 实现之后的实测：三处改动全部无效，瓶颈是一条规则（2026-09-09）

上面三处改动跑了两个臂，都停在早期，因为主指标（出度）在同一批任务上纹丝不动：

| 同一批 16–17 个任务 | 探索轮 | 探测 | 合计出度 |
|---|---:|---:|---:|
| 仅覆盖排序 | 53 | 13 (19%) | 0.69 |
| 覆盖排序 + `--allow_icon_only_probes` | 53 | 10 (19%) | 0.64 |
| g_on（基线） | 50 | 10 (20%) | 0.67 |
| s1a（基线） | 50 | 10 (20%) | 0.70 |

**探测数三臂完全相同（10 : 10 : 10）。**

原因是逐层排除出来的：

```
探索轮 57
  其中 51 轮真的评估了候选（只有 6 轮连候选都没有）
  但 48 轮探测数为 0  →  候选被全部拒绝
拒绝理由: action_button_requires_semantic_inverse  92.3%
```

**排序器、icon-only 放行、探测预算，全都在 `role == "button"` 这条规则的下游。** 重排一个被清空的列表、给一个空列表更多时间、放行一类根本走不到那条检查的元素——三者必然无效。（icon-only 元素多数 role 就是 button，在更早的规则被拦，所以放行它只把拒绝理由从 36.3% 的 icon_only 挪到了 92.3% 的 button。）

### 这条规则拒的是对的东西

被它拒掉的 211 个按钮，按标签统计：

```
18  Start                       秒表/录音开始，不可撤销
11 × 12  0 1 2 … 9 00 ⌫         一整个数字键盘，占一半以上
 8  MODE LIST / FILMSTRIP / Z- / Z+    相机控件
 5  Pause    3  EDIT    3  CONFIRM    2  Ok
```

探测"7"既学不到东西又污染输入；`Start`/`Confirm`/`Ok` 正是这条规则存在的理由。**这里没有可挖的空间——放宽它就是去按 Confirm。**

### 因此的结论：在线安全探索有硬上限，而这不是实现缺陷

把 (a) 不可撤销的动作按钮 和 (b) 叫不出名字的图标 去掉之后，一块屏幕上剩下的可安全探测控件本来就很少。**这是正确行为，不是待优化的限制。**

由此，与文献的出度差距要重新解释：

| | 出度 | 代价 |
|---|---:|---|
| UI-KOBE（离线） | 4.2 | 每 app 3.2 小时、$6.2，**可以按 Delete 然后重置 app** |
| 本设计（在线并行） | 0.77 | 0 额外墙钟，**永远不允许弄坏正在跑的任务** |

**0.77 与 4.2 的差距不是实现落后，是"不许弄坏任务"的价格。** 离线探索可以随便走丢、按下不可逆按钮、然后把 app 恢复到初始快照；在线并行探索每一次探测都必须能原路返回，因此它能碰的控件在结构上就是一个小得多的子集。

这也把〈图的真正瓶颈〉一节的结论收紧了一层：55.7% 的边叫不出名字是真的，但**即使全部命名，可探测集合仍然被"必须可撤销"这条约束限制住**——两条约束叠加之后，在线探索能达到的图密度有一个远低于离线方法的天花板。

### 这对论文叙事的意义

不要把"图密度低"写成待改进项去和离线方法比密度——那场比较在设计约束上就输定了。应该写成**受约束条件下的可行性结果**：在不增加任何墙钟时间、不允许破坏任务状态的前提下，能建起多大的图、它能省多少步。目前的答案是：省下的推理 9.0–9.2%，其中 94–97% 来自 bootstrap 折叠；图本身的净贡献落在噪声内。

**保留的三处实现**（`CoverageRanker`、`_known_control_keys`、`--exploration_budget_s`）默认不改变行为，且都不是错的——它们只是位于瓶颈下游。`--exploration_budget_s auto` 尤其值得留着：它把「探索必须藏在推理窗口内」这个不变量第一次真正强制执行了（此前默认 120 秒等于没有预算）。

### 一句话总结这次修订

**此前所有图侧设计都在优化"用图猜中模型的下一步"，而那条路已被证伪四次；实测指出真正的瓶颈是图的出度只有 0.77——图根本不知道一块屏幕上有什么。所以设计目标应从「预测」改为「覆盖」：用那 59 分钟闲置的并行预算把出度做上去，让图侧机制先进入可测量区间，再谈怎么用它。**

## 设计修订 III：读完 LLM-Explorer 与 AutoDroid 原文之后（2026-09-09）

前两节的文献对照是从网页摘要读的。这一节是从 PDF 原文读的 **[LLM-Explorer](https://arxiv.org/abs/2505.10593)（MobiCom'25）** 与 **[AutoDroid](https://dl.acm.org/doi/10.1145/3636534.3649379)（MobiCom'24）**，逐机制对照本项目的实测，并据此改了一处实现。

### LLM-Explorer 的四个机制，逐条判定

| 机制（原文 §3.2–3.3） | 判定 | 依据 |
|---|---|---|
| **规则式状态抽象**：排除动态属性（文本内容、选中态、滚动位置），剩余元素集合相同即合并。原文实测**规则式优于 LLM 式** | ✅ **已有** | `layout_signature` 已完全排除文本、用 64px 粗网格、重复控件只计种类不计位置 |
| **抽象动作**：把功能相同的一组元素（日历 30 个日期格）合成一条 | ❌ **不转移** | 实测只能压缩 **3.1%**（986 条边 → 955 条）。我们一个任务才 9 条边，列表行重复没有堆积 |
| **`ineffective` 标志**：动作未改变抽象状态即标记，不再重试 | ⚠️ **收益有限** | 我们不记 `dst == src` 的自环步，但实测它只占 **10%**（1010 步中 100 步） |
| **app-wide 动作选择 + 容错导航**：从全 app 的未探索动作里选，不在当前屏幕就导航过去 | ❌ **结构上不可用** | 要求离开当前屏幕，我们必须原地返回 |

### 结构性发现：出度 ≈ 1 是轨迹的数学形状，不是缺陷

```
推理步 1010  →  记录成边 910（90%）
每任务 ~8.7 步 → ~8 条边、~10 个节点
```

**一条轨迹的出度按定义就是 N/(N+1) ≈ 0.8。** 要让出度 > 1，只能靠两件事：任务自己**重访**同一节点并采取**不同**动作，或**探测分叉**。而探测被安全门（92.3% 拒绝率，拒的是 Confirm 和数字键盘）封在约 4 次/app。UI-KOBE 的 4.2 来自 300 步分叉式离线探索。

这个推导可以直接验，而且验出来极干净（四次跑测 458 个 episode）：

| 分桶 | n | 成功率 | 均步 | 出度 | 图跳过 | 注入 |
|---|---:|---:|---:|---:|---:|---:|
| 从不重访 | 24 (5%) | 45.8% | 1.38 | 0.46 | **0** | **0** |
| 重访 2 次 | 115 (25%) | 67.0% | 4.12 | 0.64 | **0** | **1** |
| **重访 ≥3 次** | 319 (70%) | 37.9% | 11.00 | **0.86** | **24** | **30** |

**100% 的图跳过与 97% 的注入落在"重访 ≥3 次"的任务上**，出度随重访次数单调上升。**在线图只能在任务自身回到某块屏幕时才可能获得分叉信息**——这不是可以工程绕过的，是在线建图的定义。

由此建了 `configs/graph_active_suite.json`（**37 个任务**，十次跑测里实际产生过跳过或注入的全部任务，138 个机制事件）。信号 100% 保留，设备时间 2.3h → 45 分钟。**在机制根本不触发的任务上跑测是纯浪费。**

### AutoDroid 的可转移之处：注入的**形态**，不是内容

AutoDroid（§3.2.2）不注入独立的记忆块，而是**给 UI 表示里的元素加 `onclick` 属性**——知识直接标注在模型正在看的那个元素上。

| | 本设计（`distill`） | AutoDroid |
|---|---|---|
| 形态 | 独立 `[Memory]` 块 | 元素上的 `onclick` 属性 |
| 门 | **整块必须至少含一条正面事实**，否则完全不说 | 只要知道就标注 |
| 触发量 | **10 / 1010 步** | 每个有知识的元素 |

实测：**31% 的步骤存在候选事实**（`candidate_fact_count > 0`），但只有 10 步真的注入——**块级硬门丢掉了 97% 的已知信息**。

本 agent 的 prompt 是纯截图（任务 + 历史 + 图像，`gelab_agent.py:1042`），没有 HTML 元素列表可挂属性，所以锚点用控件的可见标签代替。**要转移的是门，不是锚点。**

实现为 `--graph_context onclick`（默认仍是 `distill`）：去掉块级正面事实门，改为逐控件一行；**每一条 per-fact 的质量过滤原样保留**——只取落点新增标签、控件必须可命名、`min_fact_utility` 底线、负面事实不单独成句。那三条都是有实测代价的（2026-08-31 无正面事实的注入丢了 4 个任务；`MarkorCreateFolder` 因为注入工具栏标签从 5 步涨到 15 步）。

### 注入漏斗的精确归因：一个阈值砍掉 93%（2026-09-09）

〈蒸馏注入消融〉证明注入没有可测量效果，〈可复现性的边界〉指出那是因为触发量（10 次/1010 步）低于噪声底。这一节定位触发量是在哪一环丢的——因为抬触发量是唯一能让图侧机制变得可测的路径。

从 `graph_context` 事件的 `raw_fact_count` / `candidate_fact_count` / `selected_fact_count` 三个字段读出的真实漏斗（1010 步）：

| 环节 | 步数 | 占比 | 该环损失 |
|---|---:|---:|---|
| 当前节点有出边 | 460 | 45.5% | — |
| → 有候选事实 | 207 | 20.5% | `_to_fact` 砍 **55%**（控件叫不出名字） |
| → 有事实通过筛选 | **15** | **1.5%** | `min_fact_utility` 砍 **93%** ★ |
| → 实际注入 | 10 | 1.0% | 正面事实门砍 **5 步** |

**192 步「有候选事实但一条都没选出来」，全被 `min_fact_utility = 0.15` 这一个数字砍掉。** 相比之下，此前被当作主要嫌疑的正面事实硬门只值 5 步。

### 顺带否掉的一个改动：AutoDroid 的 onclick 形态

按 AutoDroid（§3.2.2）实现了 `--graph_context onclick`——去掉块级正面事实门，改为逐控件一行。**在 661 个真实节点上离线重放，触发量 1.0×，完全没有提升。**

原因是逻辑等价：块级门是"`chosen` 里没有正面事实就返回空"，onclick 是"输出 `chosen` 里的正面事实"，**两者为空的条件完全相同**。改的是格式，不是门。

代码保留（默认仍 `distill`），但**不要指望它改变触发量**。这条记在这里，免得后人重做一遍。

### 阈值的可达上限：2.4×

离线扫描 `min_fact_utility`（661 个节点，`need_match=0` 因此偏保守）：

| 阈值 | 能说话的节点 | 相对 0.15 |
|---:|---:|---:|
| 0.15（现值） | 13.5% | 1.0× |
| 0.10 | 16.6% | 1.2× |
| **0.08** | 25.3% | **1.9×**（拐点） |
| 0.05 | 28.3% | 2.1× |
| 0.00 | 32.2% | **2.4×（上限）** |

**即使阈值归零也只能到 2.4×**，因为 `_to_fact` 已经先砍掉 67%——那是命名问题（`_action_label` 无法命名的控件占 55.7% 的边），不是阈值能解决的。

所以注入触发量的天花板是 **~24 次/跑测**，仍然低于 116 任务上 ±5 的噪声底。这再次指向同一个结论：**图侧机制要变得可测，要么解决命名问题，要么在机制真正触发的小套件上把噪声底降下来。** 后者已经在做（`graph_active_suite`，3 个复现）。

### 噪声底：graph-active 套件把分辨力提高了 2.5 倍（2026-09-09）

此前每个图侧结论都卡在同一句话上——「差异小于 ±5 个成功不可判读」。那个 ±5 是在 116 个任务上测的，而机制只在其中约 37 个任务上触发，另外 79 个只贡献噪声不贡献信号。

在 `configs/graph_active_suite.json`（37 任务）上跑三次**完全相同配置**的独立复现：

| 复现 | 成功 | 全体均步 | 成功均步 | 图跳过 | 注入 | 探测 |
|---|---:|---:|---:|---:|---:|---:|
| r1 | 9/37 | 10.54 | 6.67 | 6 | 8 | 51 |
| r2 | 8/37 | 11.41 | 6.88 | 4 | 7 | 63 |
| r3 | 10/37 | 11.24 | 7.30 | 6 | 10 | 72 |

```
均值 9.0 ± 1.0   极差 2
任务级翻转: r1-r2 1 (3%)   r1-r3 3 (8%)   r2-r3 2 (5%)
```

| | 全量 116 | graph-active 37 |
|---|---:|---:|
| 复现 σ | ~2.5 | **1.0** |
| 翻转率 | 8–12% | **3–8%** |
| 单臂设备时间 | 2.3 h | **45 min** |

**±2 个成功现在是可判读的**（2σ），而此前需要 ±5。设备时间同时降到三分之一。

一个必须写明的限定：这个套件的成功率只有 24%，低方差有一部分来自「稳定失败的任务不会翻转」。但机制在这个套件上确实触发（每次跑测 4–6 次跳过、7–10 次注入），所以它在因果上也是敏感的，不只是统计上方差小。**要测的是图侧机制，就应该在图会说话的地方测。**

这条与〈可复现性的边界〉合起来是本轮的方法论结论：

1. 评估一个机制之前，先算它的触发量是否高于噪声底
2. 低于就先想办法**换套件**（把不触发的任务移出去），而不是直接去测它有没有用
3. 每个结论都要同臂对照；差异小于 2σ 不可判读，σ 用同配置复现实测，不用估

### `--min_fact_utility` 实验的判据（先写死，不事后调整）

- **主读数**：注入次数是否真的涨到约 2×
- **安全读数**：成功数是否掉出三复现噪声带。掉出去 = 这个阈值在做实事，设计里必须写明它的代价；没掉 = 阈值可以放低，后续图侧工作有更大空间

后者才是这个实验真正的价值：文档已记录过坏注入的实际代价（2026-09-02，`MarkorCreateFolder` 因为注入工具栏标签从 5 步涨到 15 步），所以"放宽会不会伤人"是一个有先例、值得测的问题。

### 待验证

`onclick` 形态尚未跑测。验证顺序被噪声底约束：先用 3 个独立复现（graph-active 套件）标定该套件上的噪声底，再拿 `onclick` 臂与之比较。**在噪声底确定之前，任何单臂结果都不可判读**——这一点本轮已经栽过一次（s1a 对六个历史参照全负 −6.7，最后证明只是同配置复现分布的低端）。

### `--min_fact_utility 0.05` 的判定：注入 6.1×，成功率 +0.0σ（2026-09-09）

在 `graph_active_suite`（37 任务）上，与三个同配置复现对照。唯一差异是 `min_fact_utility` 从 0.15 降到 0.05。

| 臂 | 成功 | 全体均步 | 成功均步 | 注入 | 注入率 | 图跳过 | 跳过命中 |
|---|---:|---:|---:|---:|---:|---:|---:|
| r1 | 9 | 10.44 | 6.67 | 8 | 2.1% | 6 | 4 |
| r2 | 8 | 11.31 | 6.88 | 7 | 1.7% | 4 | 1 |
| r3 | 10 | 11.14 | 7.30 | 10 | 2.4% | 6 | 4 |
| **util05** | **9** | 10.86 | **7.56** | **51** | **13.0%** | **2** | 1 |

```
复现带 [8, 9, 10]  均值 9.0 ± 1.0   判据区间 [7, 11]（判据在跑测之前定死）
util05 = 9   偏离 +0.0σ   →  落在区间正中央
```

**三个读数：**

| | 变化 |
|---|---|
| 注入 | 8.3 → 51 （**6.1×**） |
| 成功 | 9.0 → 9 （**+0.0σ**） |
| 图跳过 | 5.3 → 2 （**0.38×**） |
| 成功均步 | 6.95 → 7.56 （**+0.61 步**） |

**注入量翻了 6 倍，成功率一动不动。** 这和全量 116 任务上的注入消融（关掉注入，净差 −1）是同一结论的两个方向：**开大和关掉都动不了结果**。

### 新发现：注入与跳过是互斥的，不是互补的

图跳过从 5.3 掉到 2（0.38×），跳过命中从 3 掉到 1。机制上讲得通：跳过的触发条件是「模型在这块屏幕上只选过一个动作、且执行过 ≥2 次」——**注入把"这个控件通向 X"写进 prompt 之后，模型据此自己做出了选择，那种一致性就被打破了**。

这是本项目第一次测到两个图侧机制**互相抵消**。它也解释了为什么此前调注入总是看不到净效果：注入涨的那点收益，被跳过掉的量抵消了。

配合成功均步 +0.61 步，整体判读是：**放宽阈值把决策从"重放已验证的边"推向"读文字自己判断"，代价是步数，收益为零。**

### 对设计的结论

1. **`min_fact_utility=0.15` 保持不变。** 它不是在保护成功率（放宽不掉），而是在保护跳过机制。这个理由和它原本的设计意图不同，要写明。
2. **注入这条路已被三种方式测尽**：关掉（净差 −1）、形态改造（onclick，1.0× 无效）、放宽阈值（6.1× 注入、+0.0σ）。**在当前图密度下，注入不是可用的杠杆。**
3. 剩下唯一没被证伪的方向仍然是**命名问题**（`_to_fact` 砍掉 55% 的候选、`_action_label` 无法命名 55.7% 的边）——它同时卡住注入和探索两条路，且是唯一能真正提高图信息量而非只是搬运既有信息的改动。

### 意外发现：探测在拆跳过的台

| | 探测 | 图跳过 | 跳过命中 | 命中率 |
|---|---:|---:|---:|---:|

**探索一次都没跑，图跳过反而翻了两三倍，命中率从约 50% 升到 85%。**

配合已经测到的「48/48 次跳过所用的边全部来自模型自走、探测发现的边被跳过 0 次」，可以合成一句完整的话：

> **探索不但不给跳过供料，它还在拆跳过的台。**

同一天测到的另一半是「注入与跳过互斥」（`min_fact_utility` 放宽后注入 6.1×、跳过 0.38×）。两者合起来指向同一件事：**跳过依赖模型行为的一致性，而任何往环境或 prompt 里加东西的机制都在破坏这种一致性。** 这是本设计里三个机制之间第一次被测到的真实相互作用。

净差 −1   翻转 9 (8%)，与同配置复现的翻转率一致
```

**探索开关对成功率没有可测量的影响。** 净差 −1 落在噪声正中（同构建四臂 52.2 ± 2.2，翻转率 8%）。步数上也几乎没差别：全体均步 −0.23、成功均步 −0.12，两个数都小于同配置复现之间的差异。

跨天对比时看到的 +1.2σ，在同场次对照下收敛为 −1。**这是本轮第三次「跨天对比给出的信号在同场次对照下消失」**，前两次是 s1a 的 −6.7σ 和本实验中途按 62 个任务外推的 +4.5。规矩再重申一次：**只有同场次同臂对照可以判读。**

### 确认的发现：探测在拆跳过的台

这一条在同场次对照下复现了，而且更强：

| | 探测 | 未复原 | 图跳过 | 跳过命中 | 命中率 |
|---|---:|---:|---:|---:|---:|
| off | 0 | 0 | **13** | **11** | **85%** |
| on | 101 | 11 | 7 | 4 | 57% |

**关掉探索，图跳过接近翻倍（1.9×），命中率从 57% 升到 85%。**

跳过的触发条件是「模型在这块屏幕上只选过一个动作、且执行过 ≥2 次」。探测每次跑测污染 11 轮未复原的屏幕状态并改变后续轨迹，让那种一致性凑不齐——不只是少触发，触发的那些质量也更差（命中率低 28 个点）。

与同日测到的另一半（`min_fact_utility` 放宽后注入 6.1×、跳过 0.38×）合起来：

> **跳过依赖模型行为的一致性；任何往环境里加动作（探测）或往 prompt 里加文字（注入）的机制，都在破坏这种一致性。**

三个机制之间第一次被测到的真实相互作用，而且方向一致：**它们互相抵消，不互相增强。**

### 对设计的结论

1. **探索在当前构建下的净贡献是零**：不改变成功率、不改变步数、不给跳过供料（48/48 来自模型自走的边），反而把跳过打掉一半。它唯一确定的产出是每次跑测 11 轮未复原的脏状态。
2. **三个机制里只有 bootstrap 折叠是净正的**（384/384，占省下推理的 94–97%），跳过是小额正贡献（总步数 0.3–0.7%）且**在探索关闭时更好**，注入与前瞻为零。
3. 因此当前证据支持的最优配置是：**bootstrap 折叠 + 跳过 + 关闭探测**。这个配置在本次对照里是 55/115、成功均步 5.78，且跳过命中率 85%。

## 用图的历史信息引导探索：`GraphKeywordRanker`（2026-09-10）

### 这一节回答的问题

「如何用 graph 信息增强 exploration」此前完全没有答案：所有排序器匹配的都是**模型上一轮推理的 need**，图对探索的贡献是零。

### 机制

图不能预测模型会点什么（四次独立证伪，其中均匀随机排序拿到 57/115，是历史最好之一）。但它能可靠回答**什么已经知道了**——`discovered_labels` 记录着探测或权威步在某个控件背后看到过的文本。所以：

```
score(候选) = sim(候选, need) − 0.5 · max_j sim(候选, 已发现标签_j)
```

关键词取自本节点的出边，以及**一跳之外**的边（探测把已经走过的下一屏重新发现一遍同样是浪费）。

**实现三件套：**

| | |
|---|---|
| `semantic_service.py` | 常驻 22M 编码器（`paraphrase-MiniLM-L6-v2`），socket 协议 |
| `GraphKeywordRanker`（`rankers.py`） | 两阶段：便宜排序器把 108 个候选收窄到 32，编码器再重排 |
| `_discovered_labels_near()`（`live_probe.py`） | 从图快照取本节点 + 一跳邻居的已发现标签 |

**为什么必须做成常驻服务**：探索进程是每步 spawn 的新解释器，加载 MiniLM 要 7.4 秒，会把探索推出它必须待在里面的推理窗口。服务化之后每次调用 46–87 ms。第一版对每个已知标签发一次请求（24 次往返），单轮 6.9 秒——改成一次调用、候选只编码一次才进预算。服务不可达时**静默回退**到基础排序，一个可选模型绝不允许中断探测窗口。

### 跑测前先测天花板

```
模型的下一次点击在候选集内:  4.4–14.9%（容差 40–100px）
现有排序器已把它排进前 3:    3.5– 9.6%
→ 完美排序器的空间: 每 114 步多命中 2–6 次
```

其余 85% 的情况模型的动作**根本不在候选集里**——被安全门挡掉（Confirm、数字键盘、无标签图标）。这条路能给的就这么多。

### 结果（graph-active 套件 37 任务，同任务对比）

| 臂 | 成功 | 成功均步 | 探测 | 边/探测 | 未复原 | 跳过 | 命中 | 命中率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **sem** | 12 | 8.42 | 33 | 0.79 | 4 | 14 | 10 | 71% |
| **sem2** | 9 | 7.67 | 32 | 0.66 | 4 | 10 | 8 | 80% |
| r1 | 9 | 6.67 | 51 | 0.65 | 9 | 6 | 4 | 67% |
| r2 | 8 | 6.88 | 63 | 0.59 | 11 | 4 | 1 | 25% |
| r3 | 10 | 7.30 | 72 | 0.71 | 10 | 6 | 4 | 67% |

**成功率：不成立。** 第一次 12（+3.0σ，掉出判据区间 [7,11]），复现 9（+0.0σ）。两组区间重叠（semantic [12,9] vs 基线 [9,8,10]）。这是当天第四次单臂信号在复现下消失，判定标准在跑测前定死、事后未改。

**三个机制读数：两次都复现，且与基线完全不重叠。**

```
探测    semantic [33, 32]   基线 [51, 63, 72]   减少约 45%
未复原  semantic [ 4,  4]   基线 [ 9, 11, 10]   减少约 60%
图跳过  semantic [14, 10]   基线 [ 6,  4,  6]   增加约 2 倍
```

**用不到一半的探测，换来一半的探测事故和两倍的图跳过。**

### 这条结果为什么重要

同一天早些时候测到「探测在拆跳过的台」——关掉探索后图跳过从 7 涨到 13、命中率从 57% 升到 85%。当时的解释是探测污染屏幕状态、破坏跳过依赖的行为一致性。

`GraphKeywordRanker` 给出了更精确的版本：**探测数减少 45% 而跳过增加一倍，说明破坏跳过的不是「探测」本身，而是「探错东西」**——脏状态与无谓的轨迹偏移。探到该探的地方，两个机制就不再互斥。

这是本设计里第一次把两个图机制从互相抵消变成共存，而且是在**两次独立复现里都成立**的读数。

### 尚未成立的部分

成功率没有可复现的提升。`sem` 独赢的两个任务（`ExpenseDeleteMultiple2` 13 步、`SimpleCalendarAddOneEventInTwoWeeks` 15 步）都是重复型长任务，与「图只在重访 ≥3 次的任务上有分叉信息」一致，但 `sem2` 没有在同样的任务上复现，所以这只是一个假说，不是结论。

在双方都成功的 7 个任务上配对比步数是 **6.57 vs 6.95（−0.38）**，所以至少可以排除「用步数换成功」。

## Q1：如何建图 —— 跨任务记忆的联动是负的（2026-09-10）

### 问题

app memory 是本设计对「图太稀疏」的回答：一块屏幕平均被 4.0 个任务访问，一个任务学到的东西应当留给下一个。**这从未被测过**——此前每个臂都从空存量开始，存量里只有本次跑测自己放进去的东西。

### 实验

`graph_active_suite`（37 任务），两臂只差起始存量，都用 semantic 策略：

- `warm` 从 semantic 臂跑完的存量开始（20 个 package，233 屏幕，176 转移）
- 冷启动对照直接用 `sem` / `sem2`（同配置、同套件，已有两次）

| 臂 | 成功 | 成功均步 | 探测 | 未复原 | 跳过 | 命中 | 有限熵均值 |
|---|---:|---:|---:|---:|---:|---:|---:|
| sem（冷） | 12 | 8.42 | 33 | 4 | **14** | 10 | 0.224 |
| sem2（冷） | 9 | 7.67 | 32 | 4 | **10** | 8 | 0.223 |
| **warm（播种）** | **9** | 7.67 | 23 | 4 | **5** | 3 | 0.401 |
| r1 / r2 / r3（无语义、冷） | 9 / 8 / 10 | 6.7–7.3 | 51–72 | 9–11 | 4–6 | 1–4 | 0.25–0.31 |

**结论：跨任务记忆有联动，但方向是负的。** 成功率 9 = 基线均值，没有任何收益；而它把 semantic 挣来的跳过（10–14）打回 5，也就是回到"完全没有跨任务记忆"的水平。**播种抵消了排序改进的全部机制收益，却什么也没换来。**

### 一条被证伪的机制假设，记录以免重走

观察到六个臂的「有限熵均值」与跳过数负相关（r = −0.56），且两端很干净（两个 semantic 臂熵最低跳过最多，warm 熵最高跳过最少）。机制上也讲得通：`recompute_decision_entropy` 把每一条可行出边都算进去，包括探测边和播种边——这些边说的是「这个 app 有什么可能」，不是「模型会怎么做」，而跳过门读的是熵。`seed_graph` 的注释甚至明确承诺过「Nothing that the skip gate reads is seeded」，那个承诺没有兑现。

于是实现了 `--entropy_over executed`（熵只在模型执行过的边上算，无执行边时回退到全部，保证未映射屏幕仍为 inf），并在同套件上做了受控检验：

| | 熵均值 | 熵=0 节点 | **成功** | **跳过** | 未复原 | 注入 |
|---|---:|---:|---:|---:|---:|---:|
| warm | 0.245 | 74 | 9 | 5 | 4 | 3 |
| **ent_warm（熵修复）** | **0.169** | **89** | **9** | **5** | **0** | 7 |

**修复改变了它的目标指标（熵降了、"已决"节点多了），却完全没有改变结果（成功 9=9、跳过 5=5）。假设被证伪。**

这是当天第五次「跨臂相关性在受控检验下消失」（前四次：s1a 对历史参照 −6.7σ、探索关闭按前 62 任务外推 +4.5、探测量与成功 r=−0.70、semantic 的 +3.0σ）。**这个模式本身现在是可靠结论：在这个系统里，跨臂相关几乎从不预示因果。** 任何相关性发现都必须先做受控臂再写进设计。

`--entropy_over` 保留（默认 `all` = 历史行为），因为它是一个诚实的消融开关，且实现无害；但**不要指望它改变跳过**。

### 跨 app 的部分：文献说这条路本来就难

[GUI-Xplore](https://arxiv.org/pdf/2503.17709)（CVPR'25）的问题陈述与我们的处境一致：**开发者层面的结构差异（设计选择、架构差异）导致不同 app 的交互逻辑各不相同，阻碍知识迁移**。它们的解法不是造一个跨 app 抽象层，而是每个 app 一段探索视频。

**这印证了 app memory 按 package 分文件是对的粒度**：能迁移的是跨任务（同 app 内），不是跨 app。今晚的结果进一步说明，连同 app 内的跨任务迁移，在当前实现下也是净负的。

### 抗稀疏：结构上的天花板，以及文献里唯一没试过的手段

出度 ≈ N/(N+1) 是单条轨迹的数学形状（见〈设计修订 III〉）。文献的抗稀疏手段有两类：

1. **抽象状态**（LLM-Explorer：排除文本/选中态/滚动位置后比对元素集合）——**我们已有**，`layout_signature` 做的正是这件事，且额外把重复控件折叠成种类。
2. **屏幕语义聚类**（GUI-Xplore：把屏幕聚成 `warning_screen` / `configuration_screen` 这类**类型**，节点用类型标签）——**我们没有**。它同时抗稀疏（多屏→一节点，出度自然上升）并提供一个 app 无关的可迁移层。

第 2 条是今晚唯一识别出的、未被证伪的抗稀疏方向，且我们已经有 22M 编码器可以实现它。**但在做之前必须先回答：图密度上去了，下游有没有出口。** 今晚测到的是跳过 0.3–0.7% 步数、注入 0、前瞻 0 步——密度更高的图目前没有能兑现它的机制。

## 三个问题的答案（2026-09-10 通夜实验，7 个全量级臂 + 8 个套件臂）

### Q2：如何用图历史信息增强 exploration —— **唯一站得住的正向结果**

图不能预测模型会点什么（四次独立证伪，其中均匀随机排序拿到 57/115，是历史最好之一）。图能可靠回答的是**什么已经知道了**，而那正是探索最该避开的：

```
score(候选) = sim(候选, need) − 0.5 · max_j sim(候选, 已发现标签_j)
```

关键词来自 `discovered_labels`——本节点及一跳邻居的边背后已看到的文本。打分用 22M CPU 编码器（`paraphrase-MiniLM-L6-v2`）走常驻 socket，两阶段：便宜排序器把 108 个候选收窄到 32，编码器再重排（46–87 ms，在一轮探索能承受的 ~150 ms 内）。

**37 任务套件（两次独立复现，两组与基线完全不重叠）：**

```
探测      semantic [33, 32]   基线 [51, 63, 72]   −45%
未复原             [ 4,  4]        [ 9, 11, 10]   −60%
图跳过             [14, 10]        [ 6,  4,  6]   ~2×
成功               [12,  9]        [ 9,  8, 10]   ❌ 未复现
```

**全量 116（同任务 n=110）：**

```
探测    50  vs 同配置基线 [95, 96, 101, 125]   −52%   ✅ 保持
未复原   7  vs            [11, 12, 13, 13]     −43%   ✅ 保持
跳过     7  vs            [ 4,  5, 10,  4]     持平偏高（×2 未保持）
成功    55  vs 均值 51.0 ± 2.0                 +2.0σ  ⏳ 待第二臂复现
```

**主张只能到这里：用不到一半的探测、不到一半的探测事故，达到相同或更好的结果。** 成功率的 +2.0σ 必须等第二臂——37 套件上的 +3.0σ 复现后回落到 +0.0σ，同样的错误不重犯。

### Q3：如何用图历史信息增强 reasoning —— **全部为负**

| 路径 | 测法 | 结果 |
|---|---|---|
| 蒸馏注入 | 完整消融（distill vs off，各 116） | 净差 −1，噪声内 |
| 注入形态 | AutoDroid 的 onclick（661 节点离线重放） | 触发量 1.0×，逻辑等价 |
| 注入阈值 | `min_fact_utility` 0.15→0.05（37 套件） | 注入 6.1×，成功 +0.0σ，**跳过 0.38×** |
| **语义跳过检查** | 78 个历史 skip 事件离线分析 | **符号反向**：命中的余弦 0.118，未命中 0.142 |
| 结构性跳过 | 8 个臂 | **唯一有效**：48/48 来自模型自走的边，命中率 57–85% |

语义跳过那条值得单列：任何阈值都是净亏（0.15 拦下 10/20 错的、误伤 26/34 对的）。**记住的动作标签与任务的语义相似度，对"这次跳过会不会落对"没有信息，方向还是反的。** 局限：逐步 need 未落盘，用任务名做代理；但效应不是"没有"而是"反向"，更好的 need 得把符号翻过来才行。

**Q3 的答案是：图增强推理只有结构性跳过这一条路，而且它在探索被瞄准得更好时表现更好（Q2 的 ×2）。所有基于内容/语义的增强，测到的都是 0 或负。**

### Q1：如何建图 —— 跨任务联动是负的，抗稀疏只剩一条未试

见〈Q1：如何建图〉一节。八臂对照的结论：

+ 熵修复                     8      ← 轻微有害，判负
+ 跨任务播种                 5      ← 有害，打回基线以下
基线（无语义）             4–6
成功率：八个臂全部落在 8–12，没有任何一项能动它
```

### 今晚新增的实现（默认全部关闭或行为不变，192 测试通过）

| | |
|---|---|
| `semantic_service.py` | 常驻 22M CPU 编码器，socket 协议，模型只加载一次 |
| `GraphKeywordRanker` | 唯一使用图历史指导探索的排序器 |

### 三条方法论（都是踩坑换来的）

1. **跨臂相关几乎从不预示因果。** 今晚五次全部在受控对照下消失：s1a 对历史参照 −6.7σ、探索关闭按前 62 任务外推 +4.5、探测量与成功 r=−0.70、熵与跳过 r=−0.56、semantic 在 37 套件上 +3.0σ。任何相关性发现必须先做受控臂再写进设计。

3. **臂在跑时一行代码都不改。** 违反三次，第三次崩掉 17 个任务（`UnboundLocalError: gd`，改 runner 时把赋值写在 import 之前）。告警也必须区分「已知」与「新增」，否则重复噪声会掩盖真问题。

## 节点文字化：描述从哪来、为什么缺、怎么补（2026-09-10）

节点此前只有一个哈希和一串控件标签。加一句文字描述有三个用处：注入时能说出
"这个控件通向哪里"而不是罗列标签；探索时能表示"这条路通向我已经去过的地方"；
以及区分同一 activity 下的不同状态。

### 描述的两个来源

- **推理自带（免费）**：取本步 `<THINK>` 的第一句。35% 的第一句是进度或意图
  （"I have successfully navigated to the correct date"）而不是观察，这类会被
  `_OBSERVATION` 正则拒掉——把它们存成页面描述，会误导之后落到同一屏的每个任务。
- **0.6B 补写**：42.5% 的步只发一个裸工具调用，没有任何 `<THINK>`。这些交给
  与编码器同进程的 Qwen3-0.6B，输入只有 activity 与该屏可命名控件，**不含任务**
  ——39% 的屏被不止一个任务访问，写进任务名对其余每个任务都是错的。

### 第一版提示词失败：48% 是幻觉类别

`model116` 跑到第 8 个任务被停掉。主读数不合格：

| 实际页面 | 0.6B 的描述 |
|---|---|
| Chrome 首启同意框（Accept & continue / No thanks） | "A settings page with Chrome options." |
| 录音机格式选择（M4A/WAV/3GP/44.1kHz） | "A media player with audio recording options." |
| 空的下载页 | "The main settings page."（逐字抄 few-shot 答案） |

根因在提示词本身：系统提示列举了类别（"a settings page, a media player"），
few-shot 的答案又全是光秃秃的类别名，0.6B 于是学成四分类器而不是读者。

三处修改：

1. few-shot 的每个答案必须引用自己输入里的标签，删掉类别菜单；
2. `_grounded()` 确定性守卫：句子与该屏标签没有任何实词重合就丢弃。**包名刻意
   不计入证据**——包名出现在该 app 的每一句话里，正是它让 "A settings page with
   **Chrome** options" 混过去的；
3. 描述随 app 记忆跨任务携带（见下）。

回放那 11 个失败样例：13/14 通过，0 个幻觉类别，1.15 s/次。

### 缺描述的真正原因不是模型，是写入点

`desc2` 按 (是否站上过, 是否有可命名控件) 分桶：

| 桶 | 覆盖率 |
|---|---|
| 站上过 + 有标签 | 71–74% |
| 站上过 + 无标签 | 47–54% |
| 从未站上（记忆播种 / 探测发现） | 0–22% |

抽 18 个"站上过、有标签、却没描述"的节点离线补写：**16/18 补写成功**。所以这些
节点空白不是描述器失败，而是**写入点根本没走到**——描述挂在"模型在这一屏推理过"
之后，而只被落地、被跳过、被播种、或在 bootstrap 阶段经过的节点，永远不是那一屏。

对策是 episode 结束后的补全遍：`run.py` 返回之后，不在任何关键路径上，为每个仍
无名、但有标签（自身的或入边 `discovered_labels` 的）的节点各调一次描述器。在
`desc2` 自己的图上离线回放：

**覆盖率 64% → 87%，4.3 s/任务，剩余 6% 是任何地方都没有标签的节点。**

### 跨任务：记忆是描述的载体

`AppMemory` 现在存 `description`，并且：`seed_graph` 播种出来的目标节点带上
记忆里的描述与标签（此前这一桶 0% 覆盖，而它恰好是蒸馏注入要点名的那一桶）；
`upsert` 在本节点尚无描述时回落到 `recall_description()`——这使描述在**本步
exploration 之前**就可读，而不是等到推理之后。生成守卫不变：探索读的仍是
第 *i−1* 代快照。

## 注入的漏斗：为什么它不是调参问题（2026-09-10，desc2 76 步）

| 环节 | 数量 |
|---|---|
| 当前节点有 ≥1 条出边 | 24/76（32%） |
| 原始出边 | 29 |
| 通过 `_to_fact` | 10（34%） |
| 通过 `min_fact_utility` 0.15 | **0** |

离线回放 `_to_fact` 把算术钉死：
`utility = (0.25 + need_match) × weight × (0.5 + 0.5×historical) × freshness`。
OBSERVED/SPECULATIVE 边 `weight=0.45`，在 `need_match=0` 时上限
`0.25×0.45×0.75 = 0.084`，**无论多新都够不到 0.15**；VERIFIED 边全新时 0.2375。
把 freshness 固定为 1，通过数 4/13 → 8/13。

`destination_summary` 存在 fact 上，但**不参与 `utility_score`**——所以加节点
描述改变的是渲染，不是闸门。

结论：注入的零不是阈值没调对，是**结构上没有素材**——68% 的步站在图从未离开过的
新屏幕上。而"放松阈值"这条路已经被证伪过：0.15→0.05 让注入涨 6.1 倍、成功率
0.0σ、跳过掉到 0.38 倍。

## 探索的漏斗：ranker 之前就死了（2026-09-10，desc2 88 步）

- `may_probe` 只在 30/88 步为真。绑定条件是 `--min_node_visits 2`（只探重访屏）
  与 `step >= 2`。
- 真跑起来的 30 轮里，**25 轮（83%）一个探测都没完成**，177–395 ms 就退出（有
  探测的轮 2.5–4.4 s），`probe_trace.jsonl` 里一条记录都没有——连第一个候选都没
  通过筛选（`allow_icon_only_probes` 关、探测类型只有 TAP_NAV/SCROLL、重访屏的
  `already_explored_element_identities` 已耗尽）。
- 6 个任务共 7 次探测，而每步推理约 3.9 s：并行窗口基本没用上。

**这意味着此前每一次 ranker 对照，测的都是一个只有约 10% 的步能到达的环节。**
在给出任何"图如何增强探索"的结论之前，必须先把漏斗打开——这也是 `wide` 臂
（`--min_node_visits 1 --allow_icon_only_probes --probes_per_step 5`）的由来。
重访规则本身是有代价依据的（探单次经过的屏"不付钱却背全部回滚风险"，在回滚失败
的 episode 上值 22 个点的成功率），所以 `wide` 的判定读数是安全读数。

## 相关工作对照：UI-KOBE / LLM-Explorer / KG-RAG（2026-09-10 检索）

问题一要求"阅读相关论文"。与本项目最近的一批：

**UI-KOBE**（`arXiv:2605.29534`）——离线构建 app 知识图，是目前设计上最接近的工作。
每个 UI 状态节点存：语义页面描述、结构化状态快照、参考截图、可交互元素集合、
缓存的视觉嵌入、页面上的动态值。去重是两段式：先用页面描述的嵌入检索，超过阈值
再做截图级校验，防止语义不同的屏被合并；事后还有一遍审计，用语义相似度＋参考截图
＋出边重合度找可疑节点对并合并。**"同页面不同状态"用自环边表达**，自环上带一个
schema delta，说明哪个状态变量或元素变了。跨任务可复用（图描述的是 app 的一般行为
而非任务数据），但**图是按 app 分的，没有跨 app 联动**。防稀疏靠两件事：面向覆盖率
的再探索（周期性挑欠探索节点，并重放已知转移去够到它们）与边的参数化模板。给 agent
的不是整张图，而是从当前节点出发的**一跳局部动作选项表**。
代价：**每个 app 平均 54 个节点 / 226 条边，300 步探索、3.2 小时、6.20 美元**；
AndroidWorld 上 4B 模型 70.7%。

**LLM-Explorer**（`arXiv:2505.10593`）——每个状态存的是**自然语言摘要**而不是元素
列表，靠摘要做状态抽象与合并，只在新状态上触发 LLM 调用。作者自陈的局限正是跨应用
跳转与状态共享。

**KG-RAG**（`arXiv:2509.00366`）——把碎片化的 UTG 转成"意图—轨迹"对的向量库，运行时
检索相关导航路径，是对图稀疏的另一种回答：不补图，改为检索。

**AutoDroid**（MobiCom'24）——UTG 作为 app 记忆；本文档前面已实现并证伪过它的
`onclick` 注入形式。

**对本项目的三点意义**：

1. 节点存"一句文字描述 + 元素清单"不是本项目的独创选择，而是这批工作的共识
   （UI-KOBE 的语义页面描述、LLM-Explorer 的状态摘要）。本项目此前节点只有哈希，
   是落后于 SOTA 的一项，现已补上。
2. 真正的差异在**何时建图**：UI-KOBE 每个 app 要 3.2 小时、6.20 美元的离线探索，
   MobileExplorer 把探索放进任务执行的并行窗口里，离线成本为零。这是拒稿意见里
   "贡献是什么"最应该正面回答的地方——不是"我们也有图"，而是"我们的图在零离线预算
   下建成"。
3. **跨 app 联动在这批工作里也是空白**（UI-KOBE 明确按 app 分图，LLM-Explorer 自陈
   跨应用是局限）。本项目的 `AppMemory` 同样按 package 分，所以"跨 app 是否有联动"
   的诚实答案是：目前没有，而且这不是本项目的疏漏，是这一整类方法的公开缺口。

（`arXiv:2605.29534` 与 `arXiv:2605.26546` 的编号属于本次检索返回的结果，其中
2605.26546 即 MobileExplorer 自身的预印本。）

## 三个问题的答案（修订版，2026-09-10 深夜）

前一版写于节点还只有哈希的时候。这一版把节点文字化之后的实测补上，并把两个
"机制无效"的结论从相关性降级/升级为**结构性**的、有算术依据的结论。

### 问题一：如何高效地建图

**存什么。** 节点 = `hash(activity, layout_signature)` + 可命名控件清单 +
**一句文字描述**。描述有两个来源：本步 `<THINK>` 的第一句（免费，但 35% 是进度
或意图而非观察，要用 `_OBSERVATION` 拒掉），和 Qwen3-0.6B 对那 42.5% 只发裸工具
调用的步的补写（1.15 s/次，输入只有 activity 与可命名控件，**不含任务**）。
生成的描述必须过 `_grounded()` 守卫：与该屏标签没有实词重合就丢弃，**包名不算证据**。
没有这一守卫时 48% 的描述是幻觉类别。

这与 SOTA 一致：UI-KOBE 的节点存语义页面描述 + 元素集合，LLM-Explorer 每个状态
存的就是自然语言摘要。此前 MobileExplorer 的节点只有哈希，是落后的一项。

**何时写。** 在线写入点（推理之后，就当前屏）覆盖不了只被落地、被跳过、被播种、
或 bootstrap 经过的节点——按 (是否站上过, 是否有标签) 分桶后一目了然：站上过且有
标签 73%，站上过无标签 51%，从未站上 0–35%。抽样 18 个空白节点离线补写，**16 个
补写成功**，所以空白不是描述器的问题，是写入点的问题。对策是 episode 结束后的补全
遍（`run.py` 返回之后，不在任何关键路径上）：**覆盖率 64% → 87%，4.3 s/任务**，
剩余 6% 是任何地方都没有标签的节点。

**如何防稀疏 / 跨任务。** `AppMemory` 按 package 持久化，存屏幕的标签 + 描述 +
转移。`seed_graph` 播种的目标节点带上记忆里的描述与标签；`upsert` 在本节点尚无描述
时回落到 `recall_description()`——这使描述在**本步 exploration 之前**就可读。
补全遍写回记忆，所以"这个任务只是路过的屏"是"下个任务要在上面推理的屏"。
实测跨任务存量 67%，记忆播种边随跑测线性增长（32 个任务时 57 条）。

**跨 app 呢？** 目前没有，而且这不是本项目的疏漏：UI-KOBE 明确一个 app 一张图，
LLM-Explorer 自陈跨应用状态共享是其局限。这是整类方法的公开缺口，可以在论文里
作为 limitation 诚实写出，而不是假装有。

**与 SOTA 的真正差异是何时建图。** UI-KOBE 每个 app 要 300 步探索、3.2 小时、
6.20 美元的**离线**预算，换来 AndroidWorld 4B 模型 70.7%。MobileExplorer 把探索
放进任务执行的并行窗口，**离线成本为零**。拒稿意见问"贡献是什么"，答案应当是这个，
而不是"我们也有图"。

### 问题二：如何利用图历史信息增强 exploration

**已测得为正的一项**：`GraphKeywordRanker`。
`score = sim(候选, need) − 0.5 · max_j sim(候选, 已知标签_j)`，已知标签取本节点
出边 + 一跳外的 `discovered_labels`。两个套件上都复现：探测数 −37…−45%，未复原
−36…−60%，与基线不重叠。图在这里回答的**不是**"模型接下来会按哪个控件"（这一点
被四次独立实验证伪），而是"这里已经有记录的是什么"。

**但这个结论的适用范围此前被高估了。** 2026-09-10 实测 88 步：`may_probe` 只在
30 步为真（绑定条件是 `--min_node_visits 2` 与 `step >= 2`），而真跑起来的 30 轮里
**25 轮（83%）一个探测都没完成**，177–395 ms 就退出，`probe_trace.jsonl` 里连一条
记录都没有——连第一个候选都没通过筛选。6 个任务共 7 次探测，而每步推理约 3.9 s。
**此前每一次 ranker 对照，测的都是一个只有约 10% 的步能到达的环节。**

所以在给出"图如何增强探索"的最终结论之前，先跑 `wide` 臂把漏斗打开
（`--min_node_visits 1 --allow_icon_only_probes --probes_per_step 5`），再在其上加
第二个折扣项：**走过的通路**（`--visited_discount`）。已知标签说的是"这个控件背后
已经有记录"，走过通路说的是"这条路通向我已经去过的地方"——两种不同的浪费。只取
走过的通路而不是全图，因为中途的图有 20–40 个节点而编码器按字符串数收费。
默认权重 0.0，所以已测得的 labels-only ranker 逐位不变，开启即为对照臂。

### 问题三：如何利用图历史信息增强 reasoning

**跳过（skip）是唯一活着的机制。** 许可条件：节点重访（visit_count>1）+ 边
VERIFIED + 非自环 + SAFE/LOW 风险 + `decision_entropy ≤ 阈值`。实测每次全量跑
7–13 次，命中率 57–85%。注意所有被跳过重放的边 `probe_count` 都是 0——**跳过靠的
是模型自己的重复，不是探测**，所以探测和跳过是互相拆台的（探测关掉时跳过 7→13、
命中率 57%→85%）。

**边事实注入是结构性死掉的，不是调参问题。** desc2 76 步的漏斗：

| 环节 | 数量 |
|---|---|
| 当前节点有 ≥1 条出边 | 24/76（32%） |
| 原始出边 | 29 |
| 通过 `_to_fact` | 10（34%） |
| 通过 `min_fact_utility` 0.15 | **0** |

离线回放把算术钉死：`utility = (0.25 + need_match) × weight × (0.5+0.5·historical)
× freshness`。OBSERVED/SPECULATIVE 边 `weight=0.45`，`need_match=0` 时上限
`0.25×0.45×0.75 = 0.084`，**无论多新都够不到 0.15**。而"放松阈值"这条路已被证伪：
0.15→0.05 让注入涨 6.1 倍、成功率 0.0σ、跳过掉到 0.38 倍。

根因是 68% 的步站在图从未离开过的新屏幕上——图是在 episode 内边跑边建的，节点有
出边只可能来自重访或深度 2 探测命中，而前缀对齐只有 2.5%。

**注入什么：换成走过的通路。** 既然"控件 X 通向 Y"需要出边而 68% 的步没有，就换成
一个不需要任何边、只需要节点描述的说法：**本轮已经站过的屏幕，按序命名，去重，
最近的在最后**。在 desc2 的 314 步上保守下界是 **37% 的步有内容**（对照边事实 0%），
块大小中位 50 token、最大 58，**完全落在蒸馏器已有的 64-token 预算内**。

它也是模型自己拿不到的：历史窗口只留 8 条而 48% 的 episode 超过；历史里是动作不是
屏幕身份；同一屏访问三次在历史里出现三次、在这里出现一次；而且描述可以来自之前的
任务。**只陈述记录，绝不下指令**——唯一一个"告诉模型该怎么做"的提示词块代价是
12 个任务。

**如何总结图信息。** 一次总结，两处消费：exploration 之前作为 ranker 的第二个折扣
项，reasoning 之前作为注入块。两者读的都是第 *i−1* 代快照，生成守卫不变。

## 用描述合并节点：查过，不成立（2026-09-10）

节点文字化之后一个显然的想法是用描述做去重（UI-KOBE 正是这么做的：描述嵌入检索 +
截图校验）。desc2 上同 activity + 同描述但不同 layout hash 的节点有 23 组、54 个
节点，合并可减 8% 节点数，其中一组 chrome 的两个哈希合计被访问 20 次。

两个独立理由否掉它：

1. **合并救不了那两条漏斗，因为它们是时序受限而不是拆分受限。** 注入漏斗里
   "32% 的步站在有出边的节点上"是**当步快照**（第 *i−1* 代）的数字；拿 episode
   结束时的最终图重算是 70%。差距全在时间上——边是随 episode 推进才建起来的。
   模拟合并前后，这个比例都是 70%，没有变化。
2. **提出的合并与视觉签名不符。** 这 27 对的 phash 汉明距离中位 24、最大 34，
   只有 26% 落在 ≤8 以内。UI-KOBE 的两段式第二段（参考截图校验）会把其中大多数
   否掉。13 词的标签派生描述粒度太粗，会跨真正不同的屏幕碰撞。

**所以"如何防稀疏"的答案不是合并节点，而是跨任务持久化**：AppMemory 存屏幕的
标签 + 描述 + 转移，`seed_graph` 在新任务开局就把已知转移作为 SPECULATIVE 边种下。
实测跨任务存量 68%，记忆播种边随跑测线性增长。

这条也是一次"先离线查历史分布，再决定要不要花设备时间"的应用——三分钟算完，省掉
一个 1.6 小时的臂。

## "探测伤害成功率"第四次被证明是长度混淆（2026-09-10，desc2 n=39）

按是否探测切开，表面上触目惊心：

| 子集 | 成功率 | 步数中位 |
|---|---|---|
| 有探测 | 1/9 = 11% | **15**（就是上限） |
| 零探测 | 15/30 = 50% | 9 |
| 有未复原轮 | 0/3 = 0% | — |

但这不是探测的效应，是 episode 长度的效应：

| 子集 | 成功率 | 有探测占比 |
|---|---|---|
| 长 episode（≥10 步） | 3/21 = 14% | 38% |
| 短 episode（<10 步） | 13/18 = 72% | 6% |

**探测需要重访，重访需要长 episode，而长 episode 本来就在失败。** 这与
`probes-vs-success r=−0.70` 是同一个信号，那一次在受控臂下死掉了。

这条记在这里，是为了**预先保护 `wide` 臂的解读**：`wide` 会把探测变得普遍得多，
如果那个相关性是因果的，结果会是灾难性的。`wide` 恰恰就是这件事的受控实验，
安全闸 [50,58] 会接住它。看到 `wide` 的探测数上升而成功率下降时，第一件要做的事
是按步数分层，而不是归因于探测。

## 步数的噪声底：同配置双跑相差 2 步（2026-09-10）

此前只记过成功率的噪声底（全量 σ≈2.2–2.5，翻转 8–12%），没有步数的。补上：

`sem116` 的 a、b 两次是**完全相同的配置**，115 个共同任务：

| | 成功 | 步数中位 | 翻转 |
|---|---|---|---|
| sem116/a | 57 | 7.0 | — |
| sem116/b | 55 | 9.0 | 10 (9%) |

**同配置的步数中位数就能差 2 步。**（`temperature=0` 不是逐步可复现的，这一点前面
已经单独测过。）

这条直接用上了：`desc2` 相对 `desc116` 在同 41 个任务上是成功 17 vs 20、步数中位
11 vs 9，看起来像是"描述器让 episode 变长了"。但两个差值都正好落在同配置噪声里，
而且分层后长/短 episode 内部的成功率完全一致（长 4/22 vs 4/20）。
**在 n≥80 之前不应把它读成回归。**

另外顺带排除了延迟这条因果：三个臂的推理延迟中位数是 3.37 / 3.45 / 3.35 秒，
0.6B 那 1.15 秒的描述调用不在推理关键路径上。

### 长度悬崖：本基准的一个常量

| 臂 | 总 | 长 episode（≥10 步） | 短 episode（<10 步） |
|---|---|---|---|
| desc2 (n=40) | 40% | 3/21 = 14% | 13/19 = 68% |
| desc116 (n=115) | 49% | 9/52 = 17% | 47/63 = 75% |
| sem116 (n=115) | 50% | 7/51 = 14% | 50/64 = 78% |

三个臂完全一致：**episode 一旦超过 10 步，成功率从 ~75% 掉到 ~15%**。这重新定义了
所有机制的目标——图的价值不在于"多走对一步"，而在于**让 episode 不要变长**，
而这正是 skip 在做的事。

## 统一解释：图只在 episode 已经输掉之后才有素材（2026-09-10）

把三个臂的 273 个任务、2459 个推理步放在一起：

| | 数量 | 占比 |
|---|---|---|
| 短 episode（<10 步） | 148 个任务 | 54% 的任务，**28% 的步** |
| **成功出自短 episode** | 111 / 131 | **85%** |
| 任何图机制（探测/跳过/注入）触及过的任务 | 75 | **27%** |
| 其中触及短 episode 的 | 17 | **11% 的短任务** |

**三个图机制全都需要重访**：探测要 `min_node_visits ≥ 2`，跳过要 `visit_count > 1`，
注入要当前节点有出边（而出边只可能来自重访或深度 2 命中）。而重访需要长 episode，
长 episode 的成功率只有 14–17%。

于是：**图只在 episode 已经输掉之后才有素材。** 85% 的成功出自短 episode，而图机制
只碰到其中 11%。

这一句话解释了本项目每一个零结果：
- 注入 0/76 —— 68% 的步没有出边（因为还没重访）
- 跳过只在 6% 的任务上触发，且全是长 episode（步数中位 14）
- "探测伤害成功率"的相关性 —— 探测只发生在已经在失败的长 episode 上

也解释了为什么"放松阈值/加大预算/换 ranker"这类调参一律无效：**它们调的都是一个
只有 11% 的成功来源能到达的环节。**

### 两个设计推论

1. **图要起作用，知识必须从 episode 外面带进来。** episode 内部的图在长度悬崖
   之后才变富，那时已经晚了。唯一能在短 episode 的第一步就有内容的，是**跨任务
   记忆**——这就是 `AppMemory` + `seed_graph` + 描述跨任务携带的价值所在，也是为什么
   节点文字化比注入更值得做。
2. **`wide` 臂（`--min_node_visits 1`）是第一个让图机制能碰到短 episode 的臂。**
   它的读数因此不只是"探测多了多少"，而是"图机制的可达人群从 27% 涨到多少"。
   同时它也是"探测伤害成功率"那个相关性的受控证伪实验。

### 跨任务记忆是唯一能碰到短 episode 的通道（desc2 n=45）

| 子集 | 成功率 | 记忆播种触及 | 探测/跳过/注入触及 |
|---|---|---|---|
| 短 episode（<10 步） | 67% | **52%** | 19% |
| 长 episode（≥10 步） | 17% | 62% | 42% |

短 episode 贡献 85% 的成功。**跨任务记忆播种碰到它们的频率是三个 episode 内机制的
2.7 倍**——因为播种发生在 `upsert`，不需要重访，只需要这个屏在 store 里出现过。

而且它在复利：desc2 前半 52% 的任务有播种（1.7 边/任务），后半 65%（2.7 边/任务），
store 到第 46 个任务时已有 15 个包、246 个屏、166 条转移。

这是本项目里唯一一个**随跑测变强、且能在 episode 第一步就有内容**的机制。设计的重心
应当从"episode 内怎么用图"移到"怎么把上一次的图带进这一次"——节点描述的跨任务携带、
`seed_graph` 的播种质量、以及 episode 结束后的描述补全遍，都属于这条线。

### 但边级的跨任务播种是无效的：61 条播种边，0 条被走过（desc2）

上一节说跨任务记忆是唯一能碰到短 episode 的通道。那是**触及**，不是**效果**。把
播种边的下游走一遍：

| 播种边的去处 | 结果 |
|---|---|
| 被模型真的走过 | **0 / 61** |
| 升级为 VERIFIED / REUSABLE | **0 / 61** |
| 被跳过重放 | **0** |
| 进入注入 | 不可能——SPECULATIVE 权重 0.45，效用上限 0.084 < 0.15 |
| 进入探索 ranker 的 `known_labels` 折扣 | 37/61（61%）带标签，平均 3.5 个 |

也就是说，边级播种**只剩一个活着的消费者**（探索 ranker 的已知标签折扣），而那个
消费者本身只在 30/88 的步上运行。

排查过匹配是否接错：`canonical_action` 在有 `control_key` 时只保留
`action_type / control_key / text / direction / app_name`，`probe_type` 不参与，
所以播种边和执行边的哈希本应相同。唯一一例同键双边是 markor 的文本框，
播种时输入的是探测文本、执行时输入的是任务内容，`text` 不同——那是正确行为，不是 bug。

**结论：跨任务真正能转移的不是"该按哪个控件"（那是任务相关的，所以 0/61），
而是"这一屏是什么"（任务无关的，也就是描述）。** 这正好解释了为什么 0.6B 的描述
提示词里刻意不含任务，也说明今晚把 `seed_graph` 改成携带描述与标签、而不是只播种边，
方向是对的。边可以留着喂 ranker，但不应指望它变成决策。

### 描述转移优先覆盖高流量屏（desc2 n=47）

`RememberedScreen.tasks_seen` 被声明、被序列化、被反序列化，但**从来没有被自增过**
——274 个屏全读 0，所以"这条描述是写在很多任务都会落地的屏上，还是写在没人重访的屏
上"此前无法回答。已修（一个进程就是一个任务，进程内首次触及即计一次），并补了两条
测试。

同时用各任务的图重算了一遍流量：

| | 值 |
|---|---|
| 出现过的不同屏 | 268 |
| 总落地次数（任务 × 屏） | 515 |
| 未加权描述覆盖 | 66% |
| **按流量加权的描述覆盖** | **73%** |

分层看，覆盖率随流量单调上升：仅 1 个任务落地过的屏 64%，2–3 个任务 67%，
**≥4 个任务的高流量屏 81%**。也就是说描述转移优先覆盖了最该被覆盖的屏——因为高流量
屏被更多任务站上，也就更可能碰到一次带 `<THINK>` 的推理。

另外，268 个屏里有 99 个（37%）被不止一个任务落地，与代码注释里长期引用的 39%
（另一次跑测算出的）一致。

## 失败的真正构成：65% 是"没跑完"，而图救不了它（2026-09-10，三臂 279 任务）

比"长度悬崖"更锋利的切法是**是否宣布完成**：

| | 数量 | 成功率 |
|---|---|---|
| 宣布完成（`status`） | 184（66%） | **72%** |
| **从未宣布完成** | 95（34%） | **0%** |

未宣布完成的 95 个里，**83 个（87%）正好打到 15 步上限**。失败总数 147 个，其中
**未终止占 65%**，终止但答错只占 35%。

也就是说：**模型只要能跑完，就有 72% 的正确率；跑不完则必输。** 整个失败模式是
"15 步之内没结束"，不是"想错了"。

顺带纠正一个我自己先下的错误判断：短 episode 的 8 个失败全部以 `status` 结尾，看起来
像"过早宣布完成"。但按"第几步宣布完成"分层后成功率是平的（≤2 步 64%、3–4 步 73%、
5–7 步 74%、≥8 步 71%）——**宣布得早不是失败信号**，真正的信号是从不宣布。

### 那么"省步数"能救回多少

skip 是唯一直接省步的机制（一次跳过 = 少一次推理）。在那 95 个打满上限的 episode 里
统计"同屏同控件重复执行"的步：

- 合计 1409 步，其中重复步 **173（12%）**，平均每任务 **1.8 步**

**所以即使 skip 完美命中所有重复，每个卡住的任务也只能拿回约 1.8 步**，而它们距离
完成的缺口多半大于这个数。而且重复本身可能意味着模型在原地打转——更快到达同一个
死胡同，并不等于完成。

### 对论文的直接含义

**图解决不了主导失败模式，所以不应该拿成功率来卖它。** 诚实且有证据支撑的卖点是
论文标题本来就写着的那个：*Accelerating* On-Device Inference——

- **同等成功率下更少的推理调用**（已测：渐进式记忆复用 17/40 vs 16/40，推理调用少 14.5%）
- **零离线预算**（对照 UI-KOBE 每个 app 3.2 小时 / $6.20 才换到 70.7%）

今晚所有的零结果都指向同一件事：**过去把图往成功率上推的方向选错了。** 把主张收回到
"加速 + 零离线成本"，既与数据一致，也正好回答"贡献是什么"。

## 用小模型直接选探索元素（2026-09-11）

设计改为：搜索前，把**任务 + 当前页面所有可交互元素（带 a11y 信息）**一次性交给
0.6B，让它直接选要探索哪个。提示词形状：

```
Task: Find flights from Hong Kong to Paris.
Origin, destination, date, passenger count, and class are already correct.
The next unfinished step is to submit the search without editing those fields.

Candidate control labels, in arbitrary order:
- Departure airport/city Hong Kong
- ...
- Search
```

**a11y 标签**取 `content_desc` + `text` 拼接——一个控件常把字段名放在描述里、值放在
文本里（"Departure airport/city" + "Hong Kong"），单看任一个都有歧义；两者皆空时
回落到 `resource_id` 末段并把 `_-.` 打开成词，所以纯图标控件也能进候选。

**进度陈述取自第 i−1 代**：上一步站过那屏的描述 + 解析出的 need，绝不碰本步推理。

### 位置偏置：这次过了

同一个模型上一次做元素排序时败在位置偏置（2/11，不如均匀随机的 10/11）。这次跑测前
先离线复验：把正确答案轮流放到每一个位置，**15/15 全中，被选中的位置分布 3/3/3/3/3
完全均匀**（均匀随机基线 20%）。三处不同：提示词带任务与进度陈述而不是一个 need 短语；
few-shot 的答案分布在四个不同位置；候选每次按屏幕自身标签集为种子打乱。

### 两次启动，两次停机

**第一次**（1 个任务后停）：探索轮跑 2.9–4.0 秒、完成 **0 次**探测。`_pick` 每尝试
一次探测就重排一次，每次重排付一次 0.6–0.8 秒的模型调用，三次吃光 `auto` 预算
（≈3.4 秒）。修法：**按屏缓存**——两次重排之间屏幕没变，答案就没变。

**第二次**（2 个任务后停）：选择器被问 5 轮只出手 1 轮，而离线用干净的两候选屏复现
5/5 全中。排查掉的假设：不是超时（真机竞争下中位 0.44 秒、最大 0.56 秒，客户端超时
4 秒）；不是空白规范化（2544 个有名字的元素里只有 1 个带不规则空白）。**真正的问题是
仪表**：`llm_choice=""` 分不清"标签集太差"和"模型答了一句话"。补上：服务把**原始
回复**一并返回，轮级事件记下**实际候选标签**。

### 探索漏斗的堵点（`wide` 上 1594 个被丢弃的候选）

| 原因 | 占比 |
|---|---|
| `no_semantic_identifier`（无文本、无描述、无 resource_id） | **52%** |
| `action_button_requires_semantic_inverse`（按钮且不知如何撤销） | **30%** |
| 其余三条 | 18% |

这两条都是安全规则而非疏漏：第一类根本没有任何东西能命名（`a11y_label` 回落到
resource_id 也救不了），第二类放开就是那个有 22 个点成功率代价的回滚风险。所以
**选择器的作用域是给幸存候选排序**，判据据此定死，不动过滤器。

### 推理侧：同一个模型把图压成一行

`--graph_context llm` 把走过的通路交给同一个 0.6B 压成一行。真机实测：

```
step=5   9 tokens   [Memory] Started recording audio and reached the 'Recording...' status.
step=6   9 tokens   [Memory] Started recording and reached the 'New name' dialog.
```

对照确定式块 42–58 token，**压缩约 5 倍**，同样过 `_grounded` 守卫（不能被走过的屏
支撑就丢弃）。行数不足 2 时回落到确定式块。

**skip 只记录不闸门**：store 预测模型下一个控件的准确率是 82%，对注入很高（前瞻对齐
只有 2.5%），但对 skip 太低——skip 不验证就提交动作，5 次错 1 次，在 15 步上限面前
是灾难（阈值扫描见前文，一致率在 81–86% 之间平坦，加证据只缩小池子）。

## 小模型选元素：机制成立，结果为负（2026-09-11，全量 116）

`llm` 臂 = 选择器 + LLM 压缩注入 + 放宽探索。同 115 任务：

| 臂 | 成功 | 调用/任务 | 探测 | 未复原 |
|---|---|---|---|---|
| desc116 | 56 | 8.89 | 62 | 8 |
| sem116 | 57 | 8.84 | 50 | 7 |
| desc2 | 52 | 9.03 | 66 | 9 |
| wide | 56 | 8.77 | 86 | 6 |
| **path**（走过通路注入） | **59** | 8.91 | 52 | 8 |
| **llm**（选择器 + 压缩注入） | **52** | 9.42 | **125** | **11** |

**选择器本身完全达标**：268 轮里出手 252（94%），每一个答案都解析回屏上真实存在的
控件，**100% 改变了基础排序**，平均把控件从第 3.7 名提到第 1 名，探测数 52 → 125
（+140%）。弃权样本也合理：候选是 `['Share','More options','gestures view','view
pager']` 时模型回 `'Add'`，屏上没有，守卫拦下。

**但 llm vs path 翻转 21：得 7、丢 14，净 −7**，超出 ±2 噪声底。丢掉的任务上 llm
探测 17 次、path 7 次；未复原轮 11（全场最高），而有未复原轮的任务成功率 36%、
无的 46%。

### 这个对照是脏的，正在拆

`llm` 相对 `path` 一次改了四处（策略、注入形式、`min_node_visits 2→1`、允许纯图标）。
`wide` 含后两项而用旧策略拿了 56，所以放宽本身不是主因。剩下两个嫌疑：

- **(a)** 选择器让探索变多，而更多探索伤成功率；
- **(b)** path 的 59 来自**走过通路那 50 token 的完整块**，压成 9 token 一行把起作用的
  东西丢掉了。

`choose` 臂固定 (b)（保留 `distill_path`、`min_node_visits 2`、不开纯图标），只改探索
策略一处，判据：成功率落在 **[57, 61]** 就说明选择器不是那 7 个任务的原因。

### 四次停机各修掉一个独立缺陷

1. `_pick` 每次重排都付一次模型调用 → 轮时长 2.9–4.0 秒、零探测 → **按屏缓存**
2. 弃权是空字符串，分不清"标签集差"和"模型答了一句话" → **服务回传原始回复**
3. 缓存键是"当前候选集"，每次重试都失效 → 键改成**"这一屏"**（轮时长 2689→603ms）
4. `last_*` 每次 `rank()` 都重置，而最后一次调用候选最贫瘠 → 13 个确实问过的轮全被
   记成"从没问过" → **按轮粘住**

第 2 条尤其值得记：**一个只会返回空值的机制，和一个根本没被调用的机制，在日志里
长得一模一样。** 这是本项目第二次栽在这上面（第一次是 bfloat16-on-MPS 让描述器静默
失败，看起来像"这屏没有可命名控件"）。

## 选择器的隔离判定：不成立，但归因不是我先想的那个（2026-09-11）

`choose` 臂 = `path` 的配置，只改探索策略一处。同 114 任务：

| 臂 | 成功 | 调用/任务 | 探测 | 未复原 |
|---|---|---|---|---|
| **path** | **59** | 8.87 | 51 | 8 |
| **choose**（只换 `--exploration_policy llm_choice`） | **49** | 8.88 | 83 | **7** |
| llm（四处同改） | 52 | 9.37 | 123 | 11 |

翻转 16：得 3、丢 13。**未复原轮 7 vs 8——回滚健康度没变**，所以不是"探测把设备
弄脏了"。

### 我先给出的解释被自己的数据否掉了

先看到的是：选择器最常选 `Delete`（16 次）、`New Recipe`（12）、`Shutter`（4）——
全是推进任务的动作控件。于是解释成"探索去按了会改变世界的控件，回滚看起来成功但
任务状态已经前进了"。听起来很有说服力，而且方向也对：那 21 个被选过危险控件的任务，
`path` 上 43% → `choose` 上 33%。

**但逐任务归因只支持其中约 2 个。** 丢掉的 13 个任务里：

- 选择器**出手过的只有 4 个**
- **真的探测过的只有 1 个**（`RecipeDeleteMultipleRecipes`）
- **7 个是"跑不完打满 15 步"**

```
NotesIsTodo                    出手 0 探测 0  步 3→1    完成
SystemBluetoothTurnOn          出手 0 探测 0  步 6→15   未完成
SportsTrackerActivitiesCount…  出手 0 探测 0  步 2→15   未完成
TurnOffWifiAndTurnOnBluetooth  出手 0 探测 0  步 9→15   未完成
RecipeDeleteMultipleRecipes    出手 7 探测 6  步 15→15  未完成   ← 唯一真探测过的
```

**选择器在 9 个损失上根本没动过手。** 剩下的可能是跑测方差（16/114 = 14% 翻转率，
在 8–12% 带子的上沿），也可能**通过共享的 `app_memory` store 间接起作用**——选择器
改变了探测什么，store 就分叉，后面每个任务的起点也就不同。3 比 13 在纯对称噪声下
概率约 1%，所以不宜全归给方差；但**直接归因不成立**，这一条必须诚实写清。

### 记下方法论

一个看起来机制上完美的负结果（94% 出手、100% 改变排序、探测 +63%、平均从第 3.1 名
提到第 1 名），其损失里有 9/13 的任务它压根没参与。**"机制 X 变了、结果变差了"
不等于"机制 X 造成了变差"，哪怕 X 的每一项机械读数都达标。** 逐任务问一句"X 在这个
任务上到底动过手吗"，三分钟就能拆掉一个看起来严丝合缝的因果故事。

### 所以现在的结论

- **推理侧（`path`，注入走过的通路）是整晚唯一的正向结果**，59/115。
- **探索侧的选择器不被支持**，且它不是 `llm` 臂那 7 个损失的直接原因。
- 下一步不是继续拆选择器，而是**复验 59**：`path2` 同配置复跑，判据 ≥57。

## 噪声底不是 ±2，是 ±10：复跑复现了归给机制的全部代价（2026-09-11）

`path2` 是 `path` 的逐字复跑——同配置、同代码、一行没改：

|---|---|---|---|---|

**签名完全一样。** 归给选择器的那 −10，把代码一行不改重跑一遍同样出现。

一对，用它当噪声底是错的。

### 七个臂 × 114 任务：68% 的任务是基准自己决定的

| 有几个臂成功 | 任务数 |
|---|---|
| 0/7（全败） | **43** |
| 1–6/7 | 37 |
| 7/7（全胜） | **34** |

**稳定任务 77/114 = 68%，对任何机制差异贡献恒为零，却占掉每次跑测 68% 的时间。**

单臂成功数标准差 ≈ 3.0，**两臂之差的 95% 区间 ≈ ±8 个任务**。

### 直接后果

**n=115 单跑下，小于约 8 个任务的成功率差异读不出来**——这覆盖了本次会话报告过的
每一个机制结果：path 59「最佳配置」、选择器 −10、desc2 −4、wide +4、llm −7。
全部作废。

**不受影响的是臂内部的读数**：推理调用数、注入覆盖、描述覆盖、探测效率、选择器
命中率（34% vs 旧 ranker 的 2.5%），以及所有离线回放得出的结构性结论（注入漏斗的
算术、skip 的 1.9% 天花板、85% 的成功出自短 episode）。

### 易变任务套件

`configs/volatile_suite.json` / `results/mobileexplorer_runs/tasks_volatile.txt`
存下那 37 个任务。**一个臂从 2.3 小时降到约 45 分钟，信号一点不少**——因为信号本来
就只在这 37 个里。七个臂在这个套件上的得分：desc116 22、sem116 23、wide 22、
path 25、path2 15、llm 18、choose 15，与全量排序一致。

## 转向检索：语料质量是瓶颈，不是检索算法（2026-09-11）

放弃 LLM 总结那条线之后，问题变成"如何从图里提取有用信息"。先量机会，再动手。

### 机会在持久 store，不在 episode 图

沿 2327 个真实步：

| | 占比 |
|---|---|
| 当前屏在持久 store 里 | **86%** |
| 且该屏有已知出转移 | **55%** |
| 对照：episode 图当前节点有出边 | 32%（且是拿最终图算的，实时快照更低） |

### 多跳搜索没用，1 跳检索才是机会

| | 占比 |
|---|---|
| 1 跳内可达与目标相关的屏 | **22%** |
| 3 跳内可达 | 24% |

转移图 241 个屏 / 320 条边，**平均每屏 1.3 条出边**——太稀疏，多跳走不动。

### 检索排序本身也没有价值

用已在跑的 22M 编码器按任务目标给当前屏的已知转移排序：

| | 值 |
|---|---|
| top-1 命中模型按过的控件 | 40% |
| **随机基线** | **38%** |

**编码器只贡献 2 个点**，因为候选集本来就只有 2–3 个。所以这个机制**刻意不排序**。

### 真正的瓶颈：三分之一的事实是错的

| | 值 |
|---|---|
| 描述被输入法污染的屏 | 55/453 = 12%（一句"A screen with More features, Sticker Keyboard…"站在 **23 个不同的屏**上） |
| **落点是输入法屏的转移** | **103/321 = 32%** ← 这些事实是错的 |
| 控件名只有 resource_id | 122/321 = 38% |
| **真正可用的事实** | **119/321 = 37%** |

污染是跨包的：48 个受影响的屏分布在 8 个不同 app 上，activity 都属于被测应用而标签
来自键盘。`_actionable_labels` 此前**完全不过滤**，而它正是喂给描述器的东西。

**修法是结构性的**：描述一屏时只用 `package` 等于前台包的元素——一条规则同时排掉
键盘、状态栏和系统遮罩，不需要任何 app 专属列表。离线估算：可用事实 **37% → 58%**
（+64 条），且没有任何节点因此变成无标签。

### `--graph_context store` / `store_path`

读持久 store，以落点为主语渲染，三个刻意的选择都有测量依据：不排序（编码器只值
2 个点）；以落点为主语（控件名 38% 只有 resource_id，落点 92% 有真句子）；**丢弃
而非降级**（控件无名或落点无描述就整条不说——错的事实比没有事实更糟）。

离线在真实轨迹上：**34% 的步有可注入事实**（对照边事实注入 0/76），块大小中位
**25 token**，最大 61，在蒸馏器已有的 64 预算内。

判定用配对设计：`pair_base`（走过通路）vs `pair_store`（走过通路 + store 检索），
两臂从**同一份冻结 store** 起步、交替运行、只跑 37 个易变任务。因为同配置离散度是
±10，成功率单跑比大小读不出来；主读数是臂内的注入覆盖率与事实正确率。

## 成功率不可复现，机制读数可复现（2026-09-12）

`m_full` 同配置跑两次，37 个易变任务：

|---|---|---|---|
| **成功率（任务数）** | 23 | 15 | **35%** |
| 推理步数 | 323 | 334 | 3% |
| 注入覆盖率 | 100% | 100% | **0%** |
| 注入块中位 token | 51 | 51 | **0%** |
| 图跳过 | 2 | 2 | **0%** |
| 提示表跳过 | 28 | 28 | **0%** |

那 8 分的摆动**覆盖了同一天七臂消融的整个全距（17–23）**，所以那次消融的排序不含

**所以本项目每一个基于成功率的跨臂结论都落在噪声内**，包括"path 59 是最佳配置"、

## 最终设计与判定（2026-09-12/13）

### 结果：加速成立，成功率不成立

完整设计 vs 完全不建图，各三轮，37 个易变任务，交替运行，同一份冻结语料起步：

| 读数 | 完整设计 | 完全不建图 | 差 | σ |
|---|---|---|---|---|
| 成功任务数 | 17.7 ±1.53 | 19.3 ±1.53 | −1.67 | **1.3σ 读不出** |
| **成功任务均步** | **7.39 ±0.25** | 7.94 ±0.13 | **−0.55** | **3.4σ** |
| **图省下的推理调用** | **15.3 ±1.53** | 0.0 | **+15.3** | **17.4σ** |

逐轮成功任务均步 `[7.50, 7.56, 7.11]` 对 `[8.10, 7.89, 7.84]`——**三轮全部低于对照**。
改造前图只省 2 次推理调用（硬编码提示表省 28），现在图省 15.3。

### 让 87% 的预测变得可用的那个设计决定

现有 skip **替代**推理：猜错废掉一步，而历史上每个出现误跳的任务在两次跑测里都输。
**预填改成执行之后仍然跑这一步的推理**——与第 0 步开 app 同一个模式。猜错只多一个
可撤销的动作，**不花步数预算**。代价从"丢一步"降到"多一个动作"，87% 就够用。

门控全部来自实测（116 任务）：

| 门控 | 机会 | 准确率 |
|---|---|---|
| **本集这屏只按过一个控件（≥1 次）** | **115** | **83%** |
| 本集执行过 ≥2 次 | 45 | 93% |
| **store 唯一已知控件 + ≥2 个任务** | **39** | **87%** |
| store 唯一已知控件 + ≥1 个任务 | 119 | 71% |
| 最常执行的控件（放弃唯一性） | 108–182 | **54–58%** |

唯一性是信号的全部来源。链式最多三跳、每跳先验证落点再走下一跳（59% 的已决定屏
通向另一个已决定屏，可折叠步数 39→64；87% 单跳复合两跳是 76%，不验证会失控）。

### 一条贯穿全部结果的规律

**给模型更多信息（注入）一律无正收益；替模型省掉决策（预填/跳过）有 3.4σ 收益。**

注入试过五种形式全部失败：边事实（结构性为零，0/76）、AutoDroid 的 onclick、
走过通路（97% 覆盖）、store 检索（36% 覆盖）、元素清单（30% 覆盖）。七臂消融里
**不注入的臂均值最高**（20.5，且两次摆动只有 1）。破环提示是第六种，同样无收益
（m_loop 7.50 对 m_final 7.22）。

### 为什么 58/116 到不了——算术，不是调参

77 个稳定任务贡献 34 胜，所以 58 需要易变套件拿 24。实测分布 14–23（唯一一次 25
未能复现，复跑 15）。而打满 15 步未完成的 94 个 episode：

| | 值 |
|---|---|
| 重复步数**中位** | **0** |
| 重复步数均值 | 1.7 |
| **每一步动作都不同的** | **50/94 = 53%** |
| 明显打转的（有边执行 ≥4 次） | 11/94 = 12%，各浪费 7.9 步 |

**过半的失败不是浪费，是不够。** 图能回收的均值 1.7 步小于缺口。

### 论文应当主张的

不是"图提升成功率"，而是**在成功率不劣的前提下**：

- 成功任务少走 **0.55 步（−6.9%）**，3.4σ
- 图省下 **15.3 次推理调用**（改造前 2 次），17.4σ
- 节点描述覆盖 **37% → 88–90%**，观察式合格率 100%
- 检索注入素材 **0/76 → 36% 的步**
- **离线成本为零**（对照 UI-KOBE 每 app 300 步 / 3.2 小时 / 6.20 美元换 70.7%）

同一次跑测里，加速的信噪比是 **3.4**，成功率是 **1.3**。这个差距本身就是主要发现。

## 一刀切 15 步是整晚最大的测量错误（2026-09-13）

`android_world/suite_utils.py:525` —— **官方步数预算是 `10 × task_complexity`**，
而此前每一个臂都跑在 `--max_steps 15`。三个分组的官方预算：

| 分组 | n | 官方预算中位 | >15 步 | ≥30 步 |
|---|---|---|---|---|
| **全败（0/7 个臂）** | 43 | **22** | **31（72%）** | **18（42%）** |
| 易变（1–6/7） | 37 | 10 | 12（32%） | 2（5%） |
| 全胜（7/7） | 34 | 10 | 5（15%） | 1（3%） |

```
OsmAndTrack                  官方 120 步   给了 15
MarkorMergeNotes             官方  78 步   给了 15
ExpenseAddMultiple           官方  60 步   给了 15
RecipeAddMultipleRecipes     官方  60 步   给了 15   （共九个 50–78 步的任务）
```

**"全败"这一组几乎就是"高复杂度"这一组。** 那 43 个任务不是不可能，是被饿死了
步数——而我把它们当成常量，在此基础上推出"58/116 算术上到不了"。这个推论作废。

同样受影响的还有：「65% 的失败是没跑完」「打满上限的 episode 里重复步数中位为 0，
过半每一步都不同，所以是不够而不是浪费」——这些描述的是 15 步下的现象，不是基准
本身的性质。

**改用 `--max_steps 0`（交回 AndroidWorld 自己的预算）重跑全量 116。**

### 预填省下的推理调用是 0，不是 52

```
预填触发的步数           46
其中仍然调用了推理的步数   46   ← 全部
```

预填是穿透式的：点一下，然后照常跑这一步的推理。此前"图省下 52/54 次推理调用"
的说法把预填事件当成了跳过事件——**预填一次调用都没省**，它省的是步数（一步里
完成两个动作），而步数上 9.87 对 9.86，也没省。

### 61 vs 58 是噪声

| | n | 精简 | 不建图 | Δ |
|---|---|---|---|---|
| 预填触发 | 34 | 10 (29%) / 16.21 步 | 9 (26%) / 15.71 步 | +1 |
| **预填未触发** | **81** | **51 (63%) / 7.21 步** | **49 (60%) / 7.41 步** | **+2** |

+3 里的 +2 落在**两个臂配置完全相同**的 81 个任务上。翻转总数 7 赢 4 输。
结论：`full_lean ≡ full_nograph`。

## 为什么按屏幕检索必然失败：66% 不是 87%（2026-09-13）

留一法复盘，115 个任务、419 个真实执行过的转移，问"store 会不会给出模型实际
选的那个控件"：

| 门控 | 覆盖 | 命中 | 对 / 错 | 净 |
|---|---|---|---|---|
| 唯一控件 min_tasks=2 | 17% | **90%** | 66 / 7 | +59 |
| 按屏幕多数票 | 45% | **66%** | 125 / 65 | +59 |
| 目标 kNN (k=3, thr=0.5, margin=0.6) | 42% | **84%** | 147 / 29 | +118 |
| **两者并集** | **44%** | **84%** | **154 / 30** | **+124** |

此前记的 87% 是**唯一控件门控在它自己那 17% 上的命中率**（39/45），不是检索的
命中率。放宽到整块屏幕就掉到 66%——同一块屏幕上不同任务要去不同地方，按屏幕
投票必然被稀释。125 次免费跳被 65 次错点抵消，这就是端到端为零的算术来源。

**区分两种情况的不是屏幕，是任务。** 改问"目标和我最像的那批任务在这儿点了
什么"，同样覆盖下错点减半。相似度加权投票 + 冠亚军边际拒答（近似平局正是屏幕
投票出错的那一类：margin 0.0→76%，0.3→82%，0.6→84%，1.0→86%）。

冷启动（只看字母序在前的任务，不预置 store）下同一组对照：

| 检索方式 | 覆盖 | 命中 | 免费动作 | 错点 |
|---|---|---|---|---|
| 按屏幕多数票 | 46% | 60% | — | 78 |
| 目标 kNN thr=0.4 margin=0.6 | 34% | 76% | 104 | 34 |

**冷启动是必须的**：`corpus/a_store` 是同样这 116 个任务跑出来的，任务模板会以
0.95 的相似度命中自己。`retrieve_control` 另外硬性排除与本任务目标原文完全相同
的记录。

## 落点判定用 layout 签名是错的：66% vs 96%（2026-09-13）

同一 (屏幕, 控件) 被多个任务执行时，落点：

```
layout_signature 相同   315/480 = 66%
activity 相同           461/480 = 96%
```

运行时的 `matched` 用的是签名精确相等，**三分之一的正确跳被判成错**。后果有两个：
链式预填被过早掐断（这解释了为什么 max_prefill=3 从来没兑现过），以及加上回退
之后会**把正确的动作撤销掉**。改为按 activity 判定，并补一条"落点等于出发点即
未命中"的保护——activity 天然不变会让一次什么都没做的点击看起来像命中，那正是
replay loop 的入口。

## 探测的风险门砍掉 59% 的可预填边（2026-09-13）

`_risk_of` 是为探测写的：探测是投机动作，必须能 Back 撤销。用在预填上：

```
总执行边 419
  通过        172 (41%)
  无名字→拒    175 (42%)   有 resource_id，只是没有 text/content_desc
  Button类→拒   72 (17%)
```

预填不是投机：store 里只有真实任务点过、且落在同一 app 内的控件
（`observe_execution` 会丢弃跳出 app 的转移），落点还会被核对、不符会回退。
`_prefill_risk_of(mode="loose")` 只保留"带 checked 态的控件在切换状态而非导航"
这一条结构性拒绝。

## 引导后立即预填：唯一能够到 app 主屏的调用点（2026-09-13）

step 0 原本是 `open_app` + 在 app 主屏上跑推理，第一次导航要等到 step 1。而
**app 主屏是 store 覆盖最好的屏幕**——这个 app 里每个任务都站在上面。冷启动、
112 个任务，只问每个任务的第一个 app 内执行步：

```
store 能答 53/112 = 47%   答对 40 = 75%    （全屏平均 34% / 76%）
```

多省 40 步。`--prefill_after_bootstrap`。

## 省步数换不来成功率（2026-09-13）

```
成功 58 个   均 6.41 步
失败 57 个   均 13.37 步   其中耗尽预算（未主动终止）仅 17 个 = 30%
```

**70% 的失败是主动终止在错的地方**，多给步数救不回来。所以这套设计要卖的是
"成功率持平 + 步数显著下降"，不是"步数下降带来成功率上升"。头条指标应是
**成功 episode 的平均步数**（全任务均步被失败任务主导：67% 的步数烧在失败上）。
按 full_nograph h1 的真实轨迹投影，暖 store 下 6.61 → 5.16（−22%，56 个成功
任务里 44 个受益）。

## 预填来源必须拆开量：episode 30%，goal 88%（2026-09-13，线上 50 个任务）

第一次跑目标检索版时整体命中率只有 59%，配对上预填触发的 34 个任务 **10 对 18，
输 8 个**。按来源拆开之后原因是唯一的：

| 来源 | 落点命中 | 占全部跳 |
|---|---|---|
| **episode**（本轮已在该节点执行过唯一控件） | **9/30 = 30%** | 51% |
| **goal**（目标 kNN 检索） | **23/26 = 88%** | 44% |
| unique（唯一控件门控） | 3/3 = 100% | 5% |

**目标检索线上 88%，比离线冷启动预测的 76% 还好。** 拖垮整个臂的是 episode：
它的 83% 是在旧的签名规则下、在另一个总体上量的；而且代码里它不设
`expected_activity`，落点判定回落到 `node_id` —— 又是今天证明只有 66% 可靠的
那条签名规则。回退统计也被它带偏：24 次回退只有 7 次复位成功，因为大量 "miss"
其实是误判，Back 把本来正确的屏幕推走了。

`--prefill_sources` 默认改为 `store`，episode 降级为消融项。

**方法教训（与"只有同 session 的臂可读"同级）：一个由多个来源合成的机制，
整体命中率是没有意义的读数。** 59% 这个数字既不指向修法也不指向废弃；拆成
30/88/100 之后修法是唯一的。

## 控件键太严：`control_absent` 拒的次数比成功跳还多

控件键是 `resource_id|text|content_desc|class` 四段全等。标签里带计数或日期的
按钮跨屏就对不上自己：50 个任务里 `control_absent` 拒绝 **43** 次，而成功跳只有
29 次。同屏 resource_id 唯一的元素占 **97%**，所以在唯一性成立时回退到只匹配
resource_id（`--prefill_by_resource_id`），并在拒绝日志里记 `resource_id_seen`
以便下一轮直接量出回退救回了多少。

## 负结果：按 activity 索引 store 更差（2026-09-13）

layout 签名只有 66% 稳定，直觉上应该按 96% 稳定的 activity 来索引 store，让同一
屏幕的证据不被拆散。实测（冷启动，419 个执行步）**反过来**：

| 索引键 | 覆盖 | 命中 | 免费动作 | 错点 |
|---|---|---|---|---|
| layout 签名（现行） | 34% | **76%** | 104 | 34 |
| activity | 19% | **53%** | 43 | 38 |

一个 activity 下平均挂 5.6 个不同签名的屏幕（中位 4，最多 22）。签名随内容变化
这件事，在**落点核对**时是噪声，在**检索索引**时是信号：它区分得开"十月的月视图"
和"事件编辑表单"，而 activity 把两者混成一堆——唯一性门控几乎不再成立，边际门
被一堆竞争候选顶掉，覆盖和命中同时下降。

**同一个字段，在两个位置的正确用法相反。** 索引用签名，核对用 activity。

## Q2 的直接读数：exploration 元素选择正确率的完整阶梯（2026-09-13）

在"该屏幕上模型实际按下的是哪个控件"这一个问题上，各种做法的正确率：

| 做法 | 正确率 | 来源 |
|---|---|---|
| 随机选一个可点元素 | **19.3%** | 454 个源屏幕，均值 1/n（中位 8 个可点元素） |
| 本轮 episode 局部重复 | **30%** | 线上 9/30 |
| 按屏幕多数票 | **60–66%** | 冷启动 / 留一法，419 步 |
| **目标条件 kNN 检索** | **84–88%** | 离线留一法 84%，线上 23/26 = 88% |
| 唯一控件门控（覆盖只有 17%） | **90–100%** | 离线 66/73，线上 3/3 |

**这就是 Q2 的答案本身**：图历史增强 exploration 的有效形式不是"给探索排序"
（此前 GraphKeywordRanker 之外的排序尝试全部证否），而是**在图历史足够确定时直接
替模型执行那一步**，把 19.3% 的随机基线抬到 88%。而且它必须以任务目标为条件——
不以目标为条件就只有 60–66%，端到端净收益为零。

## 第一个达到目标形状的读数（2026-09-13，29 个任务中段）

冷启动、官方步数预算、来源只用 store：

| | n | 新设计 | 不建图 | Δ |
|---|---|---|---|---|
| **预填触发** | 14 | 9 (64%) / **9.00 步** | 9 (64%) / **11.07 步** | 成功 ±0，**步数 −2.07（−19%）** |
| 预填未触发 | 15 | 5 (33%) / 10.93 步 | 5 (33%) / 10.40 步 | ±0，+0.53（配置相同，噪声） |

**成功率完全持平（14 对 14），预填触发的任务上步数降 19%。** 这是整个 session
第一次同时满足"成功率不掉"和"步数明显下降"。

机制读数：预填命中 17/19 = **89%**；来源 goal 16 / unique 3 / episode 0；
**16/19 = 84% 的跳在旧的签名规则下会被判成错**；`control_absent` 从 43 次降到 4 次
（resource_id 唯一性回退匹配生效）。

### 顺带修掉的状态破坏缺陷

"落点等于出发点即未命中"这条保护会连带触发回退。29 个任务里出现 2 次，两次的
**期望 activity 都已经到达**——点击只是没有改变 layout 签名。Back 于是把 agent
从一个正确的屏幕上导航走了。改为：仍判未命中（防止链式预填在原地空转），但不
回退。屏幕没变就没有东西需要撤销。

## 这次的对照设计自带阴性对照（2026-09-13）

整个 session 反复吃亏的地方是"跨臂相关几乎从不预示因果"。这次的配对拆分把
阴性对照内建进了同一次运行：

- **预填触发层**：两个臂在这里唯一的区别就是机制本身。
- **预填未触发层**：两个臂**配置完全相同**——store 没有答案，代码路径一致。
  这一层的任何差异都是模拟器漂移或基准方差，不可能是机制。

29 个任务时：未触发层 5 对 5、步数 +0.53（≈0），触发层 9 对 9、步数 −2.07。
**阴性对照近乎为零，所以触发层的差值可以归给机制。** 这比"同一配置跑两轮取
均值"强，因为它把两层放在同一次运行的同一段时间里。

所有对照臂都在 2026-09-13 同一天、同一台模拟器上跑完（不建图 05:13–11:23，
精简 12:43–14:46，目标检索版 18:17 起），满足[[只有同 session 的臂可读]]。

## 分母错了：84% 其实是 36%（2026-09-13）

到 44 个任务时，目标检索版在输：预填触发的 24 个任务 8 对 12（−4），两边都成功
的 15 个任务上还慢 5%。而机制读数一切正常——落点命中率 90%。

用配对的无图基线做裁判（"预填按的控件，同一任务在没有预填时按过吗"）：

```
落点命中率（我一直在报的）    90%
动作正确率（真正要的）        43%
```

再把离线评测的分母修正过来，问题就完全清楚了。此前的留一法只在**"模型确实
点击导航了"的 419 步**上打分，而线上预填在**任何 store 有答案的屏幕**上都会
开火。按屏幕访问重新统计：

```
屏幕访问总数 927，其中发生点击导航的 402 = 43%
→ 剩下 57% 的步模型在打字、滑动、终止，那些步上任何预填都是错的
```

无偏重算：**开火 291 次，正确 36%，104 对 / 187 错，净 −83。**

### 修法：通过率门控

store 里已有 `tasks_seen`（站过这块屏幕的任务数）与 `tasks_executed`（按过这个
控件的任务数）。两者之比区分"直通屏"和"岔路口"：

| 门控 | 开火 | 正确率 | 对 / 错 | 净 |
|---|---|---|---|---|
| 无 | 291 | 36% | 104 / 187 | **−83** |
| 通过率 ≥30% | 188 | 52% | 97 / 91 | +6 |
| 通过率 ≥50% | 148 | 59% | 87 / 61 | +26 |
| **通过率 ≥70%** | **127** | **66%** | **84 / 43** | **+41** |
| 通过率 ≥90% | 121 | 65% | 79 / 42 | +37 |

`--prefill_pass_rate 0.7`，并新增 `nopass` 消融臂作为这次修复的直接对照。

### 输掉的任务是什么样的

| 任务 | 预填按了什么 |
|---|---|
| AudioRecorderRecordAudioWithFileName | `btn_record`（开始录音）+ `btn_record_stop` |
| ExpenseAddSingle | `btn_save\|SAVE` —— 保存空表单 |
| MarkorDeleteAllNotes | `fab_add_new_item` —— 目标是"删除所有笔记" |
| FilesMoveFile | `button1\|OK` —— 确认对话框 |

省步多的任务按的则全是导航：`icon_mime_lg`、`icon`、`text1\|Empty file`、
`content_editor`。MarkorDeleteAllNotes 那条尤其说明问题：句向量把同一 app 里
**意图相反**的目标判得很近（"删除所有笔记" vs "新建笔记"）。通过率门控从另一个
方向解决它——岔路口本来就不该预填，不管目标相似度多高。

## 通过率门控上线后的读数（2026-09-13，39 个配对任务）

| | n | 新设计 | 不建图 | Δ |
|---|---|---|---|---|
| 预填触发 | 11 | 5 (45%) / 10.36 步 | 6 (55%) / 11.91 步 | 成功 −1，**步数 −1.55（−13%）** |
| 预填未触发（阴性对照） | 28 | 13 (46%) | 14 (50%) | 成功 −1，步数 +0.46 |

**动作正确率 73%**（11 对 / 4 错，净 +7），门控前是 43%。两层的成功率差都是 −1，
即成功率持平（阴性对照同样 −1，是漂移不是机制）。

### 剩下的瓶颈是覆盖率，不是精度

```
开火率  前半 21 个任务 0.43/任务  →  后半 21 个 0.29/任务   （没有随 store 变满而上升）
拒绝    no_candidate 10.1/任务   →  8.4/任务
```

任务按字母序排，同一个 app 的任务成块出现；走完一个 app 的 5–10 个任务，下一个
app 的 store 又是空的。**冷启动下每个 app 只攒得到几个任务的记忆，撑不起覆盖。**

所以两个工作点都要报：
- **冷启动**：从零积累的诚实下界，摊到全量约 −4.5% 步数、成功率持平。
- **暖 store（分折播种，无泄漏）**：每个 app 已有约一半任务量的记忆，是"记忆
  积累之后"的工作点。

这不是给弱结果找理由——冷启动的覆盖上限是可以直接算出来的，而暖 store 的
播种方式（两折任务集不相交）排除了泄漏。

## 这个机制的物理上限：5–7% 步数（2026-09-13）

暖 store 是不是就能撑起覆盖？折间交叉选参（在折 A 上选阈值、在折 B 上评测，
不在评测集上调参）的答案是**否**：

| | 开火 | 正确率 | 净 | 跳/任务 |
|---|---|---|---|---|
| 冷启动（无偏、按屏幕真值） | 127 | 66% | +41 | 1.13 |
| **暖 store（分折播种，无泄漏）** | **96** | **68%** | **+34** | **0.83** |

**给 store 播种别的任务的记忆并不能改善预填。** 精度在 66–68% 封顶，覆盖反而
略降——同屏候选变多，岔路也变多。记忆越多不是单调更好。

顺带一个读数：**边际门（margin）在暖 store 上完全不起作用**（0.6 / 1.2 / 2.0 三
个值结果逐位相同），因为同屏带目标的候选控件通常只有一个，冠亚军之差无从谈起。
起作用的是相似度阈值本身（thr 0.4→0.55→0.7 对应 53%→58%→68%）。

### 上限的算式

```
屏幕访问里真的涉及点击导航的        43%   （927 次访问里 402 次）
其中跨任务记忆能选对控件的（门控后）  66-68%
门控放行的比例                     10-17%
→ 可省动作 ≈ 60-85 / 116 个任务 ≈ 0.5-0.7 步/任务 ≈ 全部步数的 5-7%
```

要突破它需要其中之一：**预测非点击动作**（打字内容是任务特有的，记忆里没有），
或**把控件预测做到 66% 以上**（需要对目标的理解超出 22M 编码器）。

也检查过有没有一个"极高精度子集"可以做**真跳过**（省掉整次 LLM 调用而不只是一
步）：没有。把门收到最严（pass_rate 0.9 + thr 0.7）精度反而从 68% 降到 62%，
`unique` 来源单独看也只有 36/58 = 62%。**不存在可以免检执行的高置信子集。**

### 结论

跨任务图记忆在 AndroidWorld 上可以做到**成功率持平、步数降 5–7%**，做不到显著
加速。这是机制的上限，不是实现的缺陷——上面每一项都是直接量出来的。

## 两个新的负结果（2026-09-14）

### 1. 放宽门控输了：「落空免费」在三倍量级下不成立

g_lean h1 的分组读数显示落空的预填只花 −0.12 步，据此推断"该最大化命中数而不是
净值"，跑了放宽门控的 `g_loose`（thr=.4 pass=.3 margin=0 min_tasks=1，离线预计
命中 84→100、落空 42→129）：

| 臂 | 成功 | 步/任务 | 推理 | 预填 | 落点命中 |
|---|---|---|---|---|---|
| **g_loose（放宽）** | 52/115 | **10.16** | 1161 | 109 | 83% |
| **g_lean（现行）** | 54/114 | **9.32** | **1055** | 79 | 75% |
| 不建图 | 58/115 | 9.86 | 1134 | 0 | — |

配对：g_loose 的预填触发组 **+0.48 步**（更慢），g_lean 是 **−1.02 步**。

来源结构说明了原因：`min_tasks=1` 让唯一性门几乎不再是门（`unique 84 / goal 25`，
g_lean 是 `goal 55 / unique 24`），`control_absent` 从 20 次涨到 92 次。
**「落空免费」只在落空稀少时成立；三倍量级下它不再线性。紧的门是对的。**

### 2. 路径回放输给按屏幕检索

链式预填几乎全是长度 1（75 次里 72 次）。成功跳之后的拒绝原因：21 次"store 认识
落点屏幕但无候选"、29 次"没记录过落点屏幕"、只有 4 次接着跳了第二下。

自然的想法是：建议这一跳的那个目标相似邻居任务，自己知道下一屏怎么走——沿它的
整条路径回放即可。离线实测**更差**：

| | 开火 | 命中 | 正确率 | 命中/任务 |
|---|---|---|---|---|
| 路径回放 最多 1 跳 | 73 | 52 | 71% | 0.45 |
| 路径回放 最多 3 跳 | 110 | 65 | 59% | 0.56 |
| 路径回放 最多 5 跳 | 116 | 69 | 59% | 0.59 |
| **按屏幕检索（现行）** | **126** | **84** | **67%** | **0.72** |

每跳精度随链长单调下降（71% → 59%）。**跟着单个邻居走整条路，不如在每块屏幕上
重新投票。** 至此提升覆盖的三条路——暖 store、放宽门控、路径回放——全部证否。
