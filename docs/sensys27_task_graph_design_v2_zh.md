# MobileExplorer 设计 v2：任务实体参数化的在线流程图

日期：2026-10-03。v1（`docs/sensys27_task_graph_design_zh.md`）的“模型契约 + episode 内 witness 路线”已被实测证伪，见 `docs/sensys27_task_navigation_validation_zh.md`：契约覆盖率 0/74，即便给完美契约，后见之明上界也是 0。v2 保留 v1 的思想：在线建图、为当前任务补缺口、省掉导航推理，并在复杂操作之前停下。变化在于**图的单位、任务条件的来源和许可方式**，全部由实测数据推出。数值见第 5 节，结果目录 `results/sensys27_task_navigation/20261003_proc_final/`。

## 0. 从失败里读出的约束

1. **4B 模型不会遵守可选的输出格式**，任务条件不能寄希望于模型在推理里附带结构化字段。但它在**纯文本、单一目的**的调用里能准确抽出任务实体（0.3–0.5 s，约 110 个 prompt token）。
2. **AndroidWorld 的 episode 很短，屏幕几乎不重访**（按严格签名 5%）。按“屏幕”建图的边，在同一 episode 里没有第二次使用的机会。
3. **真正重复的是“流程”，不是“屏幕”**。多实体任务（删除 A、B、C）对每个实体执行同一段决策序列，只是实体不同；第 2 个实体的列表、详情页、菜单都是新的屏幕实例。
4. **landing 命中不等于适用**。warm 预填 6/10 落点命中，其中 3 次是提交动作（FOLDER、DELETE），4 次是容器 selector 导致的实体串用。

## 1. 问题一：在线、任务特定的图怎样建立、存什么、和别的东西有什么区别

**建立。** 从空图起步，只用本 episode 里模型**真实执行**的动作。每个动作落定后，记一条“跳”（hop），并附上独立检查器的判定（持久状态是否改变）。不探测、不回滚，所以没有额外的 GUI 风险。

**存什么。** 每一跳存：
| 字段 | 作用 |
|---|---|
| 源 / 目标 activity、目标屏幕标签 | 回放时校验落点，包括实体落点 |
| 动作类型（click / long_press / input_text） | 按演示的方式回放 |
| selector：resource-id + class + 自身标签 + **内部标签**（子节点文字） | 列表行、菜单项的文字在子节点上；没有自身标签的图标靠唯一的 resource-id 命名 |
| **实体槽位**：被按控件的内部标签恰好包含某个任务实体，或者输入的文字恰好等于某个任务实体 | 把“对 A 做的事”抽象成“对 X 做的事” |
| 状态判定：不变 / 改变 / 未覆盖 | 区分导航与提交；未覆盖的跳不发证书 |

**任务条件化。** 当图里第一次出现“若干跳之后接一次提交”时，再调用一次模型，抽出任务实体（按需发起：读信息类任务没有提交，不付这次调用）。抽出的实体必须在目标原文里逐字出现，否则丢弃。实体绑定回已经记录的跳之后，这段演示就成了**模板**：上一次提交之后到这一次提交之前的那段跳，其中的实体跳是槽位，其余是固定跳，以第一个会改持久状态的跳作为终点（不含这一跳）。

**和其他东西的区别。**
- **离线 UTG / app 文档**：它们描述 app 能做什么。这里描述的是**本任务、本 episode 里模型已经验证过的一段决策**，跨任务不复用，不需要事先探索 app。
- **跨任务历史复用**（AutoDroid / SwiftAgent / OmniFlow / 本仓库的 warm store）：它们需要别的任务的成功轨迹。冷启动下这里也成立，模板来自同一任务里的第一个实体。实测的冻结 warm store 在严格门下收益为 0（第 5 节）。
- **在线 FSM / 执行图**（Agent-SAMA、EAM）：它们以状态为节点做规划。这里的单位是**以实体为参数的决策片段**，许可来自“任务契约 + 本 episode 演示 + 状态证书”三者同时成立，而不是来自访问次数或者熵。

## 2. 问题二：怎样用图定位最值得补齐的缺口

图在每一步给出当前的缺口，探索预算只用在缺口上：

| 缺口 | 定义 | 补齐方式 | 实测 |
|---|---|---|---|
| G3 演示缺口 | 还没有完成的演示 | 不探索，模型正常推理（第一个实体就是演示） | 大多数步骤处于这个状态；旧设计在这里花 probe 追求新颖界面，收益为 0 |
| G2 定位缺口 | 模板已就绪，还有未处理的实体，但不在当前屏幕上 | 模板自带的定位子流程（演示里的搜索 + 输入实体名），从最晚的可行跳开始回放 | 滚动探索 0/4 找到、2/4 没能恢复屏幕（负结果，已移除）；学来的搜索子流程见第 5 节 |
| G1 证书缺口 | 模板里有跳没拿到状态证书（检查器未覆盖） | 下一窗口在检查器包围下对这一跳做 probe 并恢复 | 在已覆盖的 7 个 app 上出现 0 次；未覆盖的 app 上永远不发证书，所以不回放 |

所以这里的“探索最值得补的路径”不是一个打分器，而是一个**集合判定**：只有 G2 和 G1 会消耗探索；G3 不探索，因为第一个实体的演示本来就要由模型完成。

## 3. 问题三：怎样省掉 navigation 推理，并在复杂判断之前停下

每一步推理之前做一次规划：
1. 模板就绪，并且还有未处理的实体。
2. 选起点：如果下一个实体直接作为模板的实体按压出现在屏幕上（并且唯一），就从那一跳开始；否则从后往前找第一个可行的起点：它的控件在屏幕上，而且实体会在被按之前先被输入。
3. 逐跳回放：每跳都重新定位，要求唯一；校验落点 activity；实体跳还要校验落点上出现了**新**实体。任何一跳不符就立即停下，从真实屏幕交还给模型（已经发生的按压如实写进历史，不假装撤销）。
4. **停在模板终点**，也就是演示里第一个改持久状态的跳之前。提交、确认、编辑文本、作答、COMPLETE 永远由模型自己做。回放的每一跳都写进模型的历史：“Now handling X the same way as A … the final confirmation for X is still pending.”

许可的三个来源缺一不可：任务契约（实体）、本 episode 演示（顺序与控件）、状态证书（不改持久状态）。这里没有访问次数、熵，也没有词汇相似度。

## 4. 已知边界

- 只对“同一任务里多个实体走同一流程”的任务有效。单实体、读信息、新增类任务（实体还不在屏幕上）不触发，只在有提交的任务上多付一次约 110 token 的抽取调用。
- 窗口级证书：同一步里先改后复原的情况看不见；网络、云同步、其他 app 的状态不在观测范围内。
- 一个实体同时出现在多个列表行上时拒绝回放（`entity_ambiguous`）；容器 selector 不能绑定实体。
- 串行 runner，edge-assisted；没有单手机资源竞争实验，也没有并行 runner 的接线。

### 5.3 时间成本（如实）

宏触发的任务里，4 个中有 3 个整体更快（每次快 5–8 秒），ExpenseDeleteMultiple2 慢 7–10 秒（只省了 2 步）。代价是串行 runner 里**每步多约 1.0 秒**（4.36 → 5.39 秒），来自检查器每步两次快照和一次落定截图，都在关键路径上。所以宏未触发的任务整体慢约 27%。这里的模型调用约 2.5 秒一次。在模型更慢的部署里（手机本地），或者把快照放进推理窗口的并行设计里，这个比例会改变，但**都没有测**。

### 5.4 开发过程中被实测发现、修复的缺陷（都带回归测试）

1. 新建空目录对文件检查器不可见，导致 FOLDER 被误判为不改状态。
2. BLOB 行导致快照解码失败。
3. 无文字图标只能靠唯一 resource-id 命名。
4. 第一个实体用长按演示时，模板形成不了。
5. 模型输入时不带坐标，输入框只能按屏幕上唯一的输入框（含 AutoCompleteTextView）认定。
6. 回放输入没有先清空输入框，导致文本被追加。
7. 回放失败的实体被误标为已完成。模型因此漏删 1 个实体，是一次**由机制造成的失败**。
8. 动画中途截图，点到了屏幕外（x=1108 > 1080）。
9. 演示开头无法回放的跳拖垮了整个模板。
10. 宏越过任务顺序处理下一个可见实体，打乱了模型的进度叙述：模型把 Pet Supplies 当作最后一项，提前宣布完成，又是一次**由机制造成的失败**。修复为只回放按任务顺序排在下一个的实体，并加进度账。

第 7、10 项说明：回放对 GELab 这类靠自身摘要追踪进度的模型，会改变模型的叙述。所以“在复杂判断之前停下”不只是指不执行提交，还要求不篡改模型对进度的认知。

### 5.5 三个问题的结论

1. **建图**：图的单位应当是“本 episode 内、以任务实体为参数的决策片段”，而不是屏幕。屏幕重访只有 5%，而在多实体任务里，片段每多一个实体就复用一次。许可由三者共同给出：任务契约（一次按需的文本调用抽出实体）、本 episode 的演示、独立的状态证书。冷启动即可成立，不依赖跨任务记忆（冻结 warm store 在严格门下收益为 0）。
2. **缺口**：有价值的探索目标只有两类：模板跳缺证书（G1，在已覆盖的 app 上 0 次），以及实体不在屏幕上（G2）。G2 用滚动探索去补是负结果；用模型自己演示过的定位子流程（搜索 + 输入实体名）可以补上，并已实测（Noise 任务，19 → 9 步）。演示缺口（G3）不探索。
3. **省推理、在复杂判断前停下**：在多实体任务上每个任务省 2–10 次决策，成功率不变，20 跳回放全部停在提交之前。收益只来自多实体任务；单实体、读信息、新增类任务上，代价是一次约 105 token 的抽取调用（只在出现提交时才发起），以及检查器的时间开销。
