# 渐进式图扩展与机会性推理绕过：可行性研究（2026-10-14）

> 结论先行：**NO-GO（在门 A 处停止）**。
> 离线 oracle 上界已经表明：即使假设授权完美（oracle 目标）、探测完美（oracle 选择，每次都探中模型之后要点的控件），在线探索新增的、可被后续复用的导航知识，在 116 个成功 episode 里最多只能绕过约 **12 次**推理调用。其中真正的导航只有约 4–5 次，其余是数值输入或实体选择。约束不在发现，而在复用：探索得到的知识几乎没有"之后还会用到它"的决策点。
> 因此没有实现目标选择器和推理窗口控制器，没有做在线 oracle 试点，也没有跑闭环实验（见第 6 节）。

## 3. 第 1 阶段：离线机会审计（`scripts/stage1_audit.py`、`stage1_lookahead.py`；`metrics/stage1_*.json`）
BASE 共 232 个 episode、**2320** 个推理前沿，记忆按留一模板冻结为 G0。

| 指标 | 状态数 | 占比 |
|---|---|---|
| A：有任务授权的安全图续写（可以直接执行） | 4 | 0.2% |
| B：至少有一个未知的安全导航槽位（可扩展的前沿） | 1313 | 57% |
| C：B，并且处在通往锚点状态的已知部分路径上（≤2 跳） | 686 | 30% |
| D：存在 2 跳前沿（某个已知后继页还有未知槽位） | 688 | 30% |
| E：在 B 状态中被拒的原因 | 推理窗口放不下 1 次探测：547；没有任务目标：57；全部是歧义槽位：0 | |
| F：盲目按屏幕顺序扩展时，第一个选中的已在 G0 中 | 178 / 1414 | 13% |

- 和上一轮的"功能缺口驱动"相比，**可扩展的机会多了两个数量级**：C = 686 个状态，而上一轮只有 11 个会改变决策的查询。也就是说，扩展式探索确实有大量可以去学的东西。
- 但是"学到"不等于"之后用得上"。探索得到的知识要产生一次推理绕过，必须满足三条：
  1. 之后有一个决策点用到这条知识；
  2. 这个决策点得到了授权；
  3. 在推理窗口里来得及探测。

  下面的上界专门量化第 1 条。

### Oracle 上界：在线探索能创造多少次推理绕过（`metrics/stage1_U_cases.json`）
这里假设**授权完美**（模型之后点什么都算被授权），**探测完美**（窗口里探的正好是模型之后要点的那个控件），并且只计 G0 中**原本没有**的边，避免把历史复用算成探索的功劳：

| 绕过的来源 | 全部 episode | 其中成功的 episode |
|---|---|---|
| 回访型：前面某一步的窗口在同一状态上探到了这个控件，后来回到这个状态时，模型正好点它 | 56 | **12** |
| 回访型，探测改为可部署的公平顺序（屏幕顺序） | 33 | **2** |
| 前瞻型：第 t 步的窗口做深度 2 探测，覆盖了第 t+1 步模型要点的控件 | 54 个候选，但**没有一个窗口放得下深度 2**（需要约 3.4 s，服务器窗口中位数 1.77 s） | 12 个候选，0 个放得下 |

成功 episode 中的 12 个回访型案例，逐个看：
- ClockTimerEntry：数字键 ×2，属于数值输入，不是导航；
- MarkorMoveNote：文件夹行 ×4，选哪个文件夹是任务参数，属于实体选择；
- RecipeDeleteMultipleRecipes：食谱卡片 ×1，实体选择；
- 真正的导航只有：MarkorDeleteAllNotes 的 QuickNote / snippets / Go to（4 次），以及 OsmAnd 的"我的位置"（1 次）。

**上界**：在线探索能新增的、可绕过的导航推理约为 **5 / 约 1150 步（成功 episode）≈ 0.4%**。即使在端侧更长的推理窗口里，前瞻型也最多再加 12 次，同样大多是实体选择。

## 4. 门 A：FAIL
- **发现不是瓶颈**：可扩展的前沿到处都有（57%），离已知锚点路径不远的前沿也有 30%。
- **复用才是瓶颈**：AndroidWorld 上的 episode 短，回访少；探到的知识要么当场就被模型用掉（模型本来就会点那个控件，不需要绕过），要么之后再也遇不到同一个决策点。
- 这个上界已经同时给了 oracle 授权和 oracle 探测。所以就算目标获取、前沿选择、推理窗口集成都做到完美，也越不过这个上界。按任务要求，在这里停止昂贵的工作。

## 5. 失败归类（按第 15 节）
| 类别 | 是否成立 | 证据 |
|---|---|---|
| 知识效用失败（图扩展了，但从没影响过实际决策或执行） | **主要原因** | 1313 个可扩展状态里，oracle 条件下能被后续复用的只有 12 个（成功 episode），其中导航 5 个 |
| 时序失败 | 是 | 前瞻型绕过需要深度 2，服务器窗口里一次都放不下；回访型也有 547 个前沿连 1 次探测都放不下 |
| 复用（授权）失败 | 是 | 绕过点中有 7 / 12 是实体或数值选择，本来就不能由图授权 |
| 安全失败 | 是（来自前几轮） | 深度 1 回滚失败 26%；历史失效时，修复需要持久化或单向操作 |
| 目标说明 / 检索 / 前沿选择失败 | 不是瓶颈 | 上界已经假设它们完美 |

## 7. 建议
1. **停止"在线探索 → 推理绕过"这个研究方向**（在 AndroidWorld + GELAB-4B 上）。限制它的是复用机会，而不是算法。
2. **简化图**：只保留 episode 内由模型授权的执行，即实体流程复用和模型提交后的确认。这是目前唯一测得"触发即有效、没有伤害"的机制（FULL5：触发的 9 个 episode 调用 −19%）。跨运行的图只记录安全事实（哪些控件不能回滚）。
3. **如果一定要论证探索**，必须换一个**回访多、窗口长**的场景，例如同一用户在同一 app 里长期重复做类似任务，并且模型在端侧推理（每次 ~10 s）。按本报告的方法，先离线算出回访型和前瞻型的上界，确认上界足够高再实现。
