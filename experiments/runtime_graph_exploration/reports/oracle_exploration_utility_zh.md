# 探索效用诊断：证据效用问题，还是目标选择问题？（2026-10-14）

> 数据：BASE 两轮共 232 个 episode、**2320** 个模型决策状态（`trace_reachability_validation/raw/full/BASE`）。记忆按留一模板构建，与 02 / 03 报告一致。
> 主模型 GELAB-ZERO-4B，temperature 0。服务器上的推理窗口实测：中位数 1.77 s，p10 0.97 s。一次探测加回滚：中位数 1.69 s，p90 2.60 s，回滚成功率 89%（FULL5 的 157 次探测）。

## Stage 1：机会审计（`scripts/opportunity_audit.py`，`metrics/opportunity_states.jsonl`）

每个状态按下面的顺序取**第一个**成立的原因：

| 原因 | 含义 | 状态数 | 占比 | 其中来自失败 episode | 模型这一步实际在做什么（前几类） |
|---|---|---|---|---|---|
| anchor_visible | 目标锚点（goal 原样点名的标签）已经在屏幕上，下一步是语义选择，不是导航 | 1133 | 48.8% | 676 | 非点击 383，unsafe 283，实体 / 点名控件 271，未知导航 82 |
| no_safe_frontier | 没有安全的非实体可点击槽位（安全资格） | 366 | 15.8% | 233 | 非点击 159，unsafe 106，实体 97 |
| outside_app | 桌面或系统 UI | 356 | 15.3% | 231 | 非点击 242 |
| unseen_frontier_only | 有安全的未知前沿，但没有任何分支有锚点证据，现有规则不生成查询 | 227 | 9.8% | 125 | 非点击 91，unsafe 54，实体 33，**已知导航 29，未知导航 8** |
| valid_query | 存在一个锚点分支，但被未知前沿挡住（合法查询） | 120 | 5.2% | 74 | 已知导航 62，unsafe 36 |
| state_unseen | 页面不在记忆中（图覆盖不足） | 80 | 3.4% | 59 | 非点击 43，**未知导航 21** |
| all_known_no_anchor | 每个安全槽位都有证据，但 2 跳内都没有锚点 | 34 | 1.5% | 22 | 已知导航 23 |
| direct | 只靠图就能授权一个槽位 | 4 | 0.2% | 2 | — |

**结论**
1. **最大的瓶颈不是图覆盖，也不是探索目标选择，而是决策本身不是导航**：
   - 49% 的状态里目标锚点已经可见；
   - 另有 31% 是没有安全前沿或不在 app 内；
   - 模型的动作 40% 不是点击（输入、滑动、结束），25% 是提交 / 对话框 / 开关，19% 是实体或被点名的控件。
2. **安全的未知前沿到处都有**：1313 / 2320 个状态（57%）至少有一个。但模型在这些状态的下一步走进未知前沿的只有 **121 次（9%）**。不与任何历史函数相连的前沿（unseen_frontier_only + state_unseen，共 307 个状态）中，模型走进未知前沿的只有 29 次。
3. **时间预算是硬约束**：服务器推理窗口里只放得下 0 次（1129 个状态，49%）或 1 次（1175 个，51%）探测，放得下 ≥2 次的只有 16 个。前沿中位数是每状态 4 个，所以即使目标选择完美，一个窗口也只能回答一个前沿。
4. **图覆盖**只解释 3.4% 的状态（state_unseen）；**动作绑定**失败（模型点击落在非槽位上）有 54 步（2.3%）。

注意：上面"模型走进的比例"只描述机会，不是在评判探索证据对不对。模型没走某个前沿，并不说明那个前沿的证据没用，这需要 Stage 2 的对照来回答。

## Stage 2：Oracle 探索效用试点（上界实验，单独标注）

### 设定
- **选状态**（`scripts/oracle_candidates.py`）：BASE 失败 episode 里的状态，并且同一任务实例（同 seed）在其他组中有成功轨迹，成功轨迹在同一 activity 上走了不同的安全导航；或者是回访 ≥3 次的循环状态。共 155 个候选，人工挑出 20 个，覆盖 14 个任务、10 个 app（`metrics/oracle_states_selected.json`）。
- **未来轨迹的用途**：只用于选状态、选探测候选，以及**在任何推理之前**预先登记正确动作集（`configs/oracle_pilot_labels.json`，含 F = 失败点 8 个、C = 对照 12 个）。不进入任何 prompt。
- **流程**（`scripts/oracle_pilot.py`）：
  1. 以同一 seed 重建任务实例，回放记录的动作到该状态；
  2. 对预先登记的候选做真实的深度 1 探测，回滚后验证状态复原；
  3. 用同一张截图、同一 goal、同一历史，分别在 8095 和 8096 两个端口上询问 GELAB-4B：M0 不加证据，ME 加上观测到的子页面可供性。
- **复原失败的处理**：探测后状态没复原的不做推理，去掉失败的探测项后重做一次，并记录。
- **正确性**：按预先登记的集合判定。两类需要人工裁决（下面单独标明）：
  - 回放只在 activity 级匹配、实际页面与记录不同的状态（1、7），按实时截图重判；
  - 日历月视图格子的 a11y 边界损坏（126 个格子边界相同），按像素位置判断点的是哪一天。

### 深度 2
没有测试。原因：
- 深度 1 在这些有利状态上就有 26% 的探测回滚失败，深度 2 会叠加这一风险；

## Stage 3：方向决策

**结论：在 AndroidWorld + GELAB-ZERO-4B、证据以 prompt 形式提供的条件下，对"运行时探索 → 增强推理"这个方向给出 NO-GO。** 停止继续优化探索目标选择。依据：
1. **机会**（Stage 1）：49% 的决策在目标锚点已可见时做出，是语义选择；模型只在 9% 的有安全未知前沿的状态里走进未知前沿；服务器推理窗口每次只放得下 0–1 次探测。
2. **效用上界**（Stage 2，由 oracle 挑选的有利状态，n = 14 个可评分状态，**不构成统计显著性**）：
   - 真实证据 11 对、安慰剂 9 对、无证据 8 对；
   - 能按内容归因的单步改进只有 1 / 14；
   - 闭环成功 1 / 4 对 1 / 4。
3. **可执行性**：即使在有利状态，深度 1 探测的回滚失败率也达 26%（8 / 31），影响 8 / 20 个状态；另有 3 / 20 个状态没有任何可以安全探测的前沿。
4. **瓶颈的性质**：是**证据效用**问题，不是目标选择问题。即使 oracle 替我们选中了正确的探测对象，探到的子页面信息也很少改变模型的决策，改变时也多半是追加文字本身造成的扰动。

**不建议**：实现新的探索控制器；在 AndroidWorld 上再跑完整的端到端对比。

**建议**：
- 论文的系统贡献放在**模型授权的执行**上：任务内的流程复用、模型提交后的确认（FULL5：触发的 9 个 episode 调用 −19%、无伤害）。探索只保留为按需的安全与验证层。
- 如果仍要论证探索的独立价值，应换到**历史转移真实失效**的受控场景（见下节），先离线测出缺口率，缺口率足够高再做在线对比。
- 证据不经过 prompt，而是由系统直接执行（"预填优于注入"）：这需要模型授权，而授权正是第 1 条里机会稀少的部分。

## Stage 3（附）：受控的运行时变化场景（已确定，尚未运行）

目的：在**历史转移真的失效**的条件下检验探索，而不是在 AndroidWorld 默认环境里去找机会。每个场景都由一次可逆的环境操作诱发，用同一套留一模板记忆，对比"历史直接回放"和"历史 + 深度 ≤2 的修复探索"。基准、安全规则和记忆划分都不改。

| 场景 | 诱发方式（可逆） | 哪些历史转移会失效 | 缺口类型 | 探索预期的作用 |
|---|---|---|---|---|
| V1 首次启动重置 | 对目标 app 执行 `pm clear`，然后由任务初始化重新写入数据 | `OPEN_APP` 之后不再到达主页面，而是到达引导页或权限对话框（如 Audio Recorder 的 "Get started"、日历的权限请求） | G2 转移缺口 | Q3 修复：找一条 ≤2 跳的安全路径回到历史入口页；只允许非持久化的关闭类动作，权限授予属于不可逆操作，交给模型 |
| V2 应用内视图偏好 | 在 Simple Calendar 设置里把默认视图从月视图改成列表 / 日视图（任务结束后改回） | 主页面骨架变化，历史上"月格子 → 日视图"和 FAB 位置相关的转移失效 | G1 入口缺口 + G3 续写缺口 | Q1 / Q3：验证 `change_view` 的子页面可供性，重新接回历史续写 |
| V3 系统语言 | 把系统语言切换到另一种语言（任务结束后改回） | 标签全变，resource-id 不变；按标签识别的历史动作身份失效 | G1 入口缺口（语义未变） | 按 rid 和结构重新绑定。探索用于确认重新绑定后的后继页面与历史一致（Q1） |
| V4 对照：显示大小 / 字号 | 修改显示大小（任务结束后改回） | 只有坐标和布局变化，按 rid 和标签的身份不变 | 预期没有缺口 | 负对照：探索应该零触发 |

- 每个场景先在 5–10 个相关模板上离线计算缺口率：历史转移在新条件下 activity 级失配的比例。缺口率足够高才做在线对比。
- V1、V2 会修改 app 状态。实验前要确认 AndroidWorld 的任务初始化或拆卸能恢复，不行就用快照恢复；V3 需要设备级设置，跑完必须改回，并核验。

## 附：受控运行时变化的简单验证（已运行，2026-10-14）
`scripts/variation_run.py`、`variation_driver.sh`；原始数据 `raw/var/`；日志 `logs/variation_driver.log`。

**设定**
- **历史函数**：同一任务实例（seed 30）成功轨迹的回放。目标控件按选择器重新定位，参数做替换，不调用模型。
- **三个条件**：
  - V0：无变化，直接回放（对照：历史路径本来能不能用）；
  - Vx plain：有变化，直接回放（变化有没有制造缺口）；
  - Vx repair：有变化，断开时做不调用模型的修复探索，再继续回放。
- **修复探索规则**：深度 ≤2；只点安全控件；图中有进入目标 activity 的边的控件优先，其余按屏幕顺序；不成功就按 BACK 回滚并验证，回滚失败即停止。

**有效样本**：只统计 V0 成功的任务，共 8 个。SimpleCalendarEventsOnDate 和 TasksHighPriorityTasks 的 V0 本身就失败，排除。

| 场景 | 任务 | V0 | 直接回放 | 回放 + 修复 | 修复失败的原因 |
|---|---|---|---|---|---|
| V2 日历默认视图改为日视图 | AddOneEvent | ✓ | ✗ 第 3 步目标缺失 | ✗ | 回到月视图需要"Change view → Monthly view"，第二步是持久化设置（不允许试探）；试探"前一天"箭头后，BACK 无法回滚 |
| | DeleteOneEvent | ✓ | ✗ 第 3 步目标缺失 | ✗ | 同上 |
| V1 清空 app 数据 | MarkorCreateFolder | ✓ | ✗ 进入引导页 IntroActivity | ✗ | 越过引导页需要 4 次 NEXT 加 1 次 DONE，共 5 步，超过深度上限；每次 NEXT 都会被回滚；图中没有引导页的证据 |
| | ExpenseDeleteSingle | ✓ | ✓（缺口出现在任务完成之后） | ✓ | 修复回滚失败，但不影响结果 |
| | RecipeDeleteSingleRecipe | ✓ | ✓ 无缺口 | ✓ 0 次探测 | — |
| V4 显示密度 420 → 340（对照） | MarkorDeleteNote | ✓ | ✓ 无缺口 | ✓ 0 次探测 | — |
| | ExpenseDeleteSingle | ✓ | ✓ | ✓（这一次回放出现完成后的缺口） | 回放时序有随机性 |
| | ContactsAddContact | ✓ | ✗ 第 2 步只有 activity 匹配，骨架变了 | ✗ | 这不是转移失效，而是回放的状态匹配太严：目标控件仍在。修复试探点了搜索框，回滚失败 |

**结论**
- 会导致任务失败的真实缺口有 **4 个**：日历 2 个、Markor 引导页 1 个、通讯录密度 1 个。**修复探索接回了 0 个**。
- 修复尝试共 6 次，其中 **4 次回滚失败**。
- 失败的原因都不是"没探到对的控件"，而是三类结构性限制：
  1. **修复本身就是持久化操作**：把设置改回去；
  2. **修复路径长于 2 跳**：引导页要 5 步，且每一步都只能前进、不能回滚；
  3. **断开其实是状态匹配过严，而不是转移失效**：这类情况该修的是匹配器（按 activity 加控件唯一定位来判断落点），不需要探索。
- **在这个简单验证里，探索的独立价值没有得到证明。** 它说明的是：真正让历史路径失效的变化，往往需要一次持久化或单向的操作，而这正是按安全规则不能拿来试探的。
