# 运行时动态下的探索：轨迹复用解决不了的问题（2026-10-14，进行中）

代码：`scripts/dyn_run.py`（臂 BASE / TRAJ / GX / GX2 / GX3；变化 V0 / V1 / V2）、`functions.py`、`trajmem.py`、`dyn_driver*.sh`
数据：`raw/dyn/`（seed 32）、`raw/dyn_s33/`（seed 33）、`metrics/fn_offline.jsonl`

## 动机
- 轨迹复用（EchoTrail 式，检索 K=2 条相似任务的成功轨迹注入 prompt）依赖历史录制时的运行时。
- 运行时一旦出现历史里没有的状态（首次启动引导、权限 / 升级对话框、设置被改等），历史轨迹无法提供"在这个新状态上该做什么"。
- 这类信息只能在**当前运行时**通过探索获得。

## 各组定义（同一 GELAB-4B、同一 prompt 格式，只改变注入内容）
| 组 | 注入什么 |
|---|---|
| BASE | 不注入 |
| TRAJ | K=2 条检索到的历史成功轨迹（每步：界面标题 + 动作），每一步都注入 |
| GX | 函数路径：从当前页出发、到达 goal 点名控件的已观测路径。只展示第一步在当前屏幕上、且本次运行没有观测到偏离的路径。推理窗口内每次探测 1 次 |
| GX2 | GX 加卡住检测：模型的动作没有改变页面就记为无效；卡住时探测还没试过的安全控件，注入"X 点了没反应 / Y 会进入某页（是否为已知页面）" |
| GX3 | GX2，但卡住时改为指令式："Recommended next action: tap Y at (x, y)"。依据是本次运行的实测：模型自己的动作已证实无效，Y 已证实有效 |

## 结果 1：正常运行时下，函数路径注入既不帮也不害（离线配对）
- 189 个状态有函数可注入，其中 38 个可评分。不注入 / 注入 / 安慰剂都是 38 / 38 正确。动作改变：注入 10 / 92，安慰剂 9 / 92。

## 结果 2：日历默认视图改为日视图（V2）对模型不构成障碍（seed 32，4 个任务）
| | BASE | TRAJ | GX |
|---|---|---|---|
| V2（日视图） | 2 | 1 | 1 |
| V0（默认） | 1 | 1 | 2 |

- 这个变化会让**回放**失效（之前的回放实验里 2 / 2 断开），但模型本身能适应日视图。
- 三组之间的差别都在单次运行的噪声内。GX 在 DeleteOneEvent 上多花了 2–4 步。

## 结果 3：Markor 首次启动引导（V1，`pm clear`；每次运行后自动走完引导并验证回到 MainActivity）
seed 32，3 个任务（CreateFolder / CreateNote / DeleteNote）：

| 组 | 走出引导页 | 任务成功 | 默认运行时下成功（V0） |
|---|---|---|---|
| BASE | 0 / 3（每个都在引导页点图片打转 9–15 步） | 0 / 3 | 3 / 3 |
| TRAJ | 0 / 3 | 0 / 3 | 2 / 3 |
| GX | 1 / 3（探测点 NEXT 后回滚失败，页面被意外推进） | 1 / 3 | 3 / 3 |
| GX2 | 2 / 3（CreateFolder 靠证据；DeleteNote 靠意外推进；CreateNote 上证据被无视 14 次） | 2 / 3 | 3 / 3 |
| GX3 | **3 / 3**（CreateNote：第一次推荐后的下一步就点了 NEXT） | 2 / 3（CreateNote 走出引导页后，在命名 / 内容上出错） | 3 / 3 |

**解读**
- **轨迹复用确实解决不了这个问题**：TRAJ 和 BASE 一样被困在引导页（0 / 3）。默认运行时下，它们都能完成同样的任务。
- **运行时探索能解决**：探索在当前状态上实测出"哪个控件能让页面变化"。给出指令式推荐后，3 / 3 走出了引导页。这类证据的可靠性来自运行时实测，满足"提示比模型更准"的条件（之前跨任务的提示只有约 50% 正确）。
- **描述性证据不够**：GX2 有 1 / 3 被模型无视；指令式的 GX3 没有被无视。这与文字推荐实验中"模型会照推荐做"的结果一致。
- **代价**：默认运行时下，卡住检测偶尔误触发（每个任务约 1 次），多 0–1 次调用，没有造成失败。探测回滚失败仍然常见：引导页上的 NEXT 一点就不可回退。
- **局限**：每组只有 3 次运行，而且只是一种变化。

## 结果 4：seed 33 复现与合计（V1，每组 6 次运行）
| 组 | 走出引导页 | 任务成功 |
|---|---|---|
| BASE | 1 / 6 | 0 / 6 |
| TRAJ | 0 / 6 | 0 / 6 |
| GX3 | **6 / 6** | **4 / 6** |
| 对照：BASE 在默认运行时（V0） | — | 5 / 6 |

GX3 走出引导页的方式要分开看：
- **4 / 6 来自注入的推荐**：CreateFolder 和 CreateNote，两个 seed 各 1 次。推荐每次都被采纳，注入 1–3 次后模型就点了 NEXT。
- **2 / 6 来自探测的副作用**：DeleteNote 两个 seed 都是这样。第一次探测点了 NEXT，回滚失败，页面被推进，模型随后自己走了出来。这不是设计内的效果，属于"探测在不可逆控件上回滚失败"。在引导页上它恰好无害；换成别的状态，就可能是有害的状态改变。
- GX3 走出引导页后仍有 2 次失败（seed 32 的 CreateNote、seed 33 的 DeleteNote），都是后续操作中模型自己出错，与引导页无关。

**结论（两个 seed）**：首次启动引导是一个"历史中不存在的运行时状态"。
- **轨迹复用对它完全无效**：TRAJ 0 / 6。
- **运行时实测的探索证据加上指令式推荐能稳定解决它**：被推荐的 4 / 4 都走出了引导页，GX3 合计成功 4 / 6，BASE 为 0 / 6。
- **但这只是一种变化**：需要第二种变化来检验它能否推广。

## 结果 5：更多变化与卡住判据（两个 seed 合计；成功 / 运行，V1 括号内是走出引导页的次数）
| 变化 | BASE | TRAJ | GX3（1 次无效即触发） | GX3b（同一控件 ≥2 次无效才触发） |
|---|---|---|---|---|
| V1 首次启动引导 | 0/6（1） | 0/6（0） | **4/6（6）** | 2/6（6） |
| V0 默认 | 5/9 | 2/3 | 3/3 | 5/6 |
| V5 启动停在其他标签页（`pref_key__app_start_tab_v2` = 3） | 5/6 | 4/6 | 5/6 | 5/6 |
| V2 日历视图改为日视图 | 2/4 | 1/4 | — | — |
| V4 笔记以查看模式打开（`pref_key__is_preview_first`） | 0/3 | 0/3 | 0/3 | — |

**误触发**（在不构成障碍的变化上注入了卡住推荐的次数）：
- GX3：V0 2 次，V4 8 次，V5 4 次；
- GX3b：V0、V5 都是 0 次。
- V4 上的例子：模型在编辑模式点了一次工具栏标题，GX3 就推荐它去点笔记标题，这个推荐没有意义。

**解读**
- V2、V4、V5 都不是模型的障碍：模型自己点 "Edit mode"、切换标签页、在日视图里操作。V4 的三个任务即使在默认运行时也做不成，失败与变化无关。真正的障碍只有 V1，一个历史中不存在、模型又无法自己理解的状态。
- GX3 和 GX3b 都能 6/6 走出引导页。GX3b 要等第二次无效才触发，多浪费一步，在步数预算紧的 CreateNote 上两次都在走出引导页后、预算耗尽前没能完成。
- 两者的取舍可以由图来决定：当前状态是否在历史图中出现过，即是否为运行时新状态。由此得到 GX4：
  - 新状态上，1 次无效就触发，因为历史帮不上忙，需要探索的实测证据；
  - 已知状态上，需要重复 2 次无效才触发。

## 结果 6：GX4 / GX5 / GX6（两个 seed × 3 个 Markor 任务；V1 首次启动引导、V0 默认）
| 组 | 设计 | V1 走出引导页 | V1 成功 | V0 成功 | 回滚失败（V1 + V0 + V5，18 次） | 多出的模型调用 |
|---|---|---|---|---|---|---|
| GX4 | 按图判断是否为新状态：新状态 1 次无效即触发，已知状态需重复 2 次 | 6/6 | 2/6 | 5/6 | 12 | 12 |
| GX5 | GX4，并把探测效果和可逆性写入图、跨 episode 复用；探过的控件不再探 | 3/6 | 1/6 | 5/6 | 8 | 8 |
| GX6 | GX5，并加升级：在新状态上模型连续无视推荐超过 2 次时，由系统执行已验证有效的控件（以 [system] 写入历史） | 4/6 | 1/6 | 5/6 | 7 | −1（升级本身省掉了调用） |

**关键更正**：GX3 / GX4 的 6/6 走出引导页里，混入了探测的副作用。
- 第一次探测点了 NEXT，引导页无法回退，页面被推进一页，这本身就打破了模型的循环。
- GX5 记住了"NEXT 不可回退"，不再重复探测，于是只剩证据注入的效果：3/6。模型在 1–5 次推荐之后才照做。
- 所以**纯证据的效果是 3/6**（BASE 1/6，TRAJ 0/6）。
- GX6 的升级每次只推进一页，而引导共有 5 步（4 次 NEXT + DONE），所以在 10 步预算内仍然不够。

**作废的运行**：V1 的 `pm clear` 会让 Markor 重建 `app.xml`，导致 `pref_key__app_start_tab_v2` 这一项消失。因此 GX4 / GX5 / GX6 在 V5 上的运行（排在 V1 之后），变化其实没有生效，已标记为 `_INVALID_pref_not_applied`。修复（缺键时补写）后，GX4 的 V5 正在重跑。BASE / TRAJ / GX3 / GX3b 的 V5 都在 `pm clear` 之前运行，记录中的设置值可以确认变化生效。

**Markor 状态的残留变化**：`pm clear` 之后，Markor 的 `app.xml` 只剩默认项，原有的非默认偏好（例如 `new_file_dialog_lastused_type`）已丢失，无法恢复原值，因为没有备份。引导页已走完，设置均为默认值。

## 当前结论
1. 在 AndroidWorld 的正常运行时里，模型能自己适应大部分界面变化：日视图、查看模式优先、其他起始标签页都不构成障碍。轨迹复用和图注入在这些变化上都没有净效果。
2. 真正的障碍是**历史中不存在、模型又无法理解的状态**，在这里就是首次启动引导。在这类状态上：
   - 轨迹复用无效：0/6；
   - 运行时探索得到的有效控件证据能帮上忙：纯证据走出引导页 3/6，加上探测副作用可达 6/6，而 BASE 只有 1/6。
   - 限制模型利用这类证据的，是 4B 模型对推荐的遵从速度，以及步数预算。
3. 图在这里的作用是：
   - 判断当前状态是否为新状态（GX4 的触发门控）；
   - 存储探测效果和可逆性，跨 episode 复用（GX5：回滚失败从 12 降到 8）。
4. 证据的局限：只有 Markor 一种阻塞状态，每组 6 次运行，结论不构成统计显著性。下一步应找到更多真实的阻塞型运行时状态（权限对话框、登录 / 升级提示、版本更新后的新引导），检验是否能推广。

**GX4 在 V5 上的重跑**（修复后，记录确认变化生效）：成功 5/6，卡住推荐注入 **0 次**（GX3 同一条件下误触发 4 次）。图判断"已知状态"的门控，在不构成障碍的变化上没有误触发。
