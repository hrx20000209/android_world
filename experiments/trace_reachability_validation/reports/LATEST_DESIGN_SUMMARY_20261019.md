# MobileExplorer 最新设计总结（2026-10-19，供 GPT 解读）

> 本文件是打包材料的入口，先读本文件，再按第 7 节的目录索引查阅细节。
> 环境：AndroidWorld（114 个任务，排除 4B_2 出错任务），seed 30，模型 GELAB-ZERO-4B（vLLM）。
> 步数口径：推理步数 = VLM 调用次数（含重新推理）；一次图执行计 1 步；启动 app 不计步。
> 同配置单轮成功数波动约 ±10 题，因此结论以多轮合并和"双方都成功任务上的配对推理次数"为准。

---

## 1. 一句话

在 VLM 推理的同时并行探索界面。agent 执行和探索观测合成一张运行时图（联合图）；每步推理之前，先检查有没有能在当前屏落地、并停在提交前的"图执行"，有就直接执行以替代推理；推理返回后，若探测改变了屏幕，先尝试保全模型的决策。

## 2. 当前最好配置：FULL29

演进路线：FULL21 → FULL23（设计评审 P0）→ FULL28（表单 v2）→ FULL29（表单 v3）。

### 2.1 推理前：图执行算子

| 算子 | 入口条件 | 做什么 |
|---|---|---|
| `open_app` | 在桌面，任务里有 app 名，且图中见过这个包 | 直接打开 app，不计步 |
| `confirm` | 模型自己提交后弹出纯确认对话框 | 点确认 |
| `fill_record`（参数化函数） | 同 app、同动词、字段齐全的函数，首步在当前屏落地 | 用当前记录的字段值执行，停在提交前 |
| `form`（表单 v3） | 当前屏有空输入框（用 hint 判空），标签与记录字段名匹配 | 填值；每个字段只填一次；记录首字段只填 title / name 框 |
| `graph_reuse` | 本局在同一页面，模型两次选同一安全导航控件、落地一致、离开了本页 | 直接执行；页内重复不复用；模型撤销即刹车 |
| 意图导航宏（P0-2） | 当前屏唯一的安全导航控件被其他成功任务验证过（cos(目标, use) ≥ 0.5，margin ≥ 0.3，观测 ≥ 2，落地一致 ≥ 0.9） | 每步 ≤ 2 跳，计 1 步，逐跳校验 activity |

**参数化函数怎么来、怎么用：**
- **抽取：** 扫描成功轨迹里 agent 的每个动作。动作文本等于任务指令里的某个值 → 记为该字段的槽位（输入 `type(field)` / 点选 `slot_click(field)`）；否则记为导航；遇到提交类控件就切分。
- **匹配：** 函数库按任务模板留一；候选需满足入口 activity 相同、动词相同、函数字段名都出现在当前任务记录中；字段多、步骤多的优先；首步必须能在实时屏幕上落地。
- **执行：** 逐步重新定位目标（输入框按 rid → 第 k 个输入框 → 焦点框；点选按"行类型 + 行内文字等于字段值"）；找不到就中断交给模型。一条记录被处理过之后模型提交，才算完成，之后自动进入下一条记录。

### 2.2 与推理并行：探索

- 每次推理期间探测（代码里每次推理上限 5 次，每个容器每窗口 1 次）；暂态页面（弹窗、对话框、输入法、选择模式、抽屉）不探；每次探测前确认屏幕仍是原状态。
- **候选过滤：**
  - 图中已有 (app, activity, 控件族) 的边不探（页面级去重）；
  - 副作用控件不探：操作动词开头、开关类、学到的副作用控件；
  - 不可回退容器里的控件不探；
  - 要求 P_rev ≥ 0.7（FULL29 允许 0.5–0.7 且可重启重放的控件；FULL30 改为只要 ≥ 0.8）。
- **优先级** = score − 0.3 × (1 − P_rev)，只探优先级 > 0 的候选。完整公式见 `reports/` 中的讨论，或 `scripts/explore_value.py`：
  - score = 证据分层的 TF-IDF 相关性（已知边目的页 0.8 / 图中近邻 0.5 / 控件自身文本），已知页面的价值沿图回传（γ = 0.7），列表行另加参数匹配项；
  - P_rev = Beta 后验：跨 app 的"角色 × 位置"先验（单个控件 78%、兄弟组 70%、带选中态的兄弟组 37%）+ 本 app 同容器的回退证据，先验强度 5。
- **四类探测：** E1（预测下一步）→ FX（按优先级）→ D2（沿已知可回退的跨 activity 边深入一层）→ RV（在当前页面内容下重新观测已知边）。

### 2.3 图（联合图）

- 页面 = (app, activity, layout)，不含内容；边 = (页面, 控件族) → 目的页；记录来源（agent / 探索）、可回退性证据、目的屏截图。
- P0-1 执行验证：成功任务经过的边写入 `edge_use.jsonl`（目标词画像，按任务留一）；导航宏执行后被模型撤销记为误用。
- 跨任务持久的学习结果：容器级不可回退、副作用控件、深层探测失败的边。

### 2.4 探测之后：恢复与决策保全

- 恢复阶梯：再点一次 / 选回原标签 → Back → 沿图路径恢复 → 重启加重放（路径不含提交、≤ 12 步）→ 内容校验。
- 决策保全：有效性放行（同页面同控件）→ 重定位（所选控件唯一在屏则移到新位置执行）→ 都不行才重新推理。

**推理节省的来源（FULL29，一轮）：** open_app 94、confirm 22、函数 56 次 / 134 步、表单 43 字段、本局复用 14、导航宏 8、函数路由 1；重新推理 15。

## 4. 探索的实际作用（截至 10-19 的证据）

1. **消融（FULL29 vs FULL29X）：** 探索在成功任务上额外带来约 −5% 的推理（6 个带探索的轮次中 4 轮方向一致），并让函数 +9 次、表单 +3、导航宏 +4；代价是重新推理 +15，被抵消在失败任务上，平均推理的净效应约为 0。
2. **探索节点的去向（FULL29）：**
   - 模型 644 次导航中，落地页已在图中的 431 次，其中最早由探索发现的 66 次（15%）；
   - 模型走"只有探索观测过"的边 5 次，落地预测 100% 准确；
   - 在"最早由探索发现的页面"上执行的函数 6 步。
3. **离线排序评估（`scripts/eval_rank_tfidf.py`，FULL23/28/29 共 750 个探测时刻）：**
   - 只用 TF-IDF 与完整打分效果相同，分层权重、价值回传、局部 IDF 没有增益；
   - IDF 无论按屏幕计还是按 app 计（留一）都没有区别，因为约 72% 的时刻所有候选都与任务无共同词；
   - 所有打分排第一的命中率为 4–6%，低于随机的 7–9%；只有 23–30% 的时刻候选集中存在至少一个有用控件；
   - 唯一稳定有效的是可回退性项：第一个有用控件的平均名次从约 3.7 提前到约 3.1。
4. **结构性上限：** 模型动作中能由图安全执行的只有约 12%（安全导航）；提交 / 对话框（21%）和实体行（21%）不可探或每任务重置。
5. **45 秒探索窗口实验（服务器上做的，`reports/exploration_window_45s_summary_20261019.md`）：**
   - 成功率提升在噪声内（两个 seed 合计 44.4%）；
   - 追加探测的命中率只有首次的约三成（4.8% vs 16.1%）；
   - 75% 的窗口没有候选，空等占 91.7%；
   - 截图采集（中位约 3.6 s）比推理（约 1.45 s）还慢。

## 5. 设计层面的诚实结论

- 可复现的收益：推理次数比 BASE 少约 10–15%，成功任务少约 15%，成功率持平（多轮）。
- 收益的主体来自**过程层**（参数化函数、表单、确认、启动），只依赖 agent 自己的成功轨迹；参数化函数与运行时图目前是两套存储（`function_cache.jsonl` 与 `graph.jsonl`）。
- 探索的直接贡献很小：成功任务上约 −5%，并被回滚失败的代价抵消；它更多提供去重、可回退性学习、恢复路径等间接价值。
- 探索打分偏启发式；离线数据显示可以简化为 priority = rel_TF-IDF(任务, 控件文本) − κ(1 − P_rev)，效果不变。

## 8. 更新（2026-10-20）：纯在线版本 FULL33–FULL36

**"纯在线"的定义（FULL33 起）：** 运行时图和函数库都只从本轮运行中积累。函数库只从本轮已完成、且模型自报完成的 episode 抽取（`function_cache_online.jsonl`），不使用以前的图和离线函数缓存。

**仍在使用的离线通用统计**（不含具体任务轨迹，但不是本轮在线得到的）：
- 可回退性的跨 app 先验 `rev_prior.json`（来自 FULL11–14 的约 950 次探测）；
- 界面侧 IDF（`ui_idf.json` / `app_tokens.json`，来自 FULL11–14 的屏幕）；
- 任务侧 IDF（来自 BASE 的任务指令）。

**设计（FULL33 → FULL36）：**
- **FULL33：** 统一图复用。启动、确认、函数（参数化边）、表单（模式边）、本局重复、跨任务宏，都作为当前页面的出边，以本轮运行时图上的边为触发依据；执行后写回图，被模型撤销就记误用并刹车。另外加了价值信息探索项（相关性未知的控件排在相关性已知为 0 的控件之前）和解析修复。
- **FULL34：** 可回滚概率改为分层贝叶斯（跨 app 角色先验 → 本轮本 app 同类探索的后验 → 控件容器证据）；单窗口对话框状态不探索。
- **FULL35：** 行 / 控件分开学习可回滚后验；在线参数化边按字段角色对齐；"重新推理前先恢复"（实测触发 11 次、成功 0 次，无效）。
- **FULL36：** 最终在线设计复现，即 FULL35 去掉"重新推理前先恢复"。

**结果（单轮，114 题口径，配对 = 与 BASE 双方都成功的任务上的推理次数）：**

| 配置 | 成功 | 平均推理 | 成功任务推理 | 配对 vs BASE |
|---|---|---|---|---|
| BASE | 51 | 10.05 | 7.41 | – |
| FULL29（离线函数库，参照） | 50 | 8.83 | 6.16 | −15% |
| **FULL33** | 47 | **8.88** | **6.13** | 7.10 → 5.85（**−18%**，24 快 / 7 慢） |
| FULL34 | **50** | 9.30 | 7.04 | 7.44 → 6.34（−15%） |
| FULL35 | 45 | 9.01 | 6.16 | 6.75 → 5.67（−16%） |
| FULL36（最终在线设计） | 47 | 9.04 | 6.83 | 7.22 → 6.54（−9%，18 快 / 9 慢） |

**判断：**
- 纯在线版本中推理节省最好的是 **FULL33**；
- FULL34 的成功数最高，但所有机制读数（回滚失败、重新推理、成功任务推理）都变差，更可能是单轮波动；
- FULL36 作为"最终在线设计"，节省反而比 FULL33 小，需要复跑确认。

**纯在线与离线的关键差别：** 参数化边（函数）从 FULL29 的 91 次降到 FULL33 的 8 次（FULL36 为 80 个函数步）。原因是在线函数库只能用本轮已跑完任务的函数，而同 app 的任务连续执行、模板各不相同。表单（模式边）从 43 升到 67，部分补偿。

**FULL36 机制计数：** FX 探测 62、E1 52、RV 158；函数 80 步、表单 67 字段；重新推理 11。

## 9. 更新（2026-10-20 下午）：FULL37

**设计 = FULL36 的最终在线设计 + 两处修正：**
1. **推理预算口径修正：** 预算改为按 VLM 推理次数计算（20 次推理），另设 40 个计数步的总上限。此前图执行也占用 20 步预算，FULL29–36 每轮有 10–15 个失败 episode 在推理还不到 20 次时就被截断，对 FULL 臂不公平。BASE 的步数本来就等于推理次数，所以修正后两者口径一致。
2. **日历环境重置：** 每局开始时把 Simple Calendar 的视图偏好重置为默认值（`HYGIENE_PREFS`：`Prefs.xml` 中 `view=1`）。这个偏好很可能是早期运行时变化实验（V2：日历视图）遗留下来的环境污染，导致此前若干 FULL 臂在日历任务上处于不利条件。

**FULL36 / FULL37 的在线设计要点（详见第 2 节与第 8 节）：**
- **统一图复用：** 启动边、确认边、参数化边（函数）、模式边（表单）、动作边（本局重复、跨任务宏）都作为当前页面的出边；以本轮运行时图上的边为触发依据；执行后写回图，被模型撤销就记误用并刹车。
- **完全在线：** 函数库只从本轮已完成、且模型自报完成的 episode 抽取。仍使用跨 app 的通用统计（可回退性先验、IDF）。
- **探索：**
  - 价值 = TF-IDF 相关性；相关性未知的控件排在相关性已知为 0 的控件之前；
  - 可回滚概率用分层贝叶斯（跨 app 角色先验 → 本轮本 app 同类探索的后验 → 容器证据），实体行和控件分开学习；
  - 单窗口对话框状态不探索；
  - 优先级扣除回滚失败的预期代价。
- **参数化边按字段角色对齐：** 函数里唯一的实体槽，绑定到当前任务唯一的实体字段。
- **恢复阶梯与决策保全：** 与 FULL29 相同。
