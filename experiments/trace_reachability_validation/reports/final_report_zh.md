# MobileExplorer：Trace-Guided Exploration 与 Backward Reachability Memory 验证报告

> 2026-10-13 实测。主 agent 为 LabServer **GELAB-ZERO-4B**（未启动 MAI-UI）；设备为本地 AndroidWorld 模拟器。所有数字都可以由 `analysis/` 下的文件重新生成。人工标签由 Claude 核对，**不是人类标注**。
> 前置报告：[pilot_findings_zh.md](pilot_findings_zh.md)（Phase I 决策门）、[environment_audit_zh.md](environment_audit_zh.md)。

## 1. Executive Summary

**对两个问题的直接回答**

1. **"探索到的和 agent 后续点的重合度低，能否用图里的 traces 预测 agent 会点什么再排序探索？"**——**能，而且这正是重合度低的主要原因。**
   - 离线（533 次点击，其中 276 次是允许探测的）：当前状态上"agent 过去选过什么"的频率排序，把 top-1 覆盖率从轮询的 **18.5%** 提到 **70%**（之前跑过的运行作为历史）；只用其他任务时为 **40%**；跨 app 没有可迁移信号（29%，与只用本 episode 相同）。更长的上下文几乎没有额外收益。
   - 在线（相同的 18 个新变体，成对运行）：trace 排序让 agent 实际要点的那个动作在**模型返回之前**就被探到并观测完，**TG 9/14 vs 轮询 1/13**；探到的结果与真实执行结果完全一致的 11/14。
   - 在 6 s 的宽预算下，轮询也能把屏上为数不多的安全控件探完（命中 13/18 vs 14/18），所以 **trace 排序的价值只在预算紧时（约 1 次 probe）显现**——而这恰好是 LabServer 约 2 s 推理窗口的真实情况。

2. **"把探索到的子节点信息总结进父节点，能否让图超过传统 UTG？"**——**以 prompt 证据的形式，在 GELAB-4B 上不能。**
   - 47 个人工标注的决策状态、6 种记忆形式中，没有一种有净收益：纠正 ≤ 弄错。
   - 子页面可点击项的"安慰剂"版本（同样长度，挂到错误的元素上）效果与真实信息一样；改变动作的是"多了一段文字"，不是内容。
   - 最有利的测试也失败：8 个 Calendar 状态的证据里明写着 "More options → Go to date"，模型 0/8 采用。
   - **深度 2 在线反而有害**：第二跳回滚失败 40%；深度 2 时 14/18 个 episode 中途停止探索，深度 1 时只有 3/18；agent 接下来两步与探到的两跳一致的只有 1/39。

**结论**：Trace-Guided（深度 1）为 **GO**；Backward Reachability 作为 prompt 证据为 **NO-GO**；深度 2 探索为 **NO-GO**。图里值得保留的父结点信息，应当是"agent 下一步最可能的动作，以及它被验证过的结果"，由运行时使用（推测观测、执行前/后校验），而不是交给模型读。

**仍未证明**：在线闭环的任务成功率提升（TG1 16/18、RR1 16/18、TG 15/18、RR 14/18，样本太小）；推测观测带来的端到端延迟收益（目前只测了潜力，没有实现复用）。

## 2. Motivation（来自上一轮实测）

- 运行时内容变化频繁：截图 62%、a11y 属性 50%；但 GUI 结构稳定（resource-id 只变 2.9%），转移结果明确不同的只有 1.4%。
- 跨变体回放成功率只有 12/56，而且常常是静默失败。
- 上一轮探索器做了 427 次 probe，但 272 次 agent 点击中只有 21 次的结果是由探索器事先观测到的——**探索没有落在 agent 要用的地方**。
- 简单 UTG 证据没有显示出推理收益。

由此出发的两个机制：(A) 用 agent 自己的历史轨迹决定先探什么；(B) 把子页面信息回传给父结点。

## 3. Trace-Guided Exploration

### 3.1 设计
- **动作身份（slot）**：class | resource-id | content-desc | label；带 rid 的列表行折叠为"行族"（行文字是运行时数据），不用坐标。行族假设的检查：7 个观测过多行的行族中，6 个落到同一目的布局；例外是 Markor 文件列表（文件夹和文件共用一个 rid）。
- **续写索引**：从执行序列 `(state_k, action_k, …, state_t)` 中统计下一动作的出现次数，阶数 k = 0…3；state 用结构签名（列表外的控件骨架 + 标题类锚点文本）。纯计数，没有学习，也没有加权分数。
- **策略**（都是按计数的字典序）：
  - P0 轮询；
  - P0u 旧探索器（未观测的优先）；
  - P1 当前状态频率；
  - P2 最长后缀，逐级回退；
  - P3 变阶，只用总支持度 ≥2 的上下文；
  - P4 = P3 + 图前沿：有支持且未知 > 有支持且结果不一致 > 有支持且已知 > 无支持且未知 > 其余。
- **冷启动回退**：P2 → P1 → P0。
- **开销**：143 个 episode 的索引构建 1.9 s；一次查询是若干字典查找，可忽略。

### 3.2 离线结果（Pilot A；图 1–3）

| 历史设定 | P0 | P1 | P2 | P3 | P4 | Oracle |
|---|---|---|---|---|---|---|
| warm top-1（n=276 可探测点击） | 18.5% | **70.3%** | 71.0% | 58.3% | 67.7% | 100% |
| warm top-3 | 50.0% | 86.6% | 86.6% | 80.1% | **87.7%** | — |
| 全部点击作分母的 top-1（n=533） | 9.6% | 36.4% | 36.8% | 30.2% | 35.1% | 51.8% |
| 跨任务 top-1 | 18.5% | 40.2% | 39.9% | 38.0% | 40.2% | — |
| 跨 app top-1 | 18.5% | 29.0% | 28.6% | 25.0% | 29.0% | — |
| 冷启动 top-1 | 18.5% | 29.0% | 28.6% | 25.0% | 29.3% | — |

- **只有 52% 的 agent 点击是允许探测的**：其余是提交、删除、开关类控件。这是"重合度"的硬上限，必须在论文中报告。
- **"新信息"指标**：agent 的下一动作此前从未被观测，而 P4 恰好排在第一，这时探测就能拿到新的、随后被用到的转移。warm 设定下 P4 有 63 次，旧探索器 35 次，oracle 126 次。
- **两跳**：98 对连续、可探测的点击中，第一跳和第二跳都排在第一的，P1 为 45 对，轮询 17 对。
- **更长的历史没有帮助**：P2 ≈ P1，P3 更差。原因是同一状态上 agent 的选择本身已经高度一致；上下文增长只会让计数更稀疏。

### 3.3 失败模式
- 频率会偏向"热门但无关"的动作（例如 Expense 主页的抽屉按钮）。
- 不同任务共享前缀时，跨任务预测会给出别的任务的动作（跨任务只有 40%）。
- 带标签身份的列表行在变体之间对不上（行文字就是参数），只能回退到屏幕顺序。

## 4. Backward Reachability Memory

### 4.1 实现
从图中确定性地派生出父结点上的记录：首跳动作 → 观测到的子页面（activity + 标题）→ 子页面的可点击项（原始 a11y 文本 / desc；无文本时用 rid）→ 第二跳 → 目的页。来源分为两类：

- **verified**：同一次运行中连续执行过；
- **composed**：由两条分别观测到的边拼成，标注为"未一起验证"。

记录保留来源和运行实例，不复制子页面截图（`reachability_memory/pilot_b_memory.json`）。真实例子见图 5：在 Recipe 详情页上，探到 "More options" 的子页面里有 Share / Share as file / Edit / Delete，并验证了 Edit 这一跳。

### 4.2 推理效用（Pilot B；图 4）
- **样本**：47 个状态，覆盖 12 个任务、8 个 app，分三类：
  - E：真实的选错元素，5 个；
  - N：Calendar 逐日翻页，8 个——方向正确但低效，原任务失败正是因为步数耗尽；
  - C：正确的对照状态，34 个。
- **记忆来源**：其他变体的观测加本 episode 之前的观测（反事实代理），不含成功标签和本运行的未来。
- **噪声底**：M0 重复调用 0/47 改变。

| 条件 | 额外 token | 改变 | 纠正 | 弄错 | 采用捷径 |
|---|---|---|---|---|---|
| M1 一跳 UTG | +172 | 7/40 | 1 | 4 | 0/8 |
| M2 + 子页面可点击项 | +341 | 5/40 | 1 | 2 | 0/8 |
| M2P 安慰剂 | +362 | 3/37 | 1 | 0 | 0/8 |
| M2pre（放在任务描述之前） | +342 | 9/40 | 2 | 3 | 0/8 |
| M3 深度 2 路径 | +528 | 5/40 | 1 | 2 | 0/8 |
| M4 整个 app 的图 | +920 | 7/47 | 0 | 5 | 0/8 |

- M1、M2、M2P、M3 在**同一批状态**上产生**同样的改变**，说明作用来自文字扰动，而不是内容。
- "第二次点击是否必要"：在这个模型上，一跳、子页面、两跳都没有收益，深度 2 只多花 token 和探索时间。
- 可纠正的空间本来就小：有证据可用的状态里，真实选错元素的只有约 4 个；GELAB 的失败主要来自低效导航和文本编辑。
- 本次结果与仓库此前"六种注入形式都没有效果、预填才有效"的结论一致。

## 5. Pilot 决策门结果
结果是 **Outcome B**：Trace-Guided 为正，Reachability 为负。因此只对 trace-guided 做在线验证，不把 reachability 加进 prompt。

## 6. 在线验证（Phase II；图 6–8）

- **设置**：6 个任务（Expense / Broccoli / Calendar / Settings / Joplin / Contacts），每个任务 3 个**新**变体，4 个 arm 在同一批变体上成对运行，共 72 个 episode；探索预算 6 s，每窗最多 6 次 probe。
- **arm**：RR = 旧探索器顺序；TG = P4；d1 / d2 表示探索深度。
- **不向 prompt 注入任何内容**；每个 arm 都以上一轮的图和安全记忆为起点。

| 指标 | RR d2 | TG d2 | RR d1 | TG d1 |
|---|---|---|---|---|
| 任务成功 | 14/18 | 15/18 | 16/18 | 16/18 |
| agent 步数 / 模型调用 | 112 / 123 | 112 / 124 | 92 / 95 | 93 / 96 |
| probe 次数（其中第二跳） | 83 (27) | 98 (33) | 129 | 129 |
| 回滚失败 | 27 | 25 | **3** | **3** |
| 探索被中止的 episode | 14 | 14 | **3** | **3** |
| 额外的模型重询 | 11 | 12 | 3 | 3 |
| 可探测点击，且探索仍在运行 | 13 | 14 | 18 | 18 |
| ……agent 的动作在窗口内被探到 | 6 | 8 | 13 | 14 |
| ……观测结果与真实结果完全一致 | 6 | 6 | 12 | 11 |
| ……**在模型返回前完成** | 0 | 0 | **1** | **9** |
| 每次命中可省的观测时间（中位） | 1.40 s | 1.40 s | 1.43 s | 1.41 s |
| 同一批状态上，trace 排序把 agent 动作排第一 / 旧顺序排第一 | — | 5 / 0 | 11 / 0 | 11 / 0 |

其他实测：
- 深度 1 probe 中位 1.90 s；第二跳 1.74 s，回滚成功 36/60。
- 回滚失败的主要来源是第二跳：在子页面上点击（例如 EDIT、对话框中的选项）之后，BACK 无法回到子页面，导致整次探测中止（"aborted_after_failed_second_hop" 24 次）。
- LabServer 推理中位约 1.9 s。

**解读**
1. **深度 2 的代价远大于收益**：中止率 14/18 vs 3/18，额外重询 4 倍，agent 步数也多约 20%（回滚失败会扰乱 agent）；两跳组合命中 1/39。
2. **深度 1 时，轮询和 trace 的命中数接近**，因为 6 s 的预算足够把屏上不到 6 个安全控件探完。**区别在时间上**：TG 先探 agent 最可能点的那个，所以 9/14 的命中在模型返回前就完成了；轮询只有 1/13。也就是说，在真实约 2 s 的窗口（只够 1 次 probe）里，**只有 trace 排序能让探索结果及时可用**。
3. **推测观测的精度足够**：命中中 11/14 (TG1) 和 12/13 (RR1) 的观测结果与真实的动作后状态完全一致，复用一次可省约 1.4 s 的动作后观测时间。按 TG1 的 9 次及时命中 / 93 步估算，每步平均约省 0.14 s——**这是推算，系统中还没有实现复用**。

## 7. 探索是否真的帮助推理？（分层回答）

| 主张 | 证据 | 结论 |
|---|---|---|
| 能预测 agent 会选哪个动作 | 离线 70%（warm）/ 40%（跨任务）；在线 top-1 11/18 | **成立** |
| 能获取有用证据 | 在线 11/14 次命中拿到与真实结果完全一致的下一屏 | **成立**（作为观测） |
| 证据注入后会改变 agent 的动作 | 改变 3–9/40，安慰剂也一样 | 会，但与内容无关 |
| 改进单步正确性 | 纠正 ≤ 弄错；捷径 0/8 | **不成立** |
| 改进闭环任务成功率 | 16 vs 16 vs 15 vs 14 / 18 | **未证明**（样本太小；深度 1 的优势来自更少的回滚失败） |

## 8. 失败分析
- **任务前缀有歧义**：跨任务只有 40%。
- **slot 对应错误**：Markor 文件列表的行族同时包含文件和文件夹。
- **动态内容**：带标签的行身份在变体之间失配。
- **只有视觉的内容**：日历事件块不进 a11y，子页面"可点击项"看不到。
- **无关的子页面信息**：M4 全图弄错 5 个。
- **上下文过长**：M4 多 920 token，输出变短，动作变差。
- **回滚失败**：第二跳失败 40%。
- **探索超出推理窗口**：轮询下命中几乎都晚于模型返回。
- **状态合并**：Calendar 不同日期的日视图被合并，自动生成的标签因此出错，需要人工修正（见 Pilot B）。

## 9. 技术方向决策

| 方向 | 评估 | 依据 |
|---|---|---|
| A：Trace-Guided Frontier Exploration（深度 1） | **GO** | 离线 3.8×；在线让命中提前到模型返回之前（9/14 vs 1/13） |
| B：Backward Reachability Memory 作为 prompt 证据 | **NO-GO**（对 GELAB-4B） | 6 种形式无净收益；安慰剂效果相同；捷径 0/8 |
| C：Trace-Guided + 深度 2 + 回传 | **NO-GO** | 回滚失败 40%，中止 14/18，两跳命中 1/39 |
| D：更简单的一跳 model-free 探索 | **GO**（作为基础） | 回滚失败 3/129；与 A 组合即可 |

## 10. 推荐系统设计（只依据实测）

**架构**：推理窗口内的"预测–预观测–校验"循环。
1. **选择**：拿到当前屏的 a11y 后，查 trace 续写索引（当前状态频率，加最长后缀回退），按 P4 字典序选出 1–2 个首跳 slot。
2. **预观测**：只做深度 1——点击 → 有界 settle → 采集 → 回滚 → 校验（沿用上一轮的回滚梯子和图引导恢复）。
3. **使用**（不进 prompt）：
   - 模型返回的动作如果等于已预观测的 slot，执行后立刻用预观测到的下一屏作为下一次推理的输入，同时在后台重新采集，比对 struct + content 签名，失配就回退到正常路径（**推测观测**，每次命中省约 1.4 s）；
   - 预观测结果同时作为**执行后校验**的期望值：动作后的真实状态与预观测不一致，就是运行时变化的信号。
4. **图结构**：沿用上一轮的不可变转移日志。父结点上只存一条派生记录：`(state, predicted slot) → verified outcome, provenance, runtime instance`。**不再给模型做子页面摘要**。

**代价**：每步 1–2 次 probe（每次约 1.9 s）；索引查询可忽略；存储是追加的 JSONL（上一轮 14 个任务为 2.9 MB）。

**可能的两个技术贡献**：
1. **Trace-conditioned speculative observation**：用 agent 自己的执行轨迹，在推理窗口内、无需辅助模型，预观测它即将执行的动作结果，并在使用前校验（9/14 及时命中，11/14 结果完全一致）。
2. **一个实测的负面结论及其系统含义**：对小型 GUI agent，图证据作为 prompt 无效（安慰剂对照），图的价值应放在执行侧（预观测、校验、预填），而且深度 1 的安全性远优于深度 2。

**与已有工作的边界**：
- PastForward 用历史转移**预测**下一屏并提前**计算**；本设计**真实执行并观测**下一屏，再在使用前校验，两者可以组合。
- OmniFlow / SwiftAgent 复用的是成功轨迹的动作；这里轨迹只用来**排序探索**，不直接执行。
- AutoDroid 的 UTG 与记忆注入正是 Pilot B 测试过、在本模型上无效的形式。

不能把"trace 匹配""图扩展""反向传播"本身当作新点。

## 11. 下一步实验（按优先级）
1. **实现推测观测复用**，在 Phase II 的 6 个任务上测端到端延迟和正确性（失配回退率）。这是方向 A 唯一还没有实测的收益。
2. **预算真实化**：每窗只允许在模型返回前完成的 probe（约 1 次），在 12–20 个任务上比较 TG1 与 RR1 的及时命中率和闭环表现。
3. **扩大可探测集合**：52% 的点击被安全规则排除。对"进入表单""打开菜单"一类可回滚但被保守排除的控件做分级。
4. **换模型复测 Pilot B**（例如更大的 GUI 模型）：判断"证据无效"是模型能力问题，还是证据形式问题。
5. **端侧窗口实测**：更长的窗口下深度 1 能探多少个控件。
