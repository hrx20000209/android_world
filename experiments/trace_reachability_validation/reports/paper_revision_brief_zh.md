## 1. 问题与动机（Motivation）

- **场景：** 移动 GUI agent（本文用 4B 级 VLM，GELAB-ZERO-4B）在 AndroidWorld 上逐步决策，每一步都调用一次 VLM 推理。
- **运行时动态（runtime dynamics）：** 同一 app 的界面在运行时会变化，例如首次启动引导页、弹窗、列表内容不同、标签页状态不同。历史轨迹复用（trajectory reuse）假设界面与历史一致，遇到运行时新出现的状态就会失效。
- **受控证据（可作为 motivating example）：** 在 Markor 首次启动引导页这一运行时新状态上：
  - 基于运行时探索的方法 6/6 次成功越过；
  - 无记忆的 BASE 为 1/6；
  - 历史轨迹复用为 0/6。

  该受控实验也显示，AndroidWorld 中大部分运行时变化是内容层面的，并不构成障碍。因此论文不应声称"运行时变化普遍阻碍 agent"，而应强调"轨迹复用对运行时新状态无能为力，需要运行时获取的知识"。
- **核心思路：** 在运行时与 agent 并行地探索界面，把 agent 自己的执行和探索观测统一组织成一张**运行时图（runtime graph）**。图通过"直接执行、替代决策"的方式减少 VLM 推理次数，同时为探索本身提供安全约束和恢复路径。

## 2. 整体框架（Figure 1 新版结构）

一张图、两个循环：

1. **推理循环（agent loop）：** 输入 = 当前截图 + 任务描述 → VLM agent 决策 → 设备执行。只有在图无法确定下一步时才调用 VLM。
2. **探索循环（online exploration）：** 与每一次 VLM 推理**并行**。在同一台设备上做一次只读探测（点击一个候选控件、观测结果），然后把屏幕恢复原状，并把观测写回图。
3. **运行时图（runtime graph memory）：** 两个循环共享，跨任务持久化。
   - Screen layer：状态节点 + 转移边；
   - Procedure layer：参数化函数。
   - 写入来源有两个：agent 自己执行的转移（agent edge）和探索得到的转移（explored edge）。
4. **图引导执行（graph-guided execution）：** 在每次推理之前读图；能确定的步骤直接执行，替代一次 VLM 决策。

建议 Figure 1 中的连线：
- Agent → Exploration（"in parallel"）
- Exploration → Graph（写入边 + 可回退性证据）
- Device/Agent → Graph（虚线，agent 边）
- Graph → Execution → Device（跳过一次推理）

Figure 1 中应删除：
- "[Memory] Inject" 箭头；
- 顶部 Prompt 中的 [INFO] / [CAUTION] 标签（最终设计不向 prompt 注入图信息）。

## 3. 技术细节（方法部分逐模块）

### 3.1 运行时图的构造（Graph Memory，回应批注 3）

**状态节点（state node）**
- 身份由 activity + 界面布局签名（layout signature）决定，**不包含内容文本**：列表多一行、时间戳变化不会产生新节点。动态内容（时间、计数）在签名中被归一化。
- 设计理由：运行时内容随任务变化，若按内容区分节点，同一页面会被拆成多个节点、永远无法"重访"，图就无法复用。

**转移边（transition edge）**：边 = (源状态, 控件族) → 目的状态。每条边记录：
- **来源（provenance）：** agent（模型自己执行）或 explore（探测得到），并按时间记录最早由谁发现；
- **可回退性证据（reversibility evidence）：** 探测后 Back 能否恢复原状态；
- **目的屏截图（destination capture）：** 用于在不实际进入的情况下判断目的页能否作为函数入口；
- **控件族（control family）：** 控件类别 + resource-id + 文本/描述，用来跨任务、跨内容匹配同一个控件。

**容器级可回退性（container-level reversibility，跨任务学习）**
- 控件的"角色"由其最近的具名父容器（标签栏、数字键盘、工具栏）表示。同一容器内的控件共享返回栈行为，例如切换标签、按数字键都不能被 Back 撤销。
- 一个控件 Back 失败后，整个容器被记为不可回退，并跨任务持久化；通用容器（content/root 等）则只记录单个控件。

**副作用记忆（effect memory）**
- 探测后若屏幕需要靠重启才能恢复，而且恢复后的内容与原来不同（说明修改了 app 数据），该控件被记为"有副作用"，在该 app 内以后不再探测。

**Procedure layer：参数化函数（parameterized function）**
- 函数 = 入口屏 → [导航点击 | 按字段点选 | 按字段输入]* → **停在提交前**，提交（Save/Send/Delete）交还给 agent。
- 字段槽位与任务指令解析出的记录绑定，指令中的表格、key: value、引号字符串、枚举、文件名、数字都会被解析成"字段 → 值"。函数执行时用当前任务的值填入槽位，因此同一函数可以跨任务复用。
- 来源：
  - 历史成功轨迹，跨任务复用时按任务模板做留一（leave-one-out），避免同模板信息泄漏；
  - 本 episode 内自己完成的子轨迹。
- 完整性规则：函数至少 2 个动作、至少 1 个字段槽位；多记录任务（一次添加多条）的函数必须覆盖每条记录的全部字段，因为半填的表单比不填更容易误导模型。
- 扩展（FULL14，作为可选设计）：**模式级表单函数（schema-level form function）**。任务中的一条记录本身就是一个过程：当前屏上有 ≥2 个输入框的标签（hint / resource-id / 上方说明文字）能对上记录字段名时，在一步内填完所有文本字段。字段名有三种归一：
  - 去掉单位词（amount_dollars → amount）；
  - 连写匹配（preparationtime ↔ preparation_time）；
  - 记录首字段（实体名，如 "Recipe: X"）对到 title / name 输入框。

**Figure 1 Graph Memory 面板建议画法**
- 两张行数不同的列表截图指向同一个节点，标注 "content-invariant state"；
- 边上用小标签标注 source / reversibility / capture；
- Procedure 例子改为 `Click "+" → Type <name> → Type <amount> → (stop) → Save`：`<name>` 用颜色标为"来自任务指令"，Save 改为灰色并标注 "left to agent"（不要打红叉，红叉会被误读为执行失败）；
- 可选：标签栏整组被标记为 non-reversible 并跨任务继承。

### 3.2 在线探索策略（Online Exploration，回应批注 1）

**时机：** 每一次 VLM 推理都并行启动一次探测窗口（推理约数秒，探测在这段时间内完成），因此探测不额外占用推理步数。

**候选：** 当前屏的可交互控件。列表行等实体控件不探，它们的数量随内容变化，信息价值低。

**第一级筛选：信息价值（information value）**
1. **去重：** 若"同一 app、同一 activity、同一控件族"的转移已在图中（不论来自 agent 还是探索、来自哪个任务），则不再探测。实测去重前有 32% 的探测是重复的（FULL12：84/265）。
2. **任务相关排序：** 按控件标签与任务"操作词"的 TF-IDF 相似度排序；跨 app 通用的控件（返回、菜单等）排后。说明：任务中 TF-IDF 最高的词通常是参数（实体、数值），用于函数的字段绑定；其余操作词用于给探索排序。TF-IDF 只决定先探哪个，不会直接执行任何动作。
3. **函数入口需求：** 若存在同动词的候选函数，但其首步不能在当前屏落地，就优先探测标签与函数入口相关的控件（入口控件标签、入口页面名），寻找函数能开始执行的页面。
4. **更深一层（depth-2）：** 当前页没有未知控件时，沿一条探索已验证可被 Back 撤销、且跨 activity 的已知边进入下一页，探测那里的未知控件，再退回。同 activity 内的弹出菜单、对话框不作为中间页，因为它们不在返回栈上。深层探测失败的边会被持久记录，以后不再经过。
5. **预测下一步（E1）：** 按本任务记忆预测模型下一步会点的控件，提前打开它。若模型确实选择了这个控件，就直接复用预先观测到的下一屏。

**第二级筛选：可回退性（reversibility）**
1. **暂态门控：** 弹窗、对话框、输入法、选择模式、抽屉打开时不探测。这些状态不在返回栈上，任何探测都会毁掉它们。
2. **副作用排除：** 标签首词为操作动词的控件（Add to / Delete / Save / Send / Start / Lap / Play / Record 等）和开关类控件（Switch / CheckBox / Toggle / Radio）不探测，因为屏幕恢复不能撤销数据层的修改。
3. **事前可回退性预测（FULL15，实验中）：**
   P(rev) = Beta 后验，其中：
   - 先验 = 跨 app 统计的"控件角色 × 屏幕位置"可回退率，来自 954 次历史探测：
     - 单个控件 78%（n=525）；
     - 同类兄弟组 70%（n=334）；
     - 带选中态的兄弟组（标签页、分段选择）37%（n=95）。
   - 似然 = 本 app 同一容器在图中的回退成功/失败次数（先验强度 5）。

   只探测 P(rev) ≥ 0.7 的控件；剩余候选都低于阈值时，这一步不探测。
4. 一个 episode 内回退失败 2 次后停止探索。

**探测与分级恢复（restore ladder）**
1. 原地内容变化 → 再点一次恢复；
2. 切换了标签 → 重新选中原标签；
3. 新页面 → Back（最多 2 次，只在第一次 Back 仅关闭了输入法时才按第二次）；
4. **图重放恢复（relaunch & replay）：** Back 失败时，强制停止 app → 重新启动 → 按本 episode 自启动以来记录的动作路径重放。
   - 前提：路径中不含提交类动作（重放提交会重复副作用），且不超过 12 步；
   - 恢复后按 activity + 布局校验；
   - 实测救回约一半的 Back 失败：FULL11 为 38/78，FULL13 为 31/43。

**探测之后的决策校验（decision validity check）**
- 探测期间模型已基于探测前的屏幕做了决策。若探测后屏幕有差异，但仍是同 activity、同布局，并且模型要点的坐标处是同一个控件（同控件族、同标签），就直接执行模型的决策，不重新推理；否则重新推理（requery）。

### 3.3 图引导执行（Graph-guided Execution，回应批注 2）

**原则：图用来"去掉决策"，而不是"给模型加信息"。**
- 每个执行算子都满足两个条件：
  1. **落地（grounding）：** 在当前实时屏幕上找得到要操作的控件或字段；
  2. **停在提交前：** 提交类动作永远由 agent 自己做。
- 条件不满足就交给 VLM 推理。

**为什么不注入：** 之前的消融中，六种把图信息注入 prompt 的形式（文本提示、高亮元素等）对成功率和步数都无显著作用；而直接替代决策的方式在步数上有显著收益（3.4σ）。另一个原因是，图给出的"下一步该点哪里"的提示正确率约 50%，而模型自己约 90%，模型又倾向于服从文本提示，因此注入是净负收益。

**执行算子（按触发顺序）**

| 算子 | 做法 | 计步 |
|---|---|---|
| 启动折叠（launch folding） | 从任务指令解析出目标 app（app 名 → 启动 activity，只保留图中观测过的包），在第一次推理之前直接打开 | 不计步 |
| 提交确认（commit confirmation） | 模型自己选择提交后，若弹出纯确认对话框（无其他输入控件），直接点击确认按钮 | 1 步 |
| 函数执行（function execution） | 候选函数首步能在当前屏落地时，用任务字段值执行整段函数 | 整段计 1 步 |
| 经图边进入函数入口（edge to function entry） | 当前屏落不了地，但从当前屏出发的某条图边（agent 或探索观测到）的目的屏截图能落地函数首步时，先走这条边再执行函数 | 1 步 |
| 预观测复用（pre-observation reuse） | 模型选中了探索刚探过的控件时，直接复用探测到的下一屏 | 省时间，不省步 |

**卡住处理（独立硬规则，不属于主算法）：** 同一导航控件连续 3 次点击无效果 → 按一次系统 Back，不向 prompt 注入任何内容。
**引导页处理（独立模块）：** 首次启动引导页单独处理，不影响主算法。

## 4. 建议的贡献点表述（3 条）

1. **以执行替代决策的运行时图复用：** 把 agent 执行与在线探索统一组织成跨任务持久的运行时图。通过启动折叠、绑定任务字段的参数化函数、经图边进入函数入口、提交确认，在能落地时直接执行，替代 VLM 决策。
2. **图引导的安全在线探索：** 探索与每次推理并行。由图决定哪些控件值得探（去重、任务相关性、函数入口需求、深一层），以及哪些控件探了会回不来（暂态门控、副作用排除、角色先验与容器证据的可回退性预测、容器级跨任务学习）。
3. **基于图的状态恢复与决策校验：** Back 失败时沿图中记录的路径重启并重放；探测后只要模型决策仍然有效就不重新推理，把探索对推理循环的干扰降到最低。

## 5. 实验设置与计步口径

- **基准：** AndroidWorld，114 个任务（排除 4B_2 结果中出错的任务），单轮 seed 30。
- **模型：** GELAB-ZERO-4B（vLLM 部署），所有臂使用同一模型和同一系统提示。
- **对比：**
  - 4B_2：已有的 4B 基线结果文件；
  - BASE：同一环境、同一 agent，不使用图和探索。
- **计步口径：** 推理步数 = VLM 调用次数（包含探测后的重新推理）。一次多跳的图执行计 1 步；启动折叠在推理之前完成，不计步。4B_2 的 episode 长度本身就是推理步数。
- **噪声：** 同一配置重复运行的成功数波动约 ±10 题，因此成功数的差异需谨慎解读。更可靠的指标是配对推理步数（双方都成功的任务上比较）和机制读数。

- **"探索边 → 函数入口"已真实发生，但次数很少：** FULL14 中，ExpenseAddSingle 的表单入口边（"+"）最早由探索在前一个任务 ExpenseAddMultiple 中发现，后续任务经这条边进入并填完表单。之所以少，是因为函数覆盖面小：可用函数只覆盖 23/114 个任务，有 ≥2 个可落地文本字段的任务约 9–15 个；而且历史函数库通常先于表单函数落地。

## 7. 可以写 / 不能写的结论

**可以写（证据充分）：**
- 运行时图在推理步数上稳定优于 BASE 和 4B_2：配对比较中多数任务更快，每轮约替代 180 次推理。
- 图的收益来自"执行替代决策"，而非 prompt 注入。注入类方式在消融中无显著作用。
- 图感知的安全约束（暂态门控、副作用排除、可回退性学习）和图重放恢复显著降低了探索的代价：重放恢复救回约一半的 Back 失败，FULL13 把重新推理从 44 次降到 14 次。
- 探索扩充了约 20% 的图边，并为函数提供入口，已有实际触发的例子。
- 运行时新出现的状态（如首次引导页）上，轨迹复用失败而运行时探索有效（受控实验 6/6 vs 0/6）。

**不能写（目前没有证据或证据在噪声内）：**
- "探索直接提升了成功率"：成功数差异在 ±10 噪声内；"模型走了探索先发现的边"只说明相关，不说明因果。
- "注入探索结果让模型推理更准确"：与实验证据相反。
- "运行时变化普遍阻碍 agent"：受控实验显示大部分变化是内容层面的，不构成障碍。
- 不要把 FULL12 的成功率优势（56 vs 51/54）写成显著提升，应写成"在保持成功率的同时减少推理步数"。
