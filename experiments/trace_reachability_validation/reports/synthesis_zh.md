# 综合报告：探索的目标、该探什么、图怎么建、图怎么用（截至 2026-10-13）

> 主模型为 GELAB-ZERO-4B（LabServer），环境为本地 AndroidWorld 模拟器。本报告汇总四轮实验：
> - 上一轮的运行时动态研究；
> - Phase I/II（轨迹引导探索、子页面回传）；
> - Phase III（预填闭环）；
> - **同 app 连续任务 + 连续建图**（本轮：BASE / G / GX 三臂各 36 个 episode 已完成，GC 臂运行中）。
>
> 所有数字均为实测；"推算"会单独标出。人工标签由 Claude 核对。

## 0. 本轮新结果：同 app 连续任务 + 连续建图（图 11；三臂已全部完成，GC 臂运行中）

- **设定**：4 个 app × 3 个任务 × 3 轮，每臂 36 个 episode。每个臂在每个 app 内**从空图开始**连续建图，成功的轨迹实时入库。
- **臂**：
  - BASE：纯 agent；
  - G：用 agent 自己走过的边建图，沿跨任务 / 同任务的主导前缀跳步，每跳都验证到达页面；外加坐标修正；
  - GX：G + 探索。有轨迹的页面按轨迹探 1–2 个控件；空隙页面做覆盖式探索。

| | BASE | G | GX |
|---|---|---|---|
| 成功 | 32/36 | 32/36 | 31/36 |
| 两边都成功的配对上的步数 | 253 | **243（−4%，n=31）** | 256 vs 248（**+3%**，n=30） |
| 同配对上的模型调用 | 253 | **231（−9%）** | 260 vs 248（+5%） |
| 跳步：计划 / 实际执行的跳数 | – | 39 / 13 | 37 / 10 |
| 坐标修正 | – | 0 | 0 |
| probe / 探索中止的 episode / 额外重询 | – | – | 194 / 19 / 19 |
| 平均墙钟时间 | 34 s | 34 s | **45 s** |

**解读**
- **图跳步有小而一致的收益**：G 在成功率不变的情况下，模型调用少 9%、步数少 4%。跳步主要发生在 RecipeDeleteMultipleRecipes（8 跳，调用 42 → 34）和 Recipe 系列。
- **跳步受提交动作限制**：39 次计划只执行了 13 跳——主导后续多为 Delete、CONFIRM、SAVE，出于安全只允许导航类跳步。GC 臂（同任务证据可授权提交动作）正在运行，用来检验这一点。
- **坐标修正 0 次**：GELAB 的错误不是坐标偏差。
- **探索在闭环里是净成本**：GX 有 19/36 个 episode 因回滚失败中止探索，并带来 19 次重询；调用 +5%，耗时 +31%。最明显的例子是 SimpleCalendarDeleteOneEvent：1/3 成功、36 次调用，BASE 为 3/3、21 次调用。探索没有带来更多跳步（10 vs 13 跳），也没有找到比 agent 原路径更短的路径（shortcut 0 次）。
- **成功率**：32 / 32 / 31，都在噪声内。

## 2. 回答四个问题

### Q1：探索的目标应该是什么？
数据否定了"覆盖尽可能多的未知转移"：发现贡献 <1%；轮询只覆盖 agent 下一步的 18.5%；深度 2 主要带来回滚失败。按实测，探索只有三个目标是有收益或有潜力的：

1. **预观测 agent 最可能的下一步动作**（深度 1，按轨迹排序）。这是在线唯一测到的正面结果：模型返回前就拿到动作结果 9/14，与真实结果一致 11/14，每次可省约 1.4 s。收益在**时间**，不是正确率。
2. **覆盖"空隙页面"**：同 app 其他任务的 agent 从没操作过的页面。离线上，只有当探索真正覆盖了这些页面的出边，跨任务桥接才把空隙处的预测从 8% 提到 24–42%。这是探索在轨迹之外**唯一**测到的独立价值，还需要在线验证。
3. **学习安全事实**：哪些控件不可回滚（slot / 列表同族 / app 级记忆），让后续探索和执行更安全。

**不应该**做的：深度 2、对已有轨迹覆盖的页面做轮询或覆盖式探索、为了 prompt 去收集子页面文本。

### Q2：探索什么信息能增强 reasoning？
- **对模型本身（GELAB-4B）：没有测到任何一种。** 一跳结果、子页面可点击项、两跳路径、整张图——与"同样长度但错位"的安慰剂效果相同；Calendar 的 "Go to date" 捷径 0/8 被采用。
- **对系统（不经过模型）有用的信息**：
  - (a) **agent 下一步最可能做什么**：来自轨迹，按 (页面, 上下文) 计数；
  - (b) **这个动作在当前运行中会落到哪一页**：探索的预观测或历史后继页面，用于验证和推测观测；
  - (c) **某个控件是否通向已知工作流页面**：由探索覆盖得到，用于空隙页面的探索排序；
  - (d) **哪些控件不可回滚**。

  结论：要"增强推理"，应当**替模型做决定或替模型省时间**（预填 / 跳步 / 预观测），而不是**给模型更多上下文**。这与仓库早先"预填优于注入"的结论一致。

### Q3：graph 应该如何保存和建立？
由上面实际被用到的信息反推出设计：

1. **不可变的转移日志作为事实层**：每条记录包含源页、动作、目的页、来源（agent / 探索 / 回放）、运行实例、回滚结果、证据路径。所有派生结构都可以从日志重建；多次观测到不同结果时全部保留（实测 3.4% 的 slot 有多个结果）。
2. **两级页面身份**：
   - **layout 级**（列表外的控件骨架）用于跨变体 / 跨任务匹配——struct 级会被标题里的数据拆开，人工复核中 14/16 是错误拆分；
   - **struct + content 级**用于执行验证和回滚校验——layout 级会错误合并，例如 Settings 的不同子页。
3. **动作身份**：class | rid | desc | label；带 rid 的列表行折叠为"行族"，行文字视为运行时数据，不用坐标。
4. **每个页面上的续写计数（关键结构）**：按 (页面, 最近 k 步上下文) 统计下一动作，**包括所有动作类型**（输入、滑动、提交、结束）。只统计点击会丢掉任务阶段，实测导致"保存后再点 Add"的失败。
5. **计数分两个作用域：同任务模板、同 app 其他任务**。前者可以授权不可逆的提交动作；后者只能授权可逆的导航，或用于探索排序。
6. **边的属性**：后继页面分布（用于验证）、是否可逆 / 回滚方法、来源实例、最近一次验证时间。
7. **页面属性**：是否位于已知工作流上（被任一任务的 agent 操作过）——桥接用；未知出边数量——空隙探索用；子页面标题与可点击项——只用于探索排序和人工复查，不进 prompt。

### Q4：如何利用 graph 增强 reasoning？
按实测效果排序：
1. **推测观测**（GO）：按轨迹排序，在推理窗口内预观测最可能的动作；模型选中它时，可以直接用预观测的下一屏开始下一次推理，并在后台核对。在线命中 9/14、结果一致 11/14、每次省约 1.4 s（复用尚未实现，端到端收益是推算）。
2. **验证过的预填 / 跳步**（CONDITIONAL）：只对导航动作，用阶段感知的上下文，每跳验证到达页面。减少 5–9% 的模型调用；本轮 G 少 9% 调用、4% 步数，成功率不变。受限于提交动作占多数，需要"同任务证据才允许提交"（GC 臂待补）。
3. **空隙页面的跨任务桥接**（CONDITIONAL，离线正面）：只用于决定先探什么，不用于跳步（"唯一桥接"作为跳步的精度只有 22%）。
4. **执行验证 / 运行时变化检测**（低优先级）：本批任务中历史后继页面 90% 准确，验证只拦下 1/18 次；它拦不住任务阶段错误。
5. **不推荐**：把图或子页面信息写进 prompt（NO-GO，对 GELAB-4B）；坐标修正（没有可修正的错误）；深度 2 探索。

## 3. 下一步
1. 跑完同 app 序列实验和 GC 臂，补齐成功率与步数（每臂 36 个 episode）。
2. **在线验证空隙优先探索**：有轨迹的页面只预观测 top-1，空隙页面做覆盖式探索，用桥接排序；测及时命中率与步数。
3. **实现推测观测复用**，测端到端时间——需要端侧时延（约 10 s/次）才有意义。
4. 用更大的 GUI 模型复测"证据进 prompt"，判断负面结果是模型能力问题还是证据形式问题。
