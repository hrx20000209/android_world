# MobileExplorer：AndroidWorld 运行时动态性 Motivation 与 model-free 图探索可行性研究

> 2026-10-13 凌晨在本地 AndroidWorld 模拟器上实测。所有数字都可以从 `raw/main`、`graphs/main` 用 `scripts/` 重算；每个比例都标明分母。
> **与原计划的偏差**：按用户指示，主 agent 换成 LabServer 上已部署的 **GELAB-ZERO-4B**，而不是 MAI-UI 2B（MAI-UI-2B 的 vLLM 我拉起后已经停止）。任务数为 **14 个，每个 5 个变体**（用户要求"不用选太多任务，循序渐进"）。
> "人工复核"和"正确性标注"都是 Claude 逐张看存档截图完成的，**不是人类标注者**，组会前建议由人抽查。

## 0. 一页结论

| 问题 | 结论（实测） |
|---|---|
| 运行时 UI 变化多吗？ | 对应步上，截图变化 62%，a11y 属性变化 50%，"可点击元素+标签"集合变化 36%；但**列表外的控件骨架、resource-id 几乎不变**（rid 集合变化 2.9%）。变化以**内容/数据**为主，不是结构。 |
| 变化会改变转移吗？ | 回放的 280 个 (state, action) 中，结果明确落到不同状态的只有 **4 个 (1.4%)**；另有 66 个 (24%) 只在布局层面一致。人工复核的同类样本里 14/16 其实是同一个功能屏（被数据文字拆开）。**转移层面的运行时变化很少。** |
| 历史轨迹能直接复用吗？ | 不能。strict / structure-aware 回放的任务成功率都只有 **12/56**。最关键的是**静默失败**：strict 回放有 36 个 episode 每一步都结构匹配地执行完，其中 24 个任务失败（填错金额、类别、联系人、日期）。结构校验发现不了参数/数据错误。 |
| 推理窗口内 model-free 探索可行吗？ | 部分可行。一次 probe+rollback 中位 **1.75 s**（rollback 0.85 s），LabServer 推理中位 **2.0 s**；只有 26% 的 probe 能在本窗口的实测推理时间内完成。单次 rollback 校验成功率 **89%**，但 70 个探索 episode 中 **67%** 至少失败一次（随后按规则停止探索）。 |
| 图能跨变体复用吗？ | 能。struct 匹配下，后续变体里 agent 访问的状态有 **76%** 已在图中（exact 40%，layout 93%）。探索复核旧 slot 时，112/114 (98%) 得到与之前相同的结果。结构匹配人工复核：合并正确 14/16；但被拆开的布局相同对里 14/16 是同一屏（false split）。 |
| 图证据对推理有用吗？ | **未证明**。agent 实际点击的 272 步中，54% 的目标 slot 之前已被观测过，观测结果与实际结果一致的占 84%；但其中只有 21 步的证据来自探索器，其余来自之前变体的 agent 自身执行。单步对照中，局部证据只在 5/23 个状态改变了动作，1 个小幅有益、0 个有害；全图证据改变 6/23，1 个有害。 |
| 探索是否伤害任务？ | 成对比较 v1–v4（56 对）：有探索 36/56，无探索 39/56；不一致对为 3 vs 6（不显著）。但 6 个"只有无探索成功"的 episode **全部**发生过 rollback 失败，不能排除伤害。 |

**一句话**：运行时差异真实存在但主要是内容级的；它让历史轨迹回放"看起来成功、实际出错"。在线、model-free 的观测图能以结构级精度跨变体复用，但探索本身的回滚可靠性和窗口内产出是当前瓶颈，"图证据能提升推理"还没有被证明。

## 1. 研究问题与 Motivation

GUI agent 每一步只看到当前截图，看不到"点了之后会怎样"；历史轨迹或离线知识描述的是另一个运行实例。本实验要回答两件事：(1) 同一任务的不同运行实例之间，屏幕、可操作元素和转移到底差多少；(2) 一个不调用任何模型的探索器能否在推理窗口内真实点击、观测、回滚，并把结果沉淀成跨实例可复用的图。

实测给出的 motivation 比预想的**更窄、但更扎实**：

1. **未执行动作的结果确实看不见**：探索器 427 次 probe 中 354 次 (83%) 打开了新屏（`analysis/probes.csv`）。
2. **跨实例差异主要是内容，不是结构**（第 3 节）。所以"GUI 转移经常变"不成立，**不能**这样写进论文。
3. **真正危险的是"结构不变、语义变了"**：回放在结构上毫无察觉地完成，却输入了错误的参数（第 3.3 节）。图只能验证转移，同样发现不了这类错误。这为"任务推理仍归 VLM、图只提供可验证的转移证据"的分工提供了实测理由。
4. **a11y 也有盲区**：38 个对应步的 a11y 树完全相同、截图却明显不同（日历自绘的事件块、弹出菜单下面的页面），见第 3.4 节。

## 2. 实验设置

### 2.1 环境
- 本地 AVD `emulator-5554`（Android 13，1080×2400，Apple M4 主机）。详见 [environment_report.md](environment_report.md)。
- 模型：LabServer RTX 4090 D 上的 GELAB-ZERO-4B（vLLM 0.13，`--seed 0`），经 SSH 隧道访问；temperature 0，每个请求带独立 `cache_salt`。
- Agent：仓库 `gelab_agent.py`，与 4B_2 基线版本逐字节一致；runner 只把 step 拆成"后台决策 + 执行"，prompt/parser 未改。步数上限 min(20, 复杂度预算)。

### 2.2 任务与变体（[task_manifest.csv](task_manifest.csv)）
14 个任务、10 个 app，每个任务 5 个 seed（官方 `_instantiate_task(seed)`，参数和 app 数据都由 seed 决定）：

| 类型 | 任务 | 变体机制 |
|---|---|---|
| 列表删除 | ExpenseDeleteSingle, RecipeDeleteSingleRecipe, MarkorDeleteNewestNote | 参数 + 列表数据（MarkorDeleteNewestNote 目标文字相同，只有数据变） |
| 表单录入 | ExpenseAddSingle, ContactsAddContact, MarkorCreateNote | 参数 |
| 导航 + 查询 | SimpleCalendarEventsOnDate, TasksDueOnDate, NotesTodoItemCount, SportsTrackerLongestDistanceActivity | 参数 + 数据 |
| 导航 + 删除 | SimpleCalendarDeleteOneEvent, RecipeDeleteMultipleRecipesWithConstraint | 参数 + 数据 |
| 动态内容 | OsmAndFavorite | 参数 + 地图渲染 |
| **对照** | SystemBluetoothTurnOn | **5 个 seed 目标完全相同**（测运行时噪声底） |

没有使用屏幕尺寸/字体等布局变体（E 类），所以本实验**测不到**坐标漂移。

### 2.3 每个任务的 episode
1. **干净参考**（无探索）：v0 最多 3 次，取第一次成功的。TasksDueOnDate 3 次都失败，只能用失败轨迹作参考（已标注）。
2. **agent + 探索**：v0…v4，共享一个按顺序增量构建的图。
3. **agent 无探索**：v1…v4（与第 2 项成对，用来测探索的副作用）。
4. **strict 回放**、**structure-aware 回放（+ 发散后单独标注的 VLM recovery）**：v1…v4。

总计 **255 个有效 episode**：19 个参考尝试、70 个探索、56 个无探索、56 个 strict、56 个 struct；运行错误 0 个。原始证据 330 MB。

### 2.4 关键定义
- **状态签名**（`rgs_ui.py`）：`exact`（全部 a11y 属性）、`struct`（activity + 键盘 + 列表外控件骨架 + 列表外非数字锚点文字）、`layout`（struct 去掉锚点文字）、`content`（列表文字、输入框内容、勾选状态）。systemui 只有在是状态栏/导航栏大小时才剔除（下拉快捷设置等全屏 systemui 窗口保留）。
- **对应步**：structure-aware 回放中，现场 pre-state 与参考 pre-state 在 struct 或 layout 层一致的步（n=278，覆盖 14 个任务）。
- **截图变化**：灰度差 >25 的像素占比超过 0.1%（同屏不同帧约为 0）；另报 0.5% 阈值的结果。
- **回放安全**：strict 只在坐标仍然命中同一 selector（文字参数按目标文字替换后）时执行；struct 用逐级精确谓词重定位目标（exact selector → 稳定层级 → 结构唯一），候选多于一个就判为歧义并停止，**不用加权相似度**。

**三类阻止回放的运行时变化（都有原始证据）**：
1. **参数/数据导致的静默偏离**（最主要）。ExpenseAddSingle：参数里金额存成分（37411），目标文字写 "$374.11"；类别是整数 id，目标写 "Housing"。字面替换映射不到，回放把参考的金额和类别原样录入，4/4 静默失败。ContactsAddContact、SportsTracker、Calendar 查询同理（日历点的是参考日期的格子，格子标签 "27" 不是参数字面值）。
2. **与任务参数无关的运行时内容**。对照任务 SystemBluetoothTurnOn 的 5 个 seed 目标完全相同，strict 回放仍然 4/4 失败：参考轨迹点的是 launcher 应用抽屉"推荐应用行"里的 Settings，而这一行由使用历史决定，变体里 Settings 不在屏上，原坐标落在别的 app 上（strict 正确地拒绝了执行）。这是"同一任务、同一参数、不同运行时状态"的真实例子。
3. **重复目标**。structure-aware 用精确标签重定位时，屏上常有多个同标签元素（同名笔记、多个 "Avocado Toast"），按规则判为歧义并停止。strict 反而因为坐标本身能消歧而多完成了 8 个 episode。

**没有观察到坐标漂移**：所有执行的点击步，原坐标都仍然命中同一目标，重定位 0 次。在固定设备、固定分辨率下，"坐标漂移"不是回放失败的原因；要测它需要布局变体（未做）。

### RQ4：截图差异是否对应可操作元素或转移的变化（图 2、图 5）

- 截图变化的 173 步中，可点击元素+标签集合变化 97 步 (56%)，struct 签名变化 55 步 (32%)；列表外控件骨架变化 0 步。
- **转移层面**：structure-aware 回放的 280 个 (state, action) 中，结果与参考 exact 相同 108 个，struct 相同（仅内容不同）102 个，layout 相同 66 个，**明确不同的状态 4 个 (1.4%)**，无可观测转移 0 个。人工复核的同类"layout 相同、struct 不同"样本中，14/16 是同一功能屏，所以 1.4%–25% 这个区间里真实值更接近下界。
- **反方向（a11y 盲区）**：38 个对应步 a11y 完全相同、截图却不同，出现在 5 个任务（日历、OsmAnd、Recipe、Tasks）。例：日历月视图在不同变体下事件块完全不同，但这些块是自绘的、不进 a11y 树；Recipe 的溢出菜单是弹窗，dump 只覆盖弹窗，看不到下面的不同菜谱。

**结论**：截图差异绝大多数是内容级的；转移语义在跨实例间非常稳定。不能把"截图变化"当成"转移变化"来做 motivation。

## 4. MobileExplorer 设计目标

**在 agent 推理窗口内逐步构建一个"运行时验证过的 GUI 转移图"，并把观测到的交互证据提供给后续推理。**

结合实测，这个目标统一了两件事：

- *未知转移发现*：当前屏的出边只有执行后才能知道。
- *运行时验证*：旧观测在新实例中是否仍然成立，需要（少量的）重新观测。实测表明大多数旧转移会继续成立（98%），所以验证的价值在于**发现少数变化并标注置信度**，而不是频繁重探。

图只证明"环境里发生了什么转移"，不证明"动作对任务是否正确"。第 3.3 节的静默失败说明，这条边界在实践中确实重要。

## 5. 技术设计（本实验实现的最小原型；均不调用额外 VLM/LLM）

### 机制 1：Persistent Action Frontier
- **解决的问题**：每个屏上哪些交互还没观测、哪些已观测、哪些已知不可恢复。
- **做法**：解析 a11y flat dump，取可点击、可见、可用的 app 节点 → 按 bounds 去重 → slot id = class|rid|desc|label(+序号) → 按 (y, x) 确定性排序（不做语义打分）。安全 deny-list：开关、输入框、对话框 button1/2/3、遮罩、".."、下拉/单选项、删除/发送/保存/确认等文字。
- **实测**：500 个推理窗口共见到 3769 个 slot，其中 2086 个 (55%) 判为安全；其中 1380 个未探索、312 个来自其他变体（待复核）、65 个本次已探索、329 个已知不可恢复而跳过。
- **开销**：dump 在设备端 3–70 ms。
- **局限**：deny-list 是人写的，仍然漏掉了有副作用或不可回滚的控件（Markor 对话框的 FOLDER 按钮会真的创建文件夹、编辑器的 View mode 切换、下拉选项），只能靠回滚校验发现、靠记忆避免再犯。

### 机制 2：Model-Free Probe–Observe–Rollback
- **做法**：模型请求在后台线程发出后，探索器在**模型正在看的同一屏**上执行：点击 → 有界 settle（两次连续 dump 相同，或 3 s 超时）→ 采集 → 回滚 → 校验。回滚梯子依次是：无需回滚 → 原地变化就再点一次 → tab 类控件重新选中原 tab → BACK（只有第一次仅关闭键盘或无变化时才按第二次）→ **图引导恢复**（在图中找 ≤2 跳的已观测边回到源状态，按精确 selector 逐跳校验）。校验要求 struct 和 content 签名都与源状态一致。失败后本 episode 停止探索；执行模型动作前再比对一次，如果屏幕已不是模型看到的那一屏，就重新观测并重新请求模型。
- **实测**：427 次 probe，校验通过 380 次 (89%，CI 86–92%)。各方法：BACK 296、无需回滚 48、再点 13、重新选中 5、图引导恢复 18（失败 8）。失败 47 次，其中 BACK 失败 32 次。70 个探索 episode 中 47 个 (67%) 至少失败一次；500 个窗口中 211 个因此处于关闭状态；45/500 步需要重新请求模型。
- **局限**：BACK 的语义因 app 而异；有些操作在 UI 上可回滚，却有持久副作用。

### 机制 3：Runtime Observation Graph
- **做法**：所有转移（agent、探索、回放）以不可变 JSONL 追加，节点和边是重建出来的视图。同一 slot 的多个结果全部保留；不可恢复记忆有三级：slot、列表同族（同屏同 rid）、app 级（跨任务）。
- **实测**：struct 图共 287 个节点、422 条边、506 个已观测 slot，其中多结果 slot 17 个 (3.4%)。原始图证据共 2.9 MB（14 个任务）。
- **局限**：struct 签名会把带数据的标题拆成不同节点（false split），layout 签名会合并不同设置子页（见 RQ6）。

### 机制 4：Graph Convergence and Stitching
- 新观测的目的状态如果已经是图中节点，并且之前从别的 (源, slot) 到达过，就记为汇合。struct 规则下共 163 次汇合（后续变体中 144 次）。图 7 的例子：从 v3 编辑页返回，落到 v0 探索时已见过的"日视图"节点。两张截图的日期不同，正好说明汇合只是状态模板的对应，**不是任务进度**。

### 机制 5：Evidence Retrieval for Inference
- 按当前 struct 签名取**本步观测时间之前**记录的出边，生成"点击 'X' (x,y) → 打开某 Activity；出现 'A','B'"这样的文本，不含任何任务成功信息。
- 效用见第 6.5 节：没有测到收益。

## 6. Design Feasibility 结果（RQ5–RQ9）

### RQ5：有界探索能发现多少未知转移（图 6、图 8）
- 70 个探索 episode 共 427 次 probe：313 次是首次探索（discover），114 次是跨变体复核（revalidate）；新屏 354、无变化 48、原地变化 18、离开 app 7。
- 每次 probe（含回滚）耗时中位 1.75 s、p90 2.60 s；≤1 s 的只有 11%，≤2 s 的 67%。LabServer 推理时间中位 2.03 s（p10 0.94、p90 2.66）。按每个窗口的实测推理时间截断，只有 **112/427 (26%)** 的 probe 能在推理期间完成。在仍允许探索的 289 个窗口里，平均每窗 1.48 次 probe。
- 本原型串行地先探索、后等模型，平均每步墙钟时间约 2.97 s，而模型本身平均 1.89 s：**探索在远端推理设置下拉长了关键路径**。如果在手机上推理（仓库此前在 Orin 上测得约 10 s/步），窗口能容纳约 5 次 probe——这只是**推算**，没有在设备上测。

### RQ6：新状态能否匹配到已有节点（图 9、人工复核）
- 后续变体（v1–v4）中 agent 访问过的 400 个状态，已在图中的比例：exact 159 (40%)，**struct 303 (76%)**，layout 372 (93%)。
- 按 struct 规则建图，图中节点为 287 个；各变体单独建图节点总数为 583 个（per-run）。
- 人工复核（`analysis/review/labels.json`，各 16 对）：
  - struct 合并的跨变体对：**14/16 确为同一功能屏**；2 个错误合并：联系人表单姓名区展开/折叠；Settings "Bluetooth" 与 "Pair new device"（标题位于滚动容器内，未计入锚点）。
  - layout 相同、struct 不同（被拆开）的对：**14/16 其实是同一功能屏**（标题中的实体名、日期、对话框消息、toast 让它们被拆开）；只有 2 对确实不同（表单焦点不同导致 NEXT 与 SAVE；OsmAnd 校验错误导致 Save 禁用）。
  - struct 规则下，39% (112/287) 的新状态与已有节点 layout 相同，被保守标为歧义。
- **结论**：struct 规则合并精度高，但拆分过细；layout 规则召回高，但会错误合并。需要介于两者之间的规则，例如锚点只取 toolbar 标题的模板部分，或用"出边行为是否相同"来决定是否合并。

### RQ7：探索路径多常汇合到已有节点
- struct 规则下 163 次汇合（exact 98 次、layout 182 次），汇合目标此前已观测出边合计 656 条（按事件累计，有重复计数）。
- 实际避免的重复探索：本次已探索而跳过 65 次，不可恢复而跳过 329 次；另有 312 次"其他变体已知"的 slot 被有意复核。如果只做发现、不做复核，这 312 次 probe 都可以省下，代价是第 RQ8 节的那 2% 变化无法被发现。

### RQ8：能否保留跨变体的结果变化而不错误合并
- 探索复核：struct 规则下 112/114 (98%) 与之前结果相同；layout 规则 159/162 相同，exact 规则 69/74 相同。
- agent 自身执行的复核：struct 规则下 221/250 (88%) 相同（agent 动作包括输入等，结果依赖参数）。
- 多结果 slot：struct 17/506；图中全部保留并标注实例，没有覆盖旧观测。
- 错误合并只在人工样本中观察到 2/16；没有自动方法量化全量错误合并率。

### RQ9：哪些证据可能对推理有用；收益是否被证明

**证据相关性**（`analysis/summary.json → evidence_relevance`）：探索 episode 中 agent 共点击 272 次：
- 当前状态在本步之前已在图中：191 次 (70%)；
- agent 选的 slot 之前被观测过：146 次 (54%)；其中观测结果与本次实际结果 struct 一致的 122 次 (84%)，不一致 20 次 (14%)；
- 但这 146 次中，**只有 21 次的观测来自探索器**，其余来自之前变体中 agent 自己的执行。

也就是说，跨运行记忆的价值主要来自"之前跑过的轨迹"，推理窗口内的探索只额外贡献了很小一部分相关证据。

**单步效用对照**（6.5；`analysis/utility/`；图 10）：23 个决策状态，覆盖 12 个任务，证据只取本步之前的观测。
- A（无证据）vs B（局部证据，平均多 227 个 prompt token）：动作改变 5/23。其中 1 个小幅有益（直接在已获焦的输入框输入，省一步），3 个中性，1 个不确定；有害 0。
- A vs C（全任务图，平均多 628 token）：动作改变 6/23，其中 **1 个有害**（未取得答案就 STATUS 结束）。
- 一个典型反例：Markor 删除任务中，B 的证据明确写着 "点击 Delete lines → no visible change"，模型仍然重复这个无效动作。
- 延迟差异不可解读：A 总是先请求，可能受冷启动影响。

**结论**：没有证据表明图证据能提升 GELAB-4B 的单步决策；也没有做闭环 A/B。要建立推理收益，需要 (1) 把证据放在模型最需要的时刻（比如本例的循环、未知控件），(2) 更强的标注，(3) 闭环成功率实验。

### 探索对任务的副作用
v1–v4 成对比较 56 对：两边都成功 33、都失败 14、只有探索成功 3、只有无探索成功 6。McNemar 检验 3 vs 6 不显著；但"只有无探索成功"的 6 个探索 episode 全部发生过 rollback 失败。按仓库已有的经验，单次运行的成功率波动约 ±10/115，这里无法下结论，但机制层面有明确风险。

## 7. 与已有工作的区别（保守表述）

OmniFlow / SwiftAgent / PastForward / PRMAgent 的概括沿用仓库 `docs/` 中依据原稿整理的描述；AutoDroid 依据其公开论文；GUI-Xplore 依据 arXiv 2503.17709。**EchoTrail-GUI 在本地没有原文，下表只列出需要核实的维度，不作判断。**

| 工作 | 探索时机 | 探索是否依赖 VLM/LLM | 运行时更新记忆 | 结果被实际执行验证 | 图汇合 | 与推理重叠 | 测了推理收益 |
|---|---|---|---|---|---|---|---|
| AutoDroid | 离线探索建 UTG | 生成 task memory 用 LLM | 以离线为主 | 探索时真实执行 | 未作为机制 | 否 | 测了任务完成 |
| GUI-Xplore | 离线探索视频 | 下游用 VLM | 每个 app 一份 | 真实执行 | 屏幕类型聚类 | 否 | 测了下游任务 |
| OmniFlow | 历史成功轨迹编译 | 失配时回到 VLM | 成功后更新 | 回放时 re-grounding | 状态匹配 | 否 | 测了效率 |
| SwiftAgent | 历史 workflow + reuse point | gap 由模型补 | 成功后更新 | 回放验证 | — | 否 | 测了效率 |
| PastForward | 历史 transition / KV | 用模型提前计算 | 在线累积 | 用当前屏验证预测 | — | **是（提前计算，而不是提前观测）** | 测了延迟 |

"用图""自动探索""记忆注入""回放 re-grounding"本身都不是新点。本实验支持的区别只有：(1) 探索与推理窗口重叠、完全 model-free，并且回滚有校验；(2) 图保留跨运行实例的多结果观测，并用观测到的失败来泛化安全规则。

## 8. 主要发现与局限性

**得到支持**
- 运行时变化普遍存在，但集中在内容层（截图 62%、a11y 50%），结构层很少（rid 2.9%）。
- 历史轨迹回放很脆弱：任务成功 12/56，**静默失败多达 24 个**。
- 结构级状态匹配能跨变体复用：后续变体 76% 的状态已在图中，合并精度 14/16。
- 已知转移在跨变体时高度稳定（98%）；图能保留少数变化。

**没有得到支持 / 不成立**
- "转移经常变"：明确不同的只有 1.4%。
- "坐标漂移是回放失败的原因"：本设置下 0 例（没有做布局变体）。
- "探索产生的证据能改善推理"：单步对照中，有益 1、有害 0–1，闭环未测；相关证据主要来自之前的 agent 轨迹，而不是探索。
- "探索在推理窗口内基本免费"：在 2 s 的远端窗口内，只有 26% 的 probe 能完成；回滚失败让 67% 的 episode 中途停止探索。

**局限**
- 用的是 GELAB-ZERO-4B，不是 MAI-UI 2B；推理在 LabServer 上远端执行，延迟和端侧不同，所有端侧窗口数字都是推算。
- 每个任务 5 个变体、14 个任务；同一任务内的步不是独立样本（因此同时报告按任务平均）。
- 人工复核和标注由 Claude 完成，样本量小（各 16 对、23 个状态）。
- 实验中途根据观察到的失败修了几处实现：z-order 命中判断、tab 重新选中、值选择项、全屏 systemui 窗口。之前的运行保留在 `raw/old_*`，未进入统计；MarkorCreateNote 和 MarkorDeleteNewestNote 的探索臂在修复后重跑过。由于这些修复，各任务的安全规则并不完全同一时刻生效（见 `execution_log.md`）。
- TasksDueOnDate 没有成功参考，它的回放只能作为"参考错误"的例子。
- 签名中的锚点规则（排除纯数字和时间）是启发式的。

## 9. 下一步设计建议

1. **把回滚可靠性当作一等问题**。每个 episode 的失败率 67% 是可行性的头号障碍。可以尝试：(a) 隔离的探索实例或状态快照（仓库已有 parallel_exploration_state_capture 的思路），让探索根本不需要回滚；(b) 第一次遇到某个控件前，先按 app 级不可恢复记忆做冷启动的保守限制；(c) 用图引导恢复（本次挽回 18 次）作为基线机制继续扩展。
2. **按 agent 的需要定向探索，而不是 round-robin**。agent 点击中有 46% 的目标 slot 从未被观测过；应当测试"优先探索 agent 最可能点的那一类控件"（不用 VLM 打分，例如用历史转移频率）能否提高 21/272 这个比例。
3. **改进状态模板**：在 struct 与 layout 之间找一个能同时降低 false split 和 false merge 的规则（例如锚点取 toolbar 标题、加入"出边行为相同"判据），并在更大的人工样本上测精度。
4. **把回放的静默失败作为 motivation**，再加一个"参数感知回放"的强基线：用目标文字的 diff 驱动替换，并对日期/金额等格式做归一化。
5. **端侧实测**：在真机上测推理窗口与 probe 的真实重叠。
6. **闭环 A/B**：在 37 个"波动任务"上做有/无证据的闭环对比，并使用同一会话内的重复运行来估计噪声。

**最能站住的 1–2 个技术贡献**：
- (A) 一个**实测研究**：AndroidWorld 的运行时差异以内容为主、转移非常稳定，而轨迹回放会静默出错。这为"转移可复用、语义仍需模型"的分工提供了量化依据。
- (B) **带回滚校验、并从失败中泛化安全规则的 model-free 运行时观测图**（多结果保留、跨任务的不可恢复记忆、图引导恢复），并给出可靠性和成本的实测数据。

要达到 MobiSys/MobiCom/SenSys 的门槛，至少还需要：回滚失败率降到每个 episode 个位数百分比；端侧窗口的实测；闭环的效率或成功率收益（相对于强的参数感知回放基线）；更多 app 和变体，以及人工标注的精度数据。

**可能被问到的问题**
- 为什么不是 MAI-UI 2B？→ 按指示用了 GELAB-4B，结论中与模型无关的部分（UI 动态、回放、探索成本）可以迁移，推理效用部分需要重测。
- 探索会不会拖慢 agent？→ 在远端设置下会（每步约 +1.1 s）；端侧窗口更长，但没有实测。
- 98% 的转移不变，为什么还要在线探索？→ 价值在于未执行的出边（83% 的 probe 打开了新屏），以及少数变化的检测；但目前证据还没有转化为推理收益。
- 安全 deny-list 是不是人工规则？→ 是；目前靠回滚校验加记忆兜底，漏网的例子都在日志里。

**仍需要的实验**：闭环 A/B、端侧窗口、布局变体（坐标漂移）、更大的人工复核样本、参数感知回放基线。
